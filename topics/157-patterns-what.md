# 1. Тема

**Что такое паттерны проектирования**

---

# 2. Главное в одну фразу

Паттерн проектирования — именованное решение типичной задачи устройства кода: когда применять, какие роли у частей и чем платить за гибкость.

---

# 3. Суть

> Паттерн проектирования — это не библиотека и не фрагмент «скопируй и вставь», а **именованный рецепт**: при какой ситуации он уместен, какие объекты/модули участвуют, как они связаны и какой ценой даёт гибкость. Классический каталог GoF (Gamma et al.) группирует решения в порождающие, структурные и поведенческие.
>
> В работе паттерны нужны, когда одна и та же «боль» повторяется: создать объект без жёсткой привязки к классу, спрятать сложную подсистему за простым фасадом, оповестить подписчиков об изменении. Общий язык («тут Observer», «вынесем Strategy») ускоряет обсуждение рефакторинга и чтение чужого кода.
>
> Паттерн выбирают **после** появления проблемы, а не «на всякий случай». Слепое навешивание классов-фабрик и посредников усложняет код без выгоды. Антипаттерн — когда «решение» само становится источником боли: God Object, копипаста вместо общего контракта, Singleton как глобальная скрытая зависимость.

---

# 4. Самое главное запомнить

- Паттерн = контекст + проблема + структура решения + последствия; не «красивое имя класса».
- Три семьи GoF: **порождающие** (как создавать), **структурные** (как стыковать), **поведенческие** (как взаимодействовать).
- Паттерн описывает роли и связи; конкретный синтаксис в JS/TS/Java может отличаться.
- Сначала боль в коде, потом паттерн; иначе легко получить overengineering.
- Антипаттерн — устойчиво вредный приём; его узнают и сознательно избегают.
- В экосистеме фронта/бэка те же идеи часто уже «вшиты» в API (`addEventListener`, DI-контейнеры, middleware) — важно узнавать идею, а не только UML из учебника.

---

# 5. Описание

```text
повторяющаяся боль в коде
        │
        ▼
  есть ли именованный паттерн?
        │
   да ──┼── нет → локальное простое решение / рефакторинг без ярлыка
        ▼
  подходит ли контекст?
        │
   да ──┼── нет → другой паттерн или без паттерна
        ▼
  внедрить роли и связи
        │
        ▼
  проверить цену: читаемость, связность, тесты
```

## Зачем вообще «имена»

Без общего словаря команда спорит о реализации: «вынесем колбэк», «сделаем класс-менеджер», «подписку на события». С паттерном достаточно сказать: «нужен Observer» или «спрячем за Facade» — и у всех появляется одна картина ролей.

Паттерн **не заменяет** понимание домена и данных. Он помогает структурировать уже понятную задачу: уведомления UI, смена алгоритма расчёта, единая точка создания объектов.

## Три семьи (GoF)

| Семья | Вопрос | Примеры (дальше по группе) |
|---|---|---|
| Порождающие | *Как* создавать объекты, не размазывая `new`? | Factory, Prototype, Singleton, Abstract Factory |
| Структурные | *Как* собрать части в целое без жёсткой спайки? | Adapter, Proxy, Facade, Decorator, Bridge, Composite, Flyweight |
| Поведенческие | *Как* объектам взаимодействовать и менять поведение? | Observer, Strategy, Command, Chain of Responsibility, Mediator, Template Method, Memento |

В этой группе тем конкретные паттерны разбираются отдельно; здесь важно уметь отнести идею к семье и не путать «создание» со «связью» или «общением».

## Паттерн ≠ алгоритм ≠ фреймворк

- **Алгоритм** — способ вычислить результат (сортировка, поиск). Паттерн — способ **организовать** код вокруг задачи.
- **Библиотека / фреймворк** — готовый код. Паттерн — описание; реализация своя или уже встроена в API.
- **Идиома языка** — короткий приём конкретного языка (`??`, деструктуризация). Паттерн обычно шире и переносится между языками.

Пример узнавания в браузере: подписка на DOM-события — идея **Observer**; обёртка над неудобным API сторонней либы — идея **Adapter**; цепочка middleware в Express — близка к **Chain of Responsibility**.

## Как решать «нужен ли паттерн»

1. Сформулировать боль: что ломается при изменении требований (дублирование, жёсткая связка, невозможность подменить поведение в тестах).
2. Проверить, что простого рефакторинга (вынести функцию, разделить модуль) недостаточно.
3. Взять паттерн с подходящим контекстом и **минимальной** реализацией под язык (в JS часто хватает функций и модулей вместо иерархии классов).
4. Оценить последствия: стало ли проще менять одну ось и не стало ли хуже читать «счастливый путь».

Короткий контраст «без паттерна / с идеей Strategy» (смена способа доставки без `if` по всему коду):

```js
// боль: ветвление размазано
function ship(order, type) {
  if (type === 'courier') { /* … */ }
  else if (type === 'pickup') { /* … */ }
}

// идея Strategy: способ доставки — подставляемый модуль
const strategies = {
  courier: (order) => { /* … */ },
  pickup: (order) => { /* … */ },
};

function ship(order, type) {
  const run = strategies[type];
  if (!run) throw new Error(`unknown: ${type}`);
  return run(order);
}
```

Имя «Strategy» здесь не обязательно писать в коде — важна **идея**: алгоритм вынесен за контракт и подменяется целиком.

## Антипаттерны и ловушки

| Ловушка | Как проявляется | Что делать |
|---|---|---|
| Паттерн «на вырост» | Лишние слои, фабрики фабрик | Ждать реальную боль |
| Имя вместо смысла | Класс `ManagerHelperService` без ролей | Описать контекст и связи |
| Singleton как глобал | Скрытые зависимости, сложные тесты | Явная передача зависимостей / DI |
| Копипаста UML из Java | Тяжёлые классы там, где хватит функции | Адаптировать к идиомам языка |

Антипаттерн — не «плохой паттерн GoF», а **устойчиво вредный** способ решать задачу (или «решать» без нужды). Его полезно знать, чтобы узнавать в ревью и в собственном коде.
