# 1. Тема

**TCP/IP: межсетевой и прикладной уровни**

---

# 2. Главное в одну фразу

Прикладной уровень задаёт смысл обмена (HTTP, DNS, …), межсетевой — доставку датаграмм по IP между сетями; вместе они отвечают на «что сказать» и «куда слать пакет», не подменяя транспорт и канал.

---

# 3. Суть

> В модели **TCP/IP** четыре уровня. Эта тема — про два верхних относительно «железа»: **прикладной** (application) и **межсетевой** (internet / IP). Прикладной — протоколы, которыми пользуются приложения и сервисы: формат сообщения, имена, семантика. Межсетевой — логическая адресация и маршрутизация: IP-пакет с адресами источника и назначения, пересылка через роутеры, служебные сообщения вроде ICMP.
>
> На практике это две разные «плоскости». Браузер и API думают HTTP-методом и путём; DNS отдаёт имя → IP. Сеть между хостами думает датаграммами: какой next hop, жив ли маршрут, не истёк ли TTL. Без прикладного уровня нет понятного контракта «клиент ↔ сервис»; без межсетевого — нет пути пакета через разные сети.
>
> Как стыкуется поток. Приложение формирует сообщение прикладного протокола (запрос DNS, HTTP, SMTP…). Ниже транспорт (TCP/UDP — отдельная тема) даёт порты и доставку на хост. Межсетевой уровень упаковывает сегмент в **IP-пакет**, роутеры смотрят на IP назначения и пересылают. На приёме слои снимаются в обратном порядке — до приложения снова доходит смысловое сообщение.
>
> Ловушка: путать «сайт открылся» с одним уровнем. Ошибка DNS — прикладная (имя не резолвится); `ENETUNREACH` / ICMP unreachable — уже про IP-путь. HTTP подробно — соседняя тема; TCP, порты и Ethernet — транспортный и канальный уровни. Здесь важно уметь сказать, *на каком уровне* ломается сценарий.

---

# 4. Самое главное запомнить

- Прикладной уровень TCP/IP ≈ OSI 5–7 в одной корзине: HTTP, DNS, SMTP, FTP… — смысл для приложений.
- Межсетевой уровень: **IP** (адресация + маршрутизация датаграмм), рядом ICMP (ошибки/диагностика), ARP ближе к стыку с каналом.
- Приложение видит имя/URL и сообщение протокола; сеть для доставки использует **IP**, не hostname.
- Инкапсуляция вниз: сообщение приложения → (транспорт) → IP-пакет → кадр канала.
- Роутер на пути обычно не разбирает HTTP — смотрит IP (и иногда транспорт для ACL/NAT).
- DNS — прикладной протокол, но его ответ *кормит* межсетевой уровень адресом для маршрутизации.
- Не смешивать с транспортом: порты, TCP handshake и Ethernet — не эта пара уровней.

| Уровень TCP/IP | Вопрос | Примеры |
|----------------|--------|---------|
| Прикладной | Что сказать сервису? | HTTP, DNS, SMTP |
| Межсетевой | Куда и как доставить пакет между сетями? | IP, ICMP |

---

# 5. Описание

```text
Приложение
   │  HTTP / DNS / …     ← прикладной уровень
   ▼
Транспорт (TCP/UDP)       ← не эта тема (см. «транспортный и канальный»)
   │
   ▼
IP-пакет src → dst        ← межсетевой уровень
   │  роутер → роутер → …
   ▼
Канал / физ. носитель     ← не эта тема
```

## Прикладной уровень

Здесь живут протоколы **между приложениями** (или процессами, которые им служат). Сообщение несёт смысл: «дай запись A для `api.example.com`», «`GET /users`», «отправь письмо».

Типичные представители:

| Протокол | Роль |
|----------|------|
| **HTTP(S)** | Запрос/ответ веб и API (детали — отдельная тема) |
| **DNS** | Имя → IP (и другие записи) |
| **SMTP / IMAP** | Почта |
| **FTP / SSH** | Файлы / удалённый шелл |

В коде это `fetch`, HTTP-клиент, `dns.lookup`, SMTP-библиотека — не «сырой» IP-сокет с ручной сборкой датаграммы.

Прикладной уровень **не** маршрутизирует пакеты по интернету: он опирается на то, что ниже уже есть способ доставить байты на нужный хост и порт.

## Межсетевой уровень

**Internet Protocol (IP)** даёт:

- **Логические адреса** узлов (IPv4 / IPv6);
- **Датаграмму** (пакет) с заголовком: источник, назначение, TTL/hop limit, протокол вышележащего уровня;
- **Маршрутизацию** между сетями: каждый роутер смотрит таблицу маршрутов и выбирает next hop.

Пакет может пройти несколько сетей; на каждом хопе TTL уменьшается. Если путь оборвался, часто приходит **ICMP** (например destination unreachable) — служебный протокол того же «этажа», не HTTP-ошибка.

Практические сигналы «это IP-уровень»:

- `ENETUNREACH`, `EHOSTUNREACH`;
- traceroute / TTL exceeded;
- «пинг не идёт», хотя DNS уже ответил.

Имя хоста здесь уже должно быть превращено в IP (DNS или hosts) — иначе межсетевому уровню нечего маршрутизировать по имени.

## Связка: DNS и HTTP «сверху», IP «посередине»

Типичный `fetch('https://api.example.com/v1')`:

```text
1. DNS (прикладной)     api.example.com → 203.0.113.10
2. TCP + TLS (транспорт)   соединение к 203.0.113.10:443
3. HTTP (прикладной)    GET /v1 …
4. IP (межсетевой)      каждый сегмент пути — датаграмма src→dst
```

Шаги 1 и 3 — прикладной уровень; шаг 4 — межсетевой на всём пути. Шаг 2 — транспорт (следующая тема пары). Тема «IP и hostname» разбирает адреса и имена подробнее; здесь важен **разрез модели**: кто за что отвечает.

## Инкапсуляция (фрагмент)

Упрощённо при отправке HTTP по TCP:

```text
┌─────────────────────────────┐
│ HTTP: GET /v1 …             │  прикладной
├─────────────────────────────┤
│ TCP: ports, seq…            │  транспорт
├─────────────────────────────┤
│ IP: src, dst, TTL…          │  межсетевой
├─────────────────────────────┤
│ Ethernet / Wi‑Fi frame      │  канал
└─────────────────────────────┘
```

Средний ящик (TCP) и нижний (кадр) — граница с соседней темой. На стенде лабы транспорт и канал приглушены: фокус на «смысл сверху» и «IP-путь».

## Ловушки

- Считать, что роутер «читает» JSON API — обычно нет, только IP (и фильтрация по портам/политикам).
- Путать `404` (прикладной HTTP) с «хост недоступен» (IP/ICMP/маршрут).
- Ждать, что знание HTTP заменит понимание адресации и маршрутизации — и наоборот.
- Класть TCP и Ethernet в «прикладной» или «межсетевой» — у них свои уровни модели.
