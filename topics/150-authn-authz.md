# 1. Тема

**Аутентификация и авторизация пользователя**

---

# 2. Главное в одну фразу

Аутентификация отвечает «кто ты», авторизация — «что тебе можно»; путать их нельзя: вход в систему не равен правам на действие.

---

# 3. Суть

> **Аутентификация (authentication, AuthN)** — проверка личности: пароль, код из SMS, Passkey/WebAuthn, OAuth-логин через провайдера. Успех даёт доказательство сессии — cookie, JWT, server-side session id. **Авторизация (authorization, AuthZ)** — решение, разрешено ли уже известному субъекту действие: читать заказ, править чужой профиль, вызвать админский API.
>
> Зачем разделять: фронт может красиво спрятать кнопку «Удалить», но реальная защита — на сервере. Без AuthN любой запрос анонимен; с AuthN без AuthZ авторизованный пользователь может вызвать чужой `DELETE /users/42`, если API смотрит только на «есть ли токен», а не на роль и владельца ресурса.
>
> Как обычно устроено во вебе. Клиент проходит login → сервер создаёт сессию или выдаёт токен → последующие запросы несут cookie/`Authorization` → middleware проверяет «сессия валидна» (AuthN), затем политики ролей, ACL или «ресурс принадлежит userId» (AuthZ). На клиенте те же факты используют для UX (роуты, меню), но не как единственный барьер.
>
> Ловушка: «мы проверяем JWT на каждый запрос» — это часто только AuthN (подпись и срок). Отдельный шаг — claims/роли и проверка объекта. Другая путаница: OAuth «войти через Google» — про делегированную аутентификацию (и иногда scopes); это не автоматически полная модель прав внутри вашего продукта.

---

# 4. Самое главное запомнить

| | Аутентификация (AuthN) | Авторизация (AuthZ) |
|--|------------------------|---------------------|
| Вопрос | Кто ты? | Можно ли это сделать? |
| Примеры | пароль, MFA, WebAuthn, OAuth login | роли, permissions, ACL, владелец ресурса |
| Типичный сбой | слабый пароль, утечка сессии | IDOR: доступ к чужому id |

- Сначала AuthN, потом AuthZ.
- UI-скрытие ≠ безопасность; проверка на API обязательна.
- Сессия/токен доказывают личность (или делегированный вход), не любой доступ.
- 401 обычно «не аутентифицирован», 403 — «аутентифицирован, но нельзя».

# 5. Описание

## Короткая схема

```text
Запрос
  → есть валидная сессия/токен?  ──нет──► 401 Unauthorized (AuthN)
  → да: субъект известен
  → есть право на действие/ресурс? ──нет──► 403 Forbidden (AuthZ)
  → да → выполнить
```

(Коды в реальных API иногда смешивают; смысл уровней всё равно разный.)

## Примеры в продукте

```text
AuthN: email+password → Set-Cookie: session=…
AuthN: Authorization: Bearer <jwt>

AuthZ: role === 'admin' → доступ в /admin
AuthZ: order.userId === currentUser.id → просмотр заказа
AuthZ: permission 'orders:write' → создание заказа
```

## Фронтенд vs бэкенд

| Слой | Роль |
|------|------|
| UI (скрыть пункт меню) | Удобство, меньше ошибок пользователя |
| Protected route на клиенте | UX-навигация, не защита данных |
| API / BFF | Обязательная AuthN + AuthZ |

## Связанные темы в группе

- **JWT** — как устроен токен и типовые ошибки хранения.
- **CORS / cookies** — как браузер передаёт учётные данные между origin.
- **CSRF** — риск для cookie-сессий при действиях «от имени» пользователя.

## Частые ошибки

- Доверять `userId` из тела запроса без сверки с сессией.
- Путать scopes OAuth с внутренней RBAC.
- Считать «токен есть» достаточным для админских операций.
- Хранить долгоживущий access-токен в `localStorage` без понимания XSS-риска.
