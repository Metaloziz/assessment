# 1. Тема

**TCP/IP: транспортный и канальный уровни**

---

# 2. Главное в одну фразу

Транспортный уровень доставляет байты между процессами на хостах (порты, TCP или UDP), канальный — кадр между соседними узлами в одном сегменте сети (MAC, Ethernet/Wi‑Fi); вместе они отвечают на «кому на хосте» и «как по проводу до соседа», не подменяя IP и прикладной смысл.

---

# 3. Суть

> В модели **TCP/IP** четыре уровня. Эта тема — про два нижних относительно приложения: **транспортный** (transport) и **канальный** (link / network access). Транспорт — порты и способ доставки на хост: надёжный поток (**TCP**) или лёгкая датаграмма (**UDP**). Канальный — кадр для передачи по локальному носителю: адреса **MAC**, Ethernet или Wi‑Fi, проверка целостности кадра.
>
> На практике это снова две плоскости. Сокет в коде видит `host:port` и поток/датаграмму. Коммутатор и NIC видят кадр с MAC источника и назначения. IP между ними решает, *куда* между сетями; транспорт и канал — *к какому процессу* и *как до следующего hop на L2*.
>
> Как стыкуется поток. Приложение отдаёт сообщение; транспорт нарезает сегменты/датаграммы с портами. IP упаковывает в пакет. На каждом участке пути пакет кладут в **кадр** канала с MAC соседа (часто после ARP). На приёме кадр → IP → транспорт → сокет приложения.
>
> Ловушка: путать «порт закрыт» с «хост недоступен» и «кадр не дошёл». `ECONNREFUSED` — транспорт/процесс; `ENETUNREACH` — IP; FCS/ошибка на L2 — локальный сегмент. Прикладной HTTP и маршрутизация IP — соседняя тема пары; здесь важны порты, TCP vs UDP и кадр канала.

---

# 4. Самое главное запомнить

- Транспортный уровень: **порты** + **TCP** (соединение, надёжность, порядок) или **UDP** (датаграмма без handshake).
- Канальный уровень: **кадр** (Ethernet/Wi‑Fi…), адреса **MAC**, доставка *в пределах сегмента* / до next hop.
- TCP: handshake (SYN → SYN-ACK → ACK), seq/ack, поток байт; UDP: «отправил и забыл» на уровне протокола.
- Порт — адрес *процесса* на хосте; IP — адрес *хоста* в сети; MAC — адрес *интерфейса* в локальном сегменте.
- Инкапсуляция: сегмент/датаграмма → IP-пакет → кадр канала.
- Коммутатор обычно смотрит MAC, не HTTP и не «читает» JSON.
- Не смешивать с прикладным и межсетевым: DNS/HTTP и маршрутизация IP — соседняя тема.

| Уровень TCP/IP | Вопрос | Примеры |
|----------------|--------|---------|
| Транспортный | Какому процессу и с какой доставкой? | TCP, UDP, порты |
| Канальный | Как до соседа по носителю? | Ethernet, Wi‑Fi, MAC, FCS |

# 5. Описание

```text
Приложение / IP          ← не эта тема (см. «межсетевой и прикладной»)
   │
   ▼
TCP / UDP + порты        ← транспортный уровень
   │
   ▼
IP-пакет                 ← стык с межсетевым
   │
   ▼
Ethernet / Wi‑Fi frame   ← канальный уровень
   │  MAC src → MAC dst
   ▼
Физ. носитель
```

## Транспортный уровень

Здесь живут протоколы **между процессами** на двух хостах (после того как IP уже знает адреса машин).

| | **TCP** | **UDP** |
|---|---------|---------|
| Модель | поток байт, соединение | датаграмма |
| Handshake | да (трёхсторонний) | нет |
| Надёжность / порядок | да (retransmission, seq) | нет на уровне протокола |
| Типично | HTTP(S), SSH, БД | DNS (часто), медиа, QUIC поверх UDP |

В коде: `net.connect` / TLS к `host:443`, или `dgram.send` на порт. Номер порта в заголовке говорит ОС, какому сокету отдать данные.

**TCP** перед обменом данными поднимает соединение: клиент шлёт SYN, сервер отвечает SYN-ACK, клиент — ACK. Дальше сегменты с sequence numbers; потеря — повтор. **UDP** кладёт данные в датаграмму с портами и длиной — без состояния «сессии» в самом протоколе.

Транспорт **не** выбирает маршрут между сетями и **не** задаёт смысл HTTP: он обслуживает доставку на порт.

## Канальный уровень

**Link layer** (в TCP/IP часто «network access») отвечает за передачу кадра **соседу** в одной локальной сети или до следующего L3-hop:

- адреса **MAC** интерфейсов;
- тип кадра (EtherType: IPv4, IPv6, ARP…);
- контроль целостности (например FCS у Ethernet);
- доступ к среде (у Wi‑Fi — своя MAC-подсистема).

IP-пакет на выходе хоста упаковывается в кадр: MAC назначения — либо целевой хост в той же подсети, либо шлюз (MAC шлюза узнают через **ARP** / NDP). Коммутатор пересылает по таблице MAC; роутер на границе сетей снимает кадр, смотрит IP и снова кадрирует на следующий сегмент.

Практические сигналы «это канал / L2»:

- нет линка (cable unplugged, Wi‑Fi dissociated);
- ошибки FCS / discarded frames на интерфейсе;
- ARP не резолвит MAC шлюза — пакет «выше» не уйдёт в кадр.

## Связка: сокет сверху, кадр снизу

Типичный HTTPS к API в той же или чужой сети:

```text
1. TCP :443          handshake, затем поток TLS/HTTP
2. IP                src → dst (межсетевой — др. тема)
3. Кадр Ethernet     MAC → next hop / peer в сегменте
4. На каждом роутере новый кадр на следующем L2-сегменте
```

Шаг 1 — транспорт; шаг 3 — канал. IP (шаг 2) стыкует конец в конец между сетями; канал — только «один прыжок по проводу/радио».

## Инкапсуляция (фрагмент)

```text
┌─────────────────────────────┐
│ HTTP / DNS …                │  прикладной (др. тема)
├─────────────────────────────┤
│ TCP/UDP: ports, seq…        │  транспорт
├─────────────────────────────┤
│ IP: src, dst, TTL…          │  межсетевой (др. тема)
├─────────────────────────────┤
│ Ethernet: MAC, EtherType…   │  канал
└─────────────────────────────┘
```

На стенде лабы прикладной и IP приглушены: фокус на портах/TCP·UDP и на кадре.

## Ловушки

- Считать, что «порт 443» — это IP-адрес или MAC.
- Ждать от UDP той же надёжности, что у TCP, «потому что DNS иногда на UDP».
- Путать отказ соединения (транспорт) с unreachable (IP) и с обрывом линка (канал).
- Думать, что коммутатор разбирает HTTP — обычно только MAC (и VLAN).
