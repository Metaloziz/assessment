# 1. Тема

**Понятие кластера серверов, зачем нужны системы управления кластерами**

---

# 2. Главное в одну фразу

Кластер объединяет несколько серверов в общий ресурс, а менеджер кластера автоматически держит нужное число копий приложения, разносит их по узлам и поднимает замену после сбоя.

---

# 3. Суть

> Представьте платёжный API на одной машине: пока она жива — всё работает, но любой сбой останавливает оплаты для всех. **Кластер** — это несколько связанных серверов (**узлов**), на которых приложение работает не как на одном компьютере, а как на общей площадке: можно запустить несколько **реплик** и разнести их по разным машинам.
>
> Сами по себе лишние серверы отказоустойчивость не дают. Нужен **менеджер кластера** — программа вроде Kubernetes, Marathon или Docker Swarm, которая знает **желаемое состояние** (сколько реплик, какой образ, какие лимиты) и постоянно сверяет его с фактом: размещает копии, направляет трафик только на здоровые экземпляры, масштабирует при нагрузке и после падения узла создаёт замену на живой машине.
>
> Ловушка: «три реплики» на одном узле — это не резерв. Убили единственный сервер — все три копии исчезают вместе с ним. Отказоустойчивость появляется, когда реплики разнесены, есть проверки готовности и менеджер умеет **self-healing** — сам восстанавливать расхождение между желаемым и фактическим состоянием.

---

# 4. Самое главное запомнить

- Кластер — несколько узлов, которые для приложения выглядят как один общий ресурс.
- Главные цели: масштабирование под нагрузку, высокая доступность и более равномерная загрузка CPU/RAM/диска.
- Горизонтальное масштабирование — добавить реплики или узлы; вертикальное — увеличить мощность одной машины.
- Менеджер кластера сравнивает желаемое состояние с тем, что реально запущено, и устраняет расхождения.
- Важные функции: размещение реплик, балансировка и discovery, проверки здоровья, self-healing, rolling update и откат.
- Кластер не заменяет архитектуру: приложению по-прежнему нужны stateless-подход, внешнее хранение данных и отказоустойчивые зависимости.

# 5. Описание

## Как устроен кластер

```text
желаемое состояние (replicas, образ, лимиты)
        ↓
менеджер кластера (scheduler + контроллеры)
        ↓
узлы node-1 … node-N  →  реплики приложения
        ↓
балансировщик / service discovery  →  только здоровые экземпляры
```

Один сервер имеет предел по мощности и является единой точкой отказа. В кластере экземпляры API можно разнести по нескольким узлам и зонам доступности. При пике — например, во время массовых платежей — система запускает дополнительные реплики. При падении одной машины трафик направляется на оставшиеся здоровые экземпляры, а менеджер создаёт замену.

На вкладке «Решение проблемы» в лабе — симулятор: один сервер против кластера с менеджером, размещение реплик и self-healing после «убить узел».

Геораспределённые кластеры могут уменьшать задержку для пользователей, но усложняют согласованность данных, маршрутизацию и требования к данным. Поэтому «несколько регионов» не является автоматическим улучшением: это архитектурное решение с ценой.

## Что автоматизирует менеджер

| Возможность | Практический эффект |
|---|---|
| Размещение задач | Подбирает узел с достаточными ресурсами и правилами размещения |
| Балансировка и discovery | Направляет трафик к доступным экземплярам |
| Масштабирование | Увеличивает или уменьшает число реплик |
| Health checks и self-healing | Убирает из трафика и перезапускает нездоровые экземпляры |
| Rolling update / rollback | Обновляет версию без полной остановки и возвращает предыдущую |
| Оркестрация ресурсов | Ограничивает CPU/RAM, избегает переполнения узлов |
| Изоляция и политики | Разделяет доступы, сети и namespaces/проекты |

Например, в Kubernetes для сервиса платежей описывают `Deployment` с несколькими репликами, `Service` для сетевого доступа, `readiness`/`liveness` probes и лимиты ресурсов. Контроллер поддерживает нужное число здоровых pod, а scheduler размещает их на worker-узлах.

## Краткое сравнение

| Система | Сильные стороны | Когда встречается в банке |
|---|---|---|
| Kubernetes | Самая распространённая экосистема, декларативные API, развитые сеть и безопасность | Новые cloud-native микросервисы, managed Kubernetes |
| Mesos/Marathon | Гибридные нагрузки, Mesos как общий слой ресурсов | Legacy-платформы, сочетание контейнеров, VM и batch-задач |
| Docker Swarm | Простая модель и близкая интеграция с Docker | Небольшие контуры и тестовые среды; реже для новых production-систем |

Выбор зависит не только от функций. Проверяют зрелость команды, доступность managed-сервиса, инструменты мониторинга, требования к изоляции и существующую платформу. Для критичного банковского сервиса важны несколько зон/узлов, резерв ресурсов, контролируемые релизы и регулярно проверяемое восстановление.

## Типичные ошибки

- Считать «три реплики» отказоустойчивостью, но размещать их на одном узле.
- Не задавать requests/limits и получать конкуренцию сервисов за память или CPU.
- Использовать liveness probe как readiness probe и отправлять трафик ещё не готовому сервису.
- Хранить сессию или файлы на локальном диске контейнера без внешнего хранилища.
- Не проверять rollback и аварийные сценарии до инцидента.
