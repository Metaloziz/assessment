# 1. Тема

**Распространённые алгоритмические ошибки: вложенные циклы и лишние проходы (`.map` / `.reduce` и др.)**

---

# 2. Главное в одну фразу

Чаще всего «тормозит» не язык, а лишняя работа: вложенные циклы дают квадратичный рост, а цепочки `.map` / `.filter` / `.reduce` — несколько полных проходов там, где хватило бы одного.

---

# 3. Суть

> Типичная алгоритмическая ошибка во фронтенде и бэкенде — сделать больше работы, чем нужно. Вложенный цикл `для каждого A перебрать все B` на данных размера n даёт порядка n² шагов: на тысяче элементов уже миллион операций, на десяти тысячах — сто миллионов.
>
> Вторая классика — чрезмерное использование цепочек массивов: `.map(...).filter(...).map(...)` читается красиво, но каждый метод идёт по всему массиву заново. Три прохода по миллиону элементов — три миллиона итераций плюс промежуточные массивы в памяти.
>
> Исправляют не «отказом от `.map`», а сокращением работы: один проход, ранний выход, индекс/`Set`/`Map` вместо повторного поиска, разбиение данных. Сначала измерить узкое место, потом упрощать алгоритм.

---

# 4. Самое главное запомнить

- **Вложенные циклы** по двум спискам длины n → часто **O(n²)**.
- Цепочка `.map` / `.filter` / `.reduce` = **несколько полных проходов** + промежуточные массивы.
- «Выглядит функционально» ≠ «дёшево на больших n».
- Ищите работу, которую можно сделать **один раз** или заменить lookup на `Set`/`Map`.
- Ранний `break` / `return` и выход при нахождении — тоже алгоритм.
- Оптимизируйте после понимания объёма данных, не «на глаз» на десяти элементах.

---

# 5. Описание

## Вложенные циклы

```javascript
// Плохо: для каждого пользователя ищем заказ перебором — O(U * O)
for (const user of users) {
  for (const order of orders) {
    if (order.userId === user.id) { /* ... */ }
  }
}
```

```javascript
// Лучше: индекс заказов по userId — один проход + дешёвый доступ
const ordersByUser = new Map();
for (const order of orders) {
  const list = ordersByUser.get(order.userId) ?? [];
  list.push(order);
  ordersByUser.set(order.userId, list);
}
for (const user of users) {
  const userOrders = ordersByUser.get(user.id) ?? [];
  // ...
}
```

Когда вложенность оправдана: маленький внутренний набор (фиксированные 3–5 вариантов), матричные задачи, где n² — сама постановка. Когда нет — почти всегда, если оба набора растут с продуктом.

## Лишние проходы по массиву

```javascript
// Три прохода + два промежуточных массива
const result = items
  .map((x) => normalize(x))
  .filter((x) => x.active)
  .map((x) => toDto(x));
```

```javascript
// Один проход
const result = [];
for (const item of items) {
  const x = normalize(item);
  if (!x.active) continue;
  result.push(toDto(x));
}
```

`.reduce` сам по себе не враг: один `reduce` может заменить цепочку. Вред — когда каждый шаг снова сканирует весь массив или внутри `reduce` прячется ещё один цикл/`find` по большому списку.

```javascript
// Скрытый O(n²): на каждый элемент — find по всему массиву
ids.map((id) => items.find((x) => x.id === id));
```

```javascript
const byId = new Map(items.map((x) => [x.id, x]));
ids.map((id) => byId.get(id));
```

## Чеклист перед merge

1. Есть ли цикл внутри цикла / `.map` внутри `.map` по большим коллекциям?
2. Сколько раз код проходит один и тот же массив?
3. Не делает ли каждый шаг `find` / `includes` / `filter` по полному списку?
4. Можно ли построить `Map`/`Set` один раз?
5. Какой реальный n в проде (10, 10³, 10⁶)?

## Типичные вопросы на собеседовании

- Почему вложенные циклы опасны? — Произведение размеров входов; рост быстрее линейного.
- Чем плоха длинная цепочка `.map`/`.filter`? — Несколько проходов и лишние аллокации.
- Когда оставлять цепочку? — Маленький n, ясность важнее микрооптимизации, нет промежуточной боли по памяти.
- Как ускорить поиск по id? — Индекс: объект, `Map`, нормализованный store.
