# 1. Тема

**Принцип API first**

---

# 2. Главное в одну фразу

API first — сначала зафиксировать сетевой контракт (ресурсы, схемы, ошибки), а уже потом писать UI и реализацию сервера под этот договор.

---

# 3. Суть

> **API first** — подход к разработке, при котором **контракт HTTP-API** (пути, методы, тела запросов/ответов, коды ошибок, версия) описывают и согласуют **раньше**, чем рисуют экраны и пишут бизнес-логику сервера. Контракт — источник истины: клиенты и бэкенд сходятся к одному документу, а не к «тому, что получилось в коде».
>
> Так несколько потребителей (web, mobile, партнёры, другой сервис) могут идти параллельно: фронт мокает ответы по схеме, бэкенд реализует те же пути, тесты проверяют соответствие. Меньше сюрпризов на стыке «кнопка уже есть, а поля в JSON другие».
>
> На практике контракт живёт в `OpenAPI` (или аналоге), ревьюят как код, при необходимости генерируют типы/SDK и гоняют **contract tests**. Изменения — через версию или явное расширение схемы, а не тихий rename поля в одном клиенте.
>
> Ловушка: назвать процесс API first, а по факту сначала собрать UI и «добавить эндпоинты под вёрстку» без схемы — контракт тогда только задним числом. Другая крайность — гигантская спека на год вперёд без реализации: API first ≠ waterfall. Соседние темы группы закрывают REST-ресурсы и сам HTTP; здесь важен порядок «договор → реализация».

---

# 4. Самое главное запомнить

- Сначала контракт (что можно вызвать и в каком виде), потом UI и серверный код под него.
- Контракт — общий артефакт: пути, методы, схемы JSON, статусы, версия.
- Клиенты и сервер сверяются с документом; расхождение схемы и ответа — баг контракта или реализации.
- `OpenAPI` (и подобные) удобны как формат договора, ревью и генерации типов/моков.
- API first не отменяет итерации: менять контракт можно, но осознанно (версия / совместимость), не «тихо в проде».
- Не путать с «сначала нарисовать все экраны» (UI first) и с «сначала написать код хендлеров без схемы» (code first).

---

# 5. Описание

```text
  [1] контракт API          [2] параллельная работа
  openapi.yaml / схема  ──►  web (мок по схеме)
       │                     mobile / другой сервис
       │                     backend (реализация путей)
       ▼
  [3] проверка              [4] релиз
  contract tests            одна версия договора
  типы / SDK из схемы       клиенты не «угадывают» поля
```

## Чем не является

| Подход | Порядок | Риск |
| --- | --- | --- |
| **API first** | контракт → клиенты и сервер | нужна дисциплина ревью схемы |
| **UI first** | экраны → «какие эндпоинты нужны» | API подстраивается под вёрстку, ломается при втором клиенте |
| **Code first** | хендлеры → спека из кода (если вообще) | документ отстаёт; клиенты копируют фактический JSON |

API first не запрещает прототипы UI: прототип опирается на **черновик контракта**, а не наоборот — «какие поля оказались в форме».

## Что входит в контракт

Минимум, без которого «договор» пустой:

- ресурсы и пути (`/orders`, `/orders/{id}`);
- методы и смысл (`GET` список, `POST` создание…);
- схемы тела и query (типы, обязательность);
- коды ответа и форма ошибки (`400` validation, `404`, `409`);
- версия или политика совместимости (`/v1/…`, заголовок, deprecation).

Пример фрагмента идеи (не полный OpenAPI):

```yaml
paths:
  /orders:
    post:
      requestBody:
        required: true
        content:
          application/json:
            schema:
              type: object
              required: [items]
              properties:
                items:
                  type: array
                  minItems: 1
      responses:
        "201":
          description: Created
        "400":
          description: Body не по схеме
```

Пока схемы нет, «API» — набор случайных JSON из разных PR.

## Как работать день за днём

1. Набросать и отревьюить контракт (как код).
2. Поднять мок / stub по схеме для клиентов.
3. Реализовать сервер так, чтобы ответы **проходили** проверку схемы.
4. В CI — contract tests: запрос/ответ против документа.
5. Ломающее изменение — новая версия или явный breaking change, а не тихий rename `userId` → `user_id` в одном сервисе.

Генерация клиентов и типов из OpenAPI ускоряет шаги 2–4, но ценность — в **согласованности**, не в «сгенерировали ради галочки».

## Ловушки

- Спека есть в репозитории, а прод отвечает иначе — контракт мёртв без проверок.
- Один «толстый» `POST /api` с полем `action` — контракт не спасает от RPC-каши (см. тему про REST).
- Сверхдетальная схема на год вперёд без поставки — снова waterfall; API first итеративен, но с явной точкой согласования.
