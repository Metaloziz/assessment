# 1. Тема

**MVC · MVVM**

---

# 2. Главное в одну фразу

MVC и MVVM помогают не сваливать кнопки, данные и сценарий «Сохранить» в один обработчик — иначе экран быстро становится непереносимым и трудно проверяемым.

---

# 3. Суть

> Представьте форму профиля: поле «Имя», кнопка «Сохранить», строка «Привет, …». Самый простой путь — написать всё в одном обработчике: прочитать поле, обрезать пробелы, записать в переменную, обновить приветствие, может ещё отправить на сервер. Так работает, пока экран один. Как только появляется второй экран с тем же именем или вы хотите проверить «обрезаются ли пробелы» без браузера — логика уже прилипла к кнопке и DOM.
>
> **MVC** и **MVVM** — два способа **разрезать** этот комок. **View** (`View`) — то, что видит человек: поля и кнопки. **Model** (`Model`) — данные и правила: как хранится имя, что считается пустым. Посередине — кто принимает клик: в MVC это **Controller** (`Controller`), в MVVM — **ViewModel** (`ViewModel`). Экран сам в данные не лезет; он либо отдаёт клик посередине, либо «смотрит» на свойства ViewModel.
>
> После «Сохранить» графы расходятся. В **MVC** экран говорит контроллеру «нажали», контроллер пишет в модель, экран **подписан** на модель и сам перерисовывается. В **MVVM** экран **приклеен** к свойству `name` и команде `save` у ViewModel: поле и приветствие подтягивают имя оттуда, модель трогает только VM.
>
> Ловушка: папка `controllers/` на сервере — про HTTP, не про этот UI-граф. И `useState` в React — ещё не MVVM, пока нет отдельного контракта «свойство + команда», а не «всё в компоненте».

---

# 4. Самое главное запомнить

- Без нарезки сценарий живёт в обработчике кнопки — его нельзя вынести в тест или другой экран без копипасты.
- MVC: `Controller` пишет в `Model`; экран подписан на модель и может её знать, но сам не пишет.
- MVVM: экран приклеен к свойствам и командам `ViewModel`; `Model` трогает только VM.
- Два экрана с одним именем без общей модели легко расходятся: на одном «Анна», на другом пусто.
- Имя папки в проекте не задаёт паттерн — смотрите, кто после клика пишет в данные.
- Binding — не «есть state»: нужен контракт, на который подписан вид.
- Толстый ViewModel, который сам ходит в API и хранит все правила, — уже вторая модель, не «состояние экрана».

# 5. Описание

```text
клик «Сохранить» на поле имени

MVC:   Экран ──событие──► Контроллер ──пишет──► Данные
       Экран ◄──подписка / рисует себя──────── Данные

MVVM:  Экран ◄──приклеен name / save──► ViewModel ──пишет──► Данные
       Экран не зовёт Данные напрямую
```

## Базовое понимание

На экране три роли, даже если в коде они пока не названы так:

| Роль | Простыми словами | Пример в форме профиля |
| --- | --- | --- |
| **View** | что видит пользователь | поле, кнопка, «Привет, …» |
| **Model** | данные и правила | имя в памяти, «пустое нельзя», `trim` |
| **Controller / ViewModel** | кто принимает жест | «Сохранить» → записать имя правильно |

**MVC** и **MVVM** отвечают на один вопрос: *после клика кто имеет право менять данные и как экран узнаёт новое значение?* Не «как названы папки в репозитории».

Мини-приложение «Профиль» в лабе показывает тот же сценарий: введите имя, нажмите «Сохранить», посмотрите, кто записал данные и откуда взялось приветствие.

## Что ломается без нарезки

Если всё живёт в одном обработчике кнопки — без Controller, ViewModel и отдельной Model — типичные проблемы такие:

**Сценарий не переносится.** Завтра то же «Сохранить» нужно в мобильном приложении или в другом компоненте. Придётся копировать обработчик целиком: чтение поля, `trim`, запись, обновление текста, возможно `fetch`. Забыли один шаг — баг только на новом экране.

**Логику нельзя проверить отдельно.** «После сохранения пробелы обрезаются?» — без нарезки тест должен поднимать DOM, кликать кнопку и читать разметку. С моделью и контроллером достаточно вызвать `save('  Анна  ')` и проверить `model.getName()`.

**Два экрана расходятся.** Шапка показывает «Привет, Анна», а в настройках имя пустое — потому что каждый виджет хранит своё локальное состояние. Общая **Model** или свойство **ViewModel** держат одно имя для всех мест.

**Правку ищут по всему файлу.** Изменили правило «имя не короче двух символов» — ищете все `onclick`, все формы, все места, где имя пишется в API. Правило должно жить в **Model** (или в одном слое посередине), а не в десяти кнопках.

**Экран знает слишком много.** Компонент и рисует, и ходит в `fetch`, и решает, что показать при ошибке сети. Смена дизайна тащит риск сломать запись данных — всё в одном файле на триста строк.

**Ложное «у нас уже MVVM».** В React положили имя в `useState` и в `onClick` сразу зовут API — это по сути тот же монолитный обработчик, только с хуком. Паттерн появляется, когда есть контракт: «поле смотрит на `vm.name`, кнопка зовёт `vm.save`», а не «компонент сам всё делает».

Нарезка не нужна на калькуляторе из одной кнопки. Она окупается, когда экранов несколько, сценарий повторяется или его хотят тестировать без браузера.

## MVC

**Идея:** экран отдаёт событие, **Controller** меняет **Model**, экран **подписан** на модель и сам обновляется.

```js
// ← MVC: экран подписан на Model, пишет Controller
function createController(model) {
  return {
    save(raw) {
      model.setName(raw.trim()); // ← Controller
    },
  };
}

view.on('submit', (raw) => controller.save(raw));
model.subscribe(() => view.render(model.getName()));
```

Экран **может знать** модель (читает `getName` по подписке), но **не должен** сам вызывать `model.setName()` — иначе контроллер обойден, это «толстый вид».

**Если MVC не соблюдать:** кнопка сама пишет в данные; приветствие обновляют вручную в том же обработчике; второй экран не узнаёт об изменении, пока не продублируете код. В лабе кейс «Экран сам пишет» показывает именно это.

**Не путать с сервером:** в Rails или Express папка `controllers/` закрывает HTTP-запрос. Это другой граф — там нет подписки экрана на модель в браузере.

## MVVM

**Идея:** не после каждого изменения вручную звать «обнови поле» и «обнови приветствие». Объявляем: поле **приклеено** к свойству `name`, кнопка зовёт команду `save`. **ViewModel** держит эти свойства и команды; **Model** — доменные данные.

```js
// ← MVVM: bind к свойству и команде, не к Model
function createViewModel(model) {
  const name = observable(model.getName());
  return {
    name, // ← bind
    save(raw) {
      model.setName(raw.trim());
      name.set(model.getName()); // ← VM, не View
    },
  };
}

bind(input, vm.name);
form.onsubmit = () => vm.save(input.value);
```

Экран **не зовёт** `Model` напрямую. Binding в браузере — это подписка: когда `name` меняется, поле и приветствие сами подтягивают значение.

**Если MVVM не соблюдать:** виджет в `onClick` сам пишет в модель и сам крутит локальный state — ViewModel пустой, binding не участвует. В лабе кейс «Экран сам пишет» для MVVM показывает обход VM.

**Ловушки MVVM:** двусторонний bind без команды может зациклить поле ↔ свойство на каждую клавишу; ViewModel, который сам ходит в API и хранит все бизнес-правила, — уже вторая модель, а не «состояние экрана».

## MVC или MVVM — что выбрать

Оба режут экран на «видно» / «данные» / «посередине». Разница — как экран узнаёт об изменении:

| | MVC | MVVM |
| --- | --- | --- |
| Кто пишет в данные | Controller | ViewModel |
| Как экран обновляется | подписка на Model | bind к свойствам VM |
| Экран знает Model? | может, но не пишет | обычно нет, только VM |

React и Vue часто смешивают: контейнер как контроллер, пропсы как bind. Это нормально — важен **граф после клика**, не ярлык в документации.

## Что не путать

| Слово в быту | Часто имеют в виду | Точнее |
| --- | --- | --- |
| «у нас MVC» | папка `controllers/` | жест → контроллер → модель → экран подписан |
| «это MVVM, есть state» | `useState` в виджете | bind к свойствам и командам VM |
| «Model» в имени класса | любой объект | данные и правила, не декорация имени |

Redux и односторонний поток — соседняя идея: действие → store → экран. Цель та же — экран не пишет в данные в обход слоя — но граф другой.
