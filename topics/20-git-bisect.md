# 1. Тема

**git bisect**

---

# 2. Главное в одну фразу

`git bisect` — бинарный поиск по истории коммитов, чтобы найти коммит, в котором появился баг.

---

# 3. Ответ для собеседования

> «Помечаем текущий как `bad`, старый рабочий как `good`. Git checkout’ит середину; говорим good/bad; сужаем диапазон за ~log₂(N) шагов.
>
> Автоматизация: `git bisect run ./test.sh` (exit 0 = good, 1 = bad, 125 = skip).
> В конце — `git bisect reset`. Нужен воспроизводимый способ проверить баг.»

---

# 4. Самое главное запомнить

- Бинарный поиск первого bad-коммита.
- Нужны границы good/bad.
- ≈ log₂(N) проверок.
- `bisect run` для автопоиска.
- Всегда `bisect reset`.

---

# 5. Описание

```bash
git bisect start
git bisect bad
git bisect good v1.2.0
# проверяем...
git bisect good   # или bad / skip
git bisect run npm test
git bisect reset
```

Бесполезен, если баг от данных/окружения, а не от коммита.

## Пошаговый сценарий

`bisect` применим к регрессии: сегодня ошибка воспроизводится, а на известной
старой ревизии её нет. Git выбирает коммит посередине диапазона; после каждой
пометки половина кандидатов исключается.

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.2.0

# Git переключился на ревизию посередине.
# Проверить приложение или тест:
git bisect good              # ошибка не проявилась
# либо:
git bisect bad               # ошибка есть

git bisect reset             # вернуть исходную ветку
```

На тысяче коммитов обычно достаточно примерно десяти проверок: это сложность
`log₂(N)`, а не линейный просмотр истории. Git в конце назовёт первый плохой
коммит и его автора/сообщение можно сразу изучить через `git show`.

## Автоматический поиск

Если регрессию надёжно проверяет тест, ручные good/bad не нужны:

```bash
git bisect start HEAD v1.2.0
git bisect run npm test
```

Для `bisect run` код возврата `0` означает good, `1–127` (кроме `125`) — bad,
а `125` — «эту ревизию нельзя проверить». Последний код позволяет пропустить
старый коммит, который не собирается из-за устаревших зависимостей:

```bash
#!/bin/sh
npm ci || exit 125
npm test -- --grep "login should work"
```

## Условия и ограничения

Проверка должна быть детерминированной: флапающий тест делает результат
недостоверным. Нужны точные good и bad границы, а также возможность собрать или
осмысленно пропустить промежуточные ревизии. При проблемах среды, данных,
конфигурации сервера или внешнего API bisect не устанавливает причину, потому что
ищет изменение именно в Git-истории.

Полезные вспомогательные команды: `git bisect log` сохраняет шаги, `git bisect
replay <file>` воспроизводит сессию, `git bisect skip` пропускает неподходящий
коммит. Не забывайте `reset`: во время сессии HEAD обычно detached, и продолжать
обычную разработку в этом состоянии не стоит.
