# 1. Тема
**Coverage. Инструменты и принцип работы**
---
# 2. Главное в одну фразу
Coverage-инструмент во время тестов отмечает, какие строки и ветки кода реально выполнились, и показывает это в отчёте — но не проверяет, что тесты правильные.
---
# 3. Ответ для собеседования
> «Coverage отвечает на вопрос: «какой код тесты вообще задели?». В Jest или Vitest включаю `--coverage`, смотрю отчёт: зелёные строки выполнялись, красные — нет. Под капотом два способа: либо в код временно вставляют счётчики (Istanbul), либо движок Node сам запоминает, что исполнял (V8 / c8). Мне как разработчику обычно достаточно `jest --coverage` или `vitest --coverage`. Важно: 100% не цель — можно вызвать функцию без `expect` и получить красивую цифру. Смотрю на непокрытые ветки ошибок и критичную логику, а не гонюсь за процентом.»
---
# 4. Самое главное запомнить
- Coverage = карта «что тесты выполнили», не «что правильно проверили».
- Запуск: `jest --coverage` или `vitest --coverage`.
- Два способа сбора: счётчики в коде (Istanbul) или данные от движка (V8).
- Строки и ветки — разное: одна ветка `if` может остаться красной.
- Цифра 100% сама по себе ничего не доказывает.
---
# 5. Описание

### Простыми словами
Представь, что тесты — это люди, которые ходят по комнатам дома (коду). Coverage — датчик: в каких комнатах кто-то побывал. Он не говорит, правильно ли они там себя вели — только «были / не были».

### Как это работает по шагам

```text
1. Берём код
2. Включаем сбор покрытия
3. Гоняем тесты
4. Смотрим отчёт: какие строки «загорелись»
```

```bash
jest --coverage
# или
vitest run --coverage
```

В отчёте обычно видно:
- **lines / statements** — выполнилась ли строка;
- **branches** — прошли ли оба исхода `if` / `? :`;
- **functions** — вызывалась ли функция.

### Два способа «подсмотреть» выполнение

| Способ | Идея | Где встречается |
|---|---|---|
| Счётчики (Istanbul) | Перед тестом в код вставляют «+1», когда строка сработала | классический Jest |
| Движок (V8 / c8) | Node сам помнит, что исполнял; отдельный tool считает отчёт | Vitest, `coverageProvider: "v8"` |

На практике чаще всего достаточно флага `--coverage` в runner — он сам подключает один из способов.

```javascript
// идея со счётчиками (упрощённо)
function shipping(total) {
  // тут «невидимо» +1 к счётчику строки
  return total >= 1000 ? 0 : 200;
}
```

### Частая ловушка

```javascript
test('плохо', () => {
  shipping(500); // код выполнился → coverage растёт
  // нет expect → поведение не проверено
});

test('хорошо', () => {
  expect(shipping(500)).toBe(200);
});
```

Ещё пример: один вызов `shipping(1000)` может закрыть почти все строки, но не обе ветки условия. Поэтому смотрят не только lines, но и branches.

### Что делать на практике
- Включать coverage локально и в CI.
- Смотреть **красные** места в важной логике, а не средний %.
- Не требовать 100% на весь проект «ради галочки».
- Не выкидывать из отчёта сложный бизнес-код, чтобы цифра выглядела лучше.
