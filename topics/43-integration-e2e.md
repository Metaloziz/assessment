# 1. Тема

**Интеграционные и e2e тесты (cypress / playwright)**

---

# 2. Главное в одну фразу

Интеграционный тест проверяет связку модулей без полного UI в браузере, а e2e гоняет критичный пользовательский путь в реальном браузере через Cypress или Playwright.

---

# 3. Суть

> **Интеграционный** тест поднимает несколько частей системы вместе — сервис + БД, API + очередь — и проверяет, что контракт между ними жив. Браузер и вёрстка обычно не участвуют: быстрее и проще готовить данные. **E2E** идёт от клика пользователя до видимого результата через всё приложение: UI, сеть, бэкенд.
>
> Зачем так делить. Большинство багов стыков ловят интеграцией. E2E оставляют на короткие критичные потоки: вход, оплата, оформление заказа — они дороже, медленнее и чаще «мигают», если сценариев слишком много.
>
> Как устроен e2e-раннер. Cypress и Playwright открывают приложение, находят элементы, печатают, кликают и ждут состояние интерфейса или сети. Cypress — цепочки `cy.visit` / `cy.get` / `should` в одном браузерном контексте. Playwright — `page.goto`, локаторы и явные `expect`, удобен для нескольких браузеров и параллели.
>
> Ловушка: тащить в e2e каждую мелкую проверку или ждать `sleep(5000)` и CSS-классы. Стабильнее роль/label/`data-testid`, независимые данные и ожидание элемента или ответа сети. Unit и компонентные тесты (RTL) e2e не заменяют.

---

# 4. Самое главное запомнить

- Интеграция — несколько реальных частей без полного браузерного UI.
- E2E — путь пользователя в настоящем браузере от действия до результата.
- Cypress и Playwright решают одну задачу; отличаются API, моделью браузера и параллелью.
- E2E — узкий слой критичных сценариев, не замена unit/integration.
- Стабильные селекторы и ожидание состояния; не фиксированный `wait(5000)`.
- Тесты не должны зависеть от порядка запуска и общих «грязных» данных.

---

# 5. Описание

```text
пользователь
    │
    ▼
 браузер / UI  ──────── e2e (Cypress / Playwright)
    │
    ▼
 API / сервисы  ─────── интеграция (+ часто БД, очередь)
    │
    ▼
  БД / внешние системы
```

## Интеграция

Интеграция отвечает на вопрос: «модули вместе ещё работают?». Типичный пример — HTTP-запрос к поднятому приложению и проверка ответа и записи в тестовой БД. Моки оставляют на внешних нестабильных зависимостях (платёжный шлюз, чужой SaaS), а свой код и свою БД по возможности держат настоящими.

```ts
// пример: API + БД без браузера
test('создаёт заказ', async () => {
  const res = await request(app).post('/orders').send({ sku: 'A1' });
  expect(res.status).toBe(201);
  const row = await db.orders.findById(res.body.id);
  expect(row?.status).toBe('created'); // ← стык API и хранилища
});
```

## E2E: Cypress и Playwright

Оба инструмента управляют браузером и проверяют то, что видит пользователь. Разница в основном в API и возможностях окружения, не в идее «пройти сценарий».

| | Cypress | Playwright |
|---|---|---|
| Стиль | цепочки `cy.*`, ретраи встроены | `async/await`, локаторы + `expect` |
| Браузеры | один основной контекст за раз | Chromium, Firefox, WebKit из коробки |
| Сеть | `cy.intercept` | `page.route` |

```js
// Cypress
cy.visit('/login');
cy.get('[data-testid=email]').type('user@example.com');
cy.get('[data-testid=submit]').click();
cy.url().should('include', '/dashboard');
```

```ts
// Playwright
await page.goto('/login');
await page.getByTestId('email').fill('user@example.com');
await page.getByTestId('submit').click();
await expect(page).toHaveURL(/dashboard/);
```

## Что покрывать e2e

Короткий список критичных путей. Остальное — unit, компоненты (RTL), интеграция. Иначе suite становится медленным и хрупким: любая правка вёрстки или флаки сети валит CI.

## Устойчивость

- Селекторы: роль, доступное имя, текст; `data-testid` — когда семантики мало.
- Данные: фикстуры / seed на тест, без зависимости от «предыдущего» сценария.
- Ожидания: элемент, URL, ответ сети — не `wait(5000)`.
- Внешние сервисы на стенде — intercept/route или отдельный test double.

Антипаттерн: e2e на каждую кнопку формы и тесты, которые проходят только если запускать файл целиком сверху вниз.
