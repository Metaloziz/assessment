# 1. Тема

**Virtual DOM**

---

# 2. Главное в одну фразу

Virtual DOM — лёгкое дерево JS-описаний UI: React сравнивает новый снимок со старым и трогает настоящий DOM только там, где описание реально изменилось.

---

# 3. Суть

> **Virtual DOM** — это не «второй браузерный DOM», а дерево обычных JavaScript-объектов (часто называют `React element` / vnode): тип узла, `props`, дети. После `render` React получает новый снимок такого дерева и сопоставляет его с предыдущим.
>
> Настоящий DOM дорог: layout, paint, потери фокуса при лишних пересозданиях. Дешевле сначала решить в JS, *что* изменилось, и затем применить короткий список правок (`patch` / commit), чем каждый раз переписывать разметку целиком через `innerHTML` или ручные `appendChild`.
>
> Цепочка упрощённо: состояние → вызов `render` → новое дерево элементов → сравнение со старым → минимальные операции над реальными узлами. JSX при компиляции как раз превращается в вызовы `createElement` / `jsx`, которые и собирают этот снимок.
>
> Ловушка: сам Virtual DOM не «ускоряет всё автоматически». Лишние рендеры, огромные деревья без мемоизации и наивная пересборка списка без стабильных `key` всё равно бьют по производительности. VDOM — модель описания и диффа; стратегия обновлений (и Fiber) — отдельные слои поверх.

---

# 4. Самое главное запомнить

- Virtual DOM = JS-дерево описаний (`type`, `props`, `children`), не живые `HTMLElement`.
- JSX → `createElement` / `jsx` → снимок элементов, а не сразу DOM.
- Diff решает, *что* поменять; commit применяет правки к реальному DOM.
- Совпадающий снимок → в DOM можно ничего не писать.
- «VDOM всегда быстрее DOM» — миф: цена в лишней работе на JS и в плохих обновлениях.
- Глубокий алгоритм сопоставления и Fiber — темы reconciliation / Fiber; здесь — роль снимка UI.

---

# 5. Описание

```text
state / props
    → render() → Virtual DOM (новый снимок)
    → diff со старым снимком
    → patch / commit → Real DOM
         (только изменённые узлы)
```

## Что лежит в снимке

Узел Virtual DOM — описание, близкое к:

```js
{
  type: 'button', // или функция/класс компонента
  props: { className: 'primary', children: 'Оплатить' },
}
```

Для компонента `type` — функция; React сначала вызовет её и получит дочернее дерево элементов. Браузерный узел появляется только на этапе commit.

## Зачем сравнивать деревья

Без промежуточного снимка типичный «наивный» путь — при любом изменении снести и заново собрать кусок UI. Тогда теряются фокус, выделение текста, внутреннее состояние нативных контролов, и браузер пересчитывает больше, чем нужно.

С VDOM:

1. Строим новый снимок (дешёвые объекты в куче).
2. Сравниваем с предыдущим по типу и `props` (и по `key` в списках).
3. Пишем в Real DOM точечно: текст, атрибут, вставка/удаление узла.

## JSX и `createElement`

```jsx
<button className="ok">{label}</button>
```

после трансформации по смыслу:

```js
createElement('button', { className: 'ok' }, label)
```

Результат вызова — элемент Virtual DOM, а не `document.createElement` в момент `render`.

## Что VDOM не обещает

| Ожидание | Реальность |
| --- | --- |
| «Любой UI через VDOM быстрее ручного DOM» | Diff + render тоже стоят CPU; выигрыш — в меньшем числе дорогих DOM-операций и декларативности |
| «Раз render вызвали — DOM обновится» | Если снимок совпал, commit может ничего не тронуть |
| «VDOM = Fiber» | Fiber — планировщик/структура работы; VDOM — модель описания UI |

Списки: без стабильного `key` React чаще пересоздаёт узлы вместо перемещения — это уже ловушка reconciliation, но цена видна именно на Real DOM.

## Мини-пример контраста

Наивно:

```js
root.innerHTML = `<ul>${items.map((x) => `<li>${x}</li>`).join('')}</ul>`;
```

С снимком: изменился один пункт — обновляем один текстовый узел (или один `li`), остальное дерево Real DOM остаётся на месте.
