# 1. Тема
**Принцип TDD**
---
# 2. Главное в одну фразу
TDD — разработка короткими циклами: сначала падающий тест, затем минимальная реализация, затем безопасный рефакторинг.
---
# 3. Ответ для собеседования
> «В TDD работаю циклом Red–Green–Refactor. Сначала формулирую поведение через минимальный падающий тест — Red. Затем пишу ровно столько production-кода, чтобы он стал зелёным — Green. После этого улучшаю дизайн без изменения поведения, пока тесты страхуют рефакторинг. Подход даёт быстрый feedback и вынуждает делать зависимости явными, но не отменяет integration и e2e-тесты.»
---
# 4. Самое главное запомнить
- Red: тест должен действительно упасть по ожидаемой причине.
- Green: минимальный код для прохождения.
- Refactor: улучшать только на зелёной базе.
- Маленькие циклы дают самый быстрый feedback.
---
# 5. Описание
Три закона TDD в формулировке Роберта Мартина:
1. Не писать production-код до падающего теста.
2. Не писать теста больше, чем нужно для падения.
3. Не писать production-кода больше, чем нужно для прохождения теста.

```javascript
// Red
test('складывает два числа', () => {
  expect(add(2, 3)).toBe(5);
});

// Green
function add(a, b) {
  return a + b;
}

// Refactor: если появится повторение — улучшаем,
// сохраняя все тесты зелёными.
```

| Фаза | Цель | Типичная ошибка |
|---|---|---|
| Red | Описать один новый контракт | Тест сразу зелёный |
| Green | Быстро подтвердить контракт | Сразу проектировать «идеально» |
| Refactor | Убрать дублирование, улучшить имена | Рефакторить при красных тестах |

TDD особенно полезен в логике с множеством граничных случаев. Он не означает, что каждый метод обязан иметь тест: важнее тестировать поведение и риски, а не механически набирать coverage.
