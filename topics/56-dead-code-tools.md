# 1. Тема

**Инструменты для определения «неработающего» кода (ts-prune, statoscope)**

---

# 2. Главное в одну фразу

ts-prune ищет неиспользуемые TypeScript-экспорты в исходниках; Statoscope показывает «мёртвые» и лишние модули уже в webpack-бандле — разные слои одной задачи.

---

# 3. Суть

> **«Неработающий» код** — это не только синтаксически мёртвые ветки, но и экспорты/модули, которые больше никто не импортирует, и код, который попал в бандл, но не нужен пользователю.
>
> **ts-prune** — CLI для TypeScript/TS-проектов: обходит граф модулей и сообщает экспорты, на которые нет ссылок. Помогает чистить публичные API библиотек и «забытые» утилиты в приложении. Не заменяет runtime-покрытие и не видит динамические `import()` / строки с именами модулей без доп. настройки.
>
> **Statoscope** (часто через `@statoscope/webpack-plugin` + UI) анализирует **stats** webpack: размеры чанков, дубликаты пакетов, модули без входящих связей в сборке, сравнение билдов. Это про артефакт сборки, а не про «красивость» исходников.
>
> Практика: исходники → ts-prune / ESLint `unused-imports`; бандл → Statoscope / webpack-bundle-analyzer. Выводы всегда сверяют с entry points, code splitting и условной загрузкой — иначе «unused» оказывается ленивым маршрутом.

---

# 4. Самое главное запомнить

- ts-prune ≈ неиспользуемые **экспорты** в TS-исходниках.
- Statoscope ≈ **бандл**: размер, дубли, модули без потребителей в stats.
- «Unused в репо» ≠ «unused в бандле» и наоборот.
- Динамические импорты и string-based require легко дают ложные срабатывания.
- Чистку лучше подстраховать тестами и проверкой entry / lazy routes.

| Инструмент | Слой | Что показывает |
|---|---|---|
| ts-prune | Source / exports | Экспорты без импортов |
| Statoscope | Webpack stats | Состав и связи модулей в бандле |

---

# 5. Описание

### ts-prune

Типичный запуск в корне проекта:

```bash
npx ts-prune
```

Вывод — список символов вида `file.ts:12 - exportName`. Дальше вручную решают: удалить, сделать внутренним (`export` → без экспорта), или оставить как публичный API пакета (тогда «unused» внутри монорепы может быть нормален).

Ограничения:

- плохо видит использование через динамические пути и reflection;
- не анализирует CSS/ассеты;
- для library mode «неиспользуемый export» часто = часть внешнего контракта.

Альтернативы рядом по смыслу: `knip`, `ts-unused-exports`, ESLint-правила на неиспользуемые импорты/переменные — они закрывают смежные, но не всегда те же кейсы.

### Statoscope

Подключается к webpack (и экосистеме на stats JSON). В UI смотрят:

- дерево модулей и чанков;
- **unused** / модули без входящих рёбер относительно выбранной точки входа;
- дубликаты одной библиотеки разных версий;
- diff двух отчётов (до/после оптимизации).

Это ответ на вопросы «почему бандл вырос?» и «какой модуль тащит зависимость?», а не «какая функция в `utils.ts` никому не нужна».

### Как сочетать

1. Найти забытые экспорты в коде (ts-prune / knip).
2. Собрать production-бандл и открыть Statoscope.
3. Убедиться, что удалённое из исходников пропало из stats; если модуль «unused» в бандле при живом импорте — смотреть tree-shaking, sideEffects, неправильный entry.

«Неработающий» код в смысле мёртвых веток выполнения (unreachable) этими инструментами не покрывается — там уже покрытие тестами, type narrowing и статический анализ потока.
