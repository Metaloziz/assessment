# 1. Тема

**Функциональное программирование vs ООП в JS**

---

# 2. Главное в одну фразу

В JavaScript ООП держит данные и методы на объекте, а функциональный стиль — в чистых функциях над значениями; язык поддерживает оба подхода, и их смешивают по задаче, а не по догме.

---

# 3. Суть

> **ООП** собирает программу из объектов: данные и поведение живут вместе, объект отвечает на методы и прячет внутреннее состояние. **Функциональный стиль** собирает программу из функций: данные — значения, которые функции принимают и возвращают; побочные эффекты (запись на диск, мутация массива, `fetch`) стараются не прятать внутри «чистой» функции.
>
> JavaScript — мультипарадигменный язык: в одном файле работают `class` / объекты / `this` и функции первого класса (`map`, колбэки, замыкания). Так удобно моделировать сущность с идентичностью (корзина, виджет) объектом, а преобразование списка — цепочкой функций без скрытого состояния.
>
> Стиль выбирают по задаче. Если важно «кто владеет данными и какие у него операции» — ООП читается естественно. Если важно «вход → выход, те же аргументы дают тот же результат» — функциональный код проще тестировать и склеивать (`filter`, затем `map`).
>
> Ловушка: считать стили врагами или надеть `map` на мутацию. JS не запрещает `push` внутри «функциональной» функции и не привязывает `this` навечно: метод, переданный как колбэк, легко теряет объект. Смешивать можно, но договорённость «кто меняет данные» должна быть явной.

---

# 4. Самое главное запомнить

- ООП: состояние и методы на одном объекте; `cart.add(item)` работает с данными этой корзины.
- Чистая функция: вход → выход без скрытой записи в общий объект; повтор с теми же аргументами даёт тот же результат.
- JS мультипарадигменный: `class`, объект-литерал и функции как значения живут в одном языке.
- `map` / `filter` / `reduce` возвращают новый массив; `push` или присваивание поля внутри колбэка — побочный эффект, не «функциональность по имени метода».
- `this` зависит от способа вызова: `obj.method()` видит объект, а оторванный `const fn = obj.method; fn()` — обычно нет.
- `const` запрещает переприсвоить переменную, но не поля объекта: `{ ...obj, total: 3 }` — новый объект, `obj.total = 3` — мутация того же.
- Глубокие деревья `extends` в JS часто хуже композиции функций или делегирования другому объекту.

# 5. Описание

```text
ООП                                    функциональный стиль
───                                    ────────────────────
объект: данные + методы                данные — значения
cart.add(item)                         addItem(cart, item) → newCart
состояние внутри (this)                нет скрытого this
наследование / полиморфизм             композиция функций
часто мутация this.items               новый массив / объект
```

Один сценарий — «добавить товар в корзину» — можно записать обоими способами. Разница не в синтаксисе `class` vs стрелка, а в том, **где живёт состояние** и **кто имеет право его менять**.

## ООП: данные и поведение вместе

Объект хранит свои поля и набор операций. Снаружи вызывают метод; как устроены внутренности — дело объекта.

```js
class Cart {
  constructor() {
    this.items = [];
  }

  add(item) {
    this.items.push(item); // ← состояние этой корзины
  }

  get total() {
    return this.items.reduce((sum, it) => sum + it.price, 0);
  }
}

const cart = new Cart();
cart.add({ id: 'a', price: 10 });
```

В JS это не «как в Java»: `class` — удобный синтаксис над прототипами, объекты часто создают литералом `{}` без класса. Детали цепочки прототипов — в группе JS; здесь важно: **идентичность** (`cart`) и **методы на экземпляре**.

Полиморфизм на практике — одинаковое имя метода у разных объектов: `shape.area()`, а реализация своя. Наследование (`extends`) — один из способов это получить, не единственный.

## Функциональный стиль: данные отдельно

Функция не «владеет» корзиной. Она получает значение и возвращает новое. Исходный объект не трогают.

```js
const addItem = (cart, item) => ({
  ...cart,
  items: [...cart.items, item], // ← новый массив, старый не push
});

const total = (cart) =>
  cart.items.reduce((sum, it) => sum + it.price, 0);

const empty = { items: [] };
const next = addItem(empty, { id: 'a', price: 10 });
// empty.items.length === 0
```

Три опоры стиля в JS:

| Идея | Что это в коде |
|---|---|
| Функции первого класса | функцию кладут в переменную, передают аргументом, возвращают из функции |
| Чистая функция | нет скрытой записи наружу; результат определяется аргументами |
| Неизменяемость | вместо `arr.push(x)` — `[...arr, x]`; вместо `obj.x = 1` — `{ ...obj, x: 1 }` |

`map` / `filter` / `reduce` как раз принимают функцию как значение и (по задумке) строят **новый** массив / значение.

```js
const prices = [10, 20, 5];
const withTax = prices.map((p) => p * 1.2); // [12, 24, 6]
// prices всё ещё [10, 20, 5]
```

## Один сценарий — два договора

```text
заказ: добавить товар, посчитать сумму

ООП:  cart.add(item)     →  изменился тот же cart
FP:   next = addItem(c, item)  →  c прежний, next — новый снимок
```

ООП удобен, когда сущность живёт долго и на неё ссылаются из UI, обработчиков, тестов: «эта корзина». Функциональный снимок удобен, когда данные гоняют по пайплайну и важно не испортить исходник (редьюсер, список заказов → отфильтровать → отсортировать → отдать в UI).

В одном модуле их часто комбинируют: объект-сервис с методами, а внутри метода — чистые функции над массивом. Это не ошибка, если мутация не «утекает» в чужие ссылки на тот же объект.

## Когда какой стиль

| Вопрос | Скорее ООП | Скорее FP |
|---|---|---|
| Есть ли идентичность («этот виджет»)? | да | нет, только значение |
| Нужно спрятать внутренности? | методы + (по желанию) `#private` | данные снаружи, функции рядом |
| Много шагов над списком? | цикл / методы коллекции | `filter` → `map` → `reduce` |
| Побочный эффект (сеть, DOM)? | метод вроде `save()` | на краю: чистый расчёт, эффект отдельно |

Встроенные объекты JS сами смешанные: `Date` и `Map` — ООП-API с методами; массивы дают и `push` (мутация), и `map` (новый массив). Язык не выбирает за вас.

## Ловушки

**`map` с мутацией.** Имя метода не делает код функциональным:

```js
items.map((it) => {
  it.price *= 1.2; // ← испортили исходные объекты
});
```

Если нужен новый список — возвращайте новые объекты (`{ ...it, price: it.price * 1.2 }`). Если цель — побочный эффект, берите `forEach` / `for...of`, а не `map`.

**Потерянный `this`.** Метод — обычная функция, пока её не вызвали как метод:

```js
const { add } = cart;
add(item); // this не cart (в строгом режиме — ошибка / undefined)
```

Лечат явной передачей данных (функциональный стиль), стрелкой в поле класса, `.bind(cart)` или обёрткой `() => cart.add(item)`.

**`const` ≠ неизменяемость.** `const cart = { items: [] }` не даёт сделать `cart = …`, но `cart.items.push(x)` проходит. Защита данных — договорённость и новые объекты, не ключевое слово.

**Наследование вместо композиции.** Три уровня `extends` ради одной общей строки — хрупко. Часто достаточно передать функцию или другой объект («корзина использует `calcTotal(items)`»), без иерархии типов.

Императивный цикл (`for`) vs декларативный `map` — соседняя тема про парадигмы; здесь водораздел — **объект с состоянием** против **функции над значением**.
