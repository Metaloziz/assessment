# 1. Тема
**Принцип BDD**
---
# 2. Главное в одну фразу
BDD описывает ожидаемое поведение системы на общем для бизнеса, QA и разработки языке, часто в сценариях Given/When/Then.
---
# 3. Ответ для собеседования
> «BDD — развитие идей TDD с фокусом на поведение и ценность для пользователя. До реализации команда согласует примеры: в каком контексте пользователь действует, что делает и какой видит результат. Их можно записать в Gherkin и автоматизировать через Cucumber. Главное преимущество не сам инструмент, а единое и проверяемое понимание требования между бизнесом, QA и разработкой.»
---
# 4. Самое главное запомнить
- BDD говорит языком поведения, а не методов и классов.
- Given — исходный контекст; When — действие; Then — наблюдаемый результат.
- Сценарии — живой контракт, если их поддерживают.
- BDD и TDD можно сочетать на разных уровнях.
---
# 5. Описание
| Аспект | TDD | BDD |
|---|---|---|
| Фокус | Дизайн и корректность кода | Поведение и бизнес-ценность |
| Язык | Технические тесты | Понятные примеры поведения |
| Типичный уровень | Unit | Acceptance / integration / e2e |
| Участники | В основном разработчики | Бизнес, QA, разработчики |

```gherkin
Feature: Оформление заказа
  Scenario: Успешная оплата картой
    Given в корзине есть товар стоимостью 1000 рублей
    When покупатель оплачивает заказ валидной картой
    Then заказ получает статус "paid"
    And пользователь видит подтверждение оплаты
```

Шаги Gherkin связываются с кодом Cucumber, который открывает страницу или вызывает API и выполняет assertions. Не стоит превращать каждый UI-клик в отдельную строку: хороший сценарий описывает бизнес-намерение, остаётся коротким и читается как пример требования.

```javascript
// Эквивалентный тестовый стиль без Gherkin
test('валидная карта оплачивает заказ', async () => {
  const order = await checkout.pay(validCard);
  expect(order.status).toBe('paid');
});
```
