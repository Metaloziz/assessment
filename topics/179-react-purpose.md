# 1. Тема

**Назначение React**

---

# 2. Главное в одну фразу

React — библиотека для декларативного UI: описываешь, *как* должен выглядеть интерфейс при текущем состоянии, а синхронизацию с DOM берёт на себя библиотека.

---

# 3. Суть

> **React** — JavaScript-библиотека для построения пользовательских интерфейсов. UI собирается из **компонентов**: функций (или классов), которые по входным данным возвращают описание разметки. Вместо ручного `appendChild` / `innerHTML` пишешь, *что* должно быть на экране при текущих `props` и `state`, а React решает, *как* обновить DOM.
>
> Без такого подхода большой интерфейс быстро превращается в кашу императивных правок: кто-то забыл снять обработчик, где-то рассинхронизировался текст и данные. React даёт один поток: данные изменились → компонент перерисовался → DOM приведён к новому описанию. Это удобно для форм, дашбордов, SPA и любых экранов, где UI часто меняется.
>
> Под капотом — дерево элементов (Virtual DOM / снимок UI), сравнение со предыдущим снимком и точечный commit в браузер. Синтаксис JSX — сахар над вызовами `createElement` / `jsx`. Состояние и эффекты в современных приложениях обычно живут в хуках.
>
> Ловушка: React — не «фреймворк всего». Роутинг, запросы к API, глобальный store — отдельные библиотеки или свой код. И декларативность не отменяет понимание, *когда* компонент рендерится и *что* дорого обновлять.

---

# 4. Самое главное запомнить

- React описывает UI как функцию от данных: `UI = f(state, props)`.
- Единица сборки — **компонент**; приложение — дерево компонентов.
- Обновления идут сверху вниз по данным (однонаправленный поток), а не через хаотичные правки DOM.
- JSX компилируется в вызовы создания элементов, не в «магический HTML в браузере».
- React отвечает за слой представления; сеть, роутинг, стили — рядом, не «внутри ядра».
- Классовые компоненты ещё встречаются в легаси; новый код пишут на функциях + хуках.

---

# 5. Описание

```text
данные (props / state)
        ↓
   компонент → описание UI (элементы)
        ↓
   React сравнивает со старым снимком
        ↓
   обновляет Real DOM (commit)
```

## Зачем декларативный UI

Императивно: «найди кнопку, поменяй текст, повесь слушатель, при ошибке покажи span». При каждом новом состоянии нужно помнить, *что уже сделано*.

Декларативно: «если `loading` — спиннер, если `error` — сообщение, иначе список». React при каждом рендере получает полное описание желаемого UI и сам приводит DOM к нему.

## Компонентная модель

```jsx
function Greeting({ name }) {
  return <p>Привет, {name}</p>;
}

function App() {
  return (
    <main>
      <Greeting name="Анна" />
    </main>
  );
}
```

Компонент можно переиспользовать, тестировать изолированно и складывать в более крупные блоки. Данные вниз передаются через `props`; локальные изменения экрана — через `state` (см. тему про props/state).

## Что React делает и чего не делает

| Делает | Не делает сам |
| --- | --- |
| Рендер компонентов и обновление DOM | HTTP-клиент «из коробки» |
| Композиция UI, контекст, хуки | Файловый роутинг (нужен router) |
| Батчинг обновлений, согласование дерева | Глобальный store (Context / Redux / …) |

## Минимальный вход в приложение

```jsx
import { createRoot } from 'react-dom/client';
import App from './App';

createRoot(document.getElementById('root')).render(<App />);
```

Корень монтируется в один DOM-узел; дальше всё дерево — React-компоненты.

## Типичные ловушки новичка

- Думать, что «вызвал функцию компонента — сразу переписал DOM»: между описанием и DOM есть фазы render и commit.
- Хранить «истину» и в React-state, и вручную в DOM — они разъедутся.
- Путать React с Next.js / Remix: это уже фреймворки *на базе* React с роутингом и SSR.
