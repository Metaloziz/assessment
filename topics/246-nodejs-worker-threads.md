# 1. Тема

**Параллелизация через worker_threads**

---

# 2. Главное в одну фразу

Если в Node.js тяжёлый расчёт «забивает» основной поток, его выносят в `worker_threads` — отдельный поток JavaScript, который считает сам, а результат присылает сообщением, пока сервер продолжает отвечать на другие запросы.

---

# 3. Суть

> Представьте HTTP-сервер как стойку регистрации с одним сотрудником — это **основной поток** Node. Пока он в коде крутит долгий цикл (хеш, разбор файла, математика), он не может заняться следующим клиентом: таймеры, другие запросы и лёгкие «ping» ждут в очереди. Это не «медленный интернет», а занятый **call stack** — стек вызовов, по которому идёт ваш JavaScript.
>
> `async`/`await` здесь не дают второе ядро процессора. Они помогают **отложить** продолжение после сети или таймера, но сам тяжёлый алгоритм на одном потоке всё равно выполняется по очереди. Чтобы считать параллельно и не блокировать стойку, в Node есть модуль **`worker_threads`**: он поднимает ещё один поток V8 со своим стеком.
>
> Схема простая: основной поток создаёт `Worker`, передаёт вход (`workerData` при старте или `postMessage` позже), worker считает и шлёт ответ в `parentPort`. Пока worker занят, main свободен — может принять `GET /ping`, пока в соседнем потоке идёт `POST /job`. Типичный кейс — тяжёлая работа внутри API: handler ждёт сообщение от worker и отдаёт JSON клиенту.
>
> Ловушки: не путать с **`cluster`** и **`child_process`** (это отдельные процессы ОС, другой API) и с **Web Workers** в браузере (похожая идея, но другая среда). Ещё — создавать поток на каждый запрос без лимита и таскать огромные объекты копированием; для больших буферов смотрят `SharedArrayBuffer` или transfer списка.

---

# 4. Самое главное запомнить

- Основной поток Node один: долгий **синхронный** код в handler блокирует event loop — другие запросы ждут.
- `async`/`await` не параллелят CPU: они откладывают работу, но не считают на втором ядре.
- `worker_threads` — отдельный поток JS в том же процессе; связь через `postMessage` и `parentPort`.
- Пока worker считает, main может обрабатывать другие HTTP-запросы и таймеры.
- Вход в worker: `workerData` при создании или сообщения после; по умолчанию данные копируются (structured clone).
- Не путать с `cluster` / `child_process` (процессы) и с браузерными Web Workers.
- Поток дороже простого колбэка: для короткой задачи overhead может съесть выигрыш; для длинного CPU — окупается.

# 5. Описание

```text
клиент: POST /job (тяжёлый расчёт)     +     GET /ping
              │                                    │
              ▼                                    ▼
         ┌──────────────────────────────────────────────┐
         │  main thread — «стойка», event loop          │
         │                                              │
         │  режим main:  burn() прямо в handler ────────┼──► ping ждёт
         │  режим worker: new Worker ──► другой поток   │
         │       ▲                         считает      │
         │       └──── message ←─────────┘             ├──► ping сразу
         └──────────────────────────────────────────────┘
```

## Базовое понимание

Node.js хорошо тянет много одновременных **сетевых** запросов: пока один клиент ждёт ответа из базы, сервер может обслужить другого. Но если в обработчике HTTP вы сами крутите тяжёлый цикл на процессоре (**CPU-bound**), «магии» нет — этот код выполняется на **основном потоке**, и пока цикл не закончится, event loop не возьмёт следующую задачу.

`worker_threads` решают именно эту проблему: тяжёлую математику передают **соседнему потоку** в том же процессе Node. Основной поток остаётся «на стойке» — принимает запросы, отвечает на лёгкие ping, ждёт результат worker через Promise вокруг `message` / `error` / `exit`.

Общая картина та же, что у однопоточного JS в браузере (тема «JS — однопоточный и синхронный язык»): один call stack на main. В браузере аналог — Web Workers; в Node — `worker_threads`. Идея одна: второй поток считает, первый остаётся отзывчивым.

## Почему async не спасает

Сеть, файлы и таймеры Node делегирует **libuv** и системе: колбэк придёт позже, и стек успеет опустеть. Но **тело вашей функции** с миллионным `for` или тяжёлым хешом всё равно крутится синхронно на main. Можно вручную резать работу на куски и между ними отдавать управление (`setImmediate`, `await` на микрозадачах), но это не ускорит алгоритм на одном ядре — только размажет блокировку.

Workers нужны, когда задача **долго и плотно** грузит CPU и вы хотите, чтобы сервер параллельно жил своей жизнью.

## Как устроен worker_threads

Минимальный контракт на стороне main:

```js
import { Worker } from 'node:worker_threads';

const worker = new Worker(new URL('./heavy.js', import.meta.url), {
  workerData: { durationMs: 350 }, // вход при старте
});

worker.on('message', (msg) => {
  console.log(msg); // результат с worker
});
```

В файле worker:

```js
import { parentPort, workerData } from 'node:worker_threads';

function burn(ms) {
  const end = performance.now() + ms;
  let x = 0;
  while (performance.now() < end) x = (x + 1) % 1e9;
  return x;
}

parentPort.postMessage({
  checksum: burn(workerData.durationMs),
});
```

HTTP-handler оборачивает ожидание в Promise: подписался на `message`, получил checksum — отправил ответ клиенту. Пока Promise «висит», event loop **не заблокирован** синхронным циклом — параллельный `GET /ping` отвечает за миллисекунды. В лабе оба режима бьют в один учебный API: один объём CPU, разница видна в задержке ping рядом с job.

## Main vs Worker под нагрузкой

| Режим | Где идёт расчёт | Параллельный ping |
| --- | --- | --- |
| main | синхронно в handler | ждёт конца job |
| worker | в другом потоке | отвечает сразу |

## Пул, границы и когда не нужны workers

На каждый запрос `new Worker` — нормально для демо; в проде чаще **пул** с очередью и лимитом потоков (обычно около числа ядер минус запас на main). Не всё стоит выносить: короткая работа плюс сериализация сообщений может быть медленнее sync на main. Задачи, где узкое место — диск или сеть (**I/O-bound**), обычно закрывают обычным async API без workers.

Передача больших объектов между потоками копирует память (structured clone). Если гоняете мегабайты, смотрите transfer list для `ArrayBuffer` или `SharedArrayBuffer` — иначе узким местом станет не расчёт, а копирование.
