# 1. Тема

**REST API и RESTful API**

---

# 2. Главное в одну фразу

REST — стиль HTTP-API вокруг ресурсов и единообразных операций; RESTful — API, который реально следует этим правилам, а не только называет себя REST.

---

# 3. Суть

> **REST** (Representational State Transfer) — архитектурный стиль для сетевых API: клиент работает с **ресурсами** по URL, меняет и читает их через стандартные HTTP-методы, а в теле получает **представление** состояния (часто JSON). Это не отдельный протокол и не библиотека — договорённость, как строить интерфейс поверх HTTP.
>
> Так API проще понимать и переиспользовать: один и тот же ресурс (`/orders/42`) обслуживают `GET` / `PUT` / `DELETE`, без зоопарка RPC-эндпоинтов вроде `/getOrder` и `/updateOrderStatus`. Клиент и сервер слабо связаны: сервер не хранит сессию диалога между запросами (**stateless**), а смысл операции читается из метода, пути и тела.
>
> **RESTful API** на практике — API, который следует REST: существительные в путях, идемпотентность там, где её ждёт метод, осмысленные статусы (`200` / `201` / `404` / `409`), гипермедиа по желанию. Название «REST API» на маркетинговой странице само по себе ничего не гарантирует.
>
> Ловушка: назвать всё REST, а под капотом оставить RPC (`POST /api/doSomething` на каждое действие) или смешать идентификатор ресурса с бизнес-глаголами в URL. Тогда теряются предсказуемость кеша, идемпотентность повторов и единообразие клиентов. Детали методов, версий HTTP и TLS — соседние темы группы; здесь важен контракт «ресурс ↔ операция».

---

# 4. Самое главное запомнить

- Ресурс — сущность с URL (`/users/12`); путь — существительное, не глагол действия.
- Операция кодируется HTTP-методом: `GET` читать, `POST` создавать, `PUT`/`PATCH` менять, `DELETE` удалять.
- Ответ — **представление** ресурса (JSON и заголовки), не «скрытый» RPC-вызов с произвольным именем.
- REST предполагает **stateless**: каждый запрос самодостаточен (auth, id, тело), сервер не опирается на «прошлый шаг» диалога.
- «REST API» — часто ярлык; **RESTful** — когда правила реально соблюдены.
- Query (`?page=1`) уточняет выборку/фильтр, но не заменяет идентификатор ресурса в пути.

# 5. Описание

```text
клиент                         сервер
  │                              │
  │  GET /orders/42              │
  │  Authorization: …            │
  │ ───────────────────────────► │  найти ресурс orders/42
  │                              │  собрать представление (JSON)
  │  200 OK                      │
  │  { "id": 42, "status": … }   │
  │ ◄─────────────────────────── │
  │                              │
  │  POST /orders                │
  │  { "items": […] }            │
  │ ───────────────────────────► │  создать ресурс
  │  201 Created                 │
  │  Location: /orders/99        │
  │ ◄─────────────────────────── │
```

## Ресурс и представление

**Ресурс** — то, о чём говорит API: заказ, пользователь, файл. Его адрес — URI. Один ресурс может отдаваться в разных форматах (`Accept: application/json` vs XML), но идентификатор один.

**Представление** — снимок состояния в теле ответа/запроса. Клиент не «держит объект на сервере», а получает и отправляет данные по правилам HTTP.

```text
/orders          → коллекция
/orders/42       → элемент коллекции
/orders/42/items → вложенный ресурс (осторожно с глубиной)
```

Глаголы вроде `/orders/42/cancel` — уже RPC-стиль. В REST отмену чаще моделируют сменой состояния (`PATCH` поля `status`) или отдельным подресурсом события, если это отдельная сущность.

## HTTP-методы и CRUD

| Операция | Типичный метод | Идемпотентность (ожидание) |
| --- | --- | --- |
| Read | `GET` | да (повтор не меняет) |
| Create | `POST` на коллекцию | нет |
| Replace / Update | `PUT` / `PATCH` | `PUT` — да; `PATCH` — зависит от семантики |
| Delete | `DELETE` | да |

Идемпотентность важна для ретраев сети: повторный `PUT` с тем же телом не должен плодить дубликаты, в отличие от наивного `POST`.

Коллекция и элемент:

```http
GET    /users
POST   /users
GET    /users/7
PUT    /users/7
PATCH  /users/7
DELETE /users/7
```

Статусы коротко: `200` — ок с телом; `201` — создано (+ часто `Location`); `204` — ок без тела; `404` — нет ресурса; `409` — конфликт состояния. Полный разбор протокола HTTP — тема «Протоколы HTTP, HTTP/2, HTTPS».

## Stateless и единообразный интерфейс

Клиент каждый раз передаёт всё нужное: токен, id, тело. Сервер не обязан помнить «на каком шаге формы вы остановились» между запросами (сессия браузера и cookie — отдельная история; для REST-API состояние диалога не прячут в памяти процесса как обязательный контракт).

Единообразие: одни и те же методы и коды для разных ресурсов. Клиент, умеющий `GET`/`POST`/`404`, переносится с `/users` на `/orders` без новой «языка команд».

## REST API vs RESTful API

| Термин | Что обычно имеют в виду |
| --- | --- |
| REST | стиль Fielding: ресурсы, представления, единообразный интерфейс, stateless… |
| REST API | HTTP-API «в духе REST» (часто размыто) |
| RESTful | API, который **соблюдает** правила: ресурсы, методы, статусы, без RPC-зоопарка |

Строгий REST по диссертации Fielding включает и HATEOAS (ссылки на следующие шаги в ответах). В продуктовых JSON-API это редко доводят до конца — и это нормально осознавать: «почти REST / pragmatic REST» ≠ «нарушаем всё подряд».

## Антипаттерны

- `POST /getUser` / `POST /deleteOrder` — глаголы вместо методов.
- Всё через один `POST /api` с полем `action` — скрытый RPC.
- Игнорировать статусы: всегда `200` + `{ "error": true }` в теле — ломает кеш и клиентов.
- Класть секретные данные только в query и логировать URL целиком.

Query-параметры (`?sort=asc&limit=20`) — фильтры и пагинация поверх ресурса; их разбор — соседняя тема группы.
