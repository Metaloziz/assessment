# 1. Тема

**Принцип выделения программных узлов, которые необходимо логировать**

---

# 2. Главное в одну фразу

Логируют не «каждую строку», а границы системы и критические точки: входы/выходы, решения, смену состояния и ошибки — с контекстом, достаточным восстановить путь запроса.

---

# 3. Суть

> **Программный узел** для логирования — место, где система пересекает границу или принимает решение с последствиями: HTTP/handler, очередь, cron, вызов Stripe, auth allow/deny, смена статуса заказа, пойманная ошибка. Лог здесь даёт сигнал для отладки и мониторинга. Лог в каждой итерации цикла или в чистой утилите `sum(a,b)` — шум: дорогой I/O, сложнее найти важное, выше риск засветить PII.
>
> Зачем принцип: на инциденте нужны ответы «какой `requestId`, где упали, что решили на auth, что ответил внешний API». Если логировали всё подряд — тонете в debug; если только `console.log('error')` без контекста — не собрать путь. Старшие инженеры заранее отмечают узлы на схеме потока, а не «добавим лог когда упадёт».
>
> Как выбирать. Нарисовать путь запроса → отметить границы, бизнес-события, интеграции, ветки решений → для каждого узла: уровень (`debug`/`info`/`warn`/`error`) и поля (`requestId`, `userId`, `operation`, latency, result). Секреты и сырые карточки — маскировать или не писать. Цель проверки: по одному `requestId` в Loki/ELK восстановить цепочку без чтения исходников наугад.
>
> Ловушка: логировать тело запросов целиком «на всякий случай»; debug на проде без sample; путать бизнес-событие (`order.paid`) с техническим шумом (`entered function`). Уровни без политики (всё `info`) обесценивают фильтры и алерты.

---

# 4. Самое главное запомнить

- Узлы = границы + решения + состояние + ошибки + интеграции.
- Не логировать: плотный цикл, тривиальные хелперы, секреты.
- Контекст: `requestId`, `userId`, `operation`, результат.
- Уровни: debug → info → warn → error (политика в команде).
- Проверка: один `requestId` → весь путь.
- Приоритет: ошибки → бизнес-события → границы → интеграции → debug.

---

# 5. Описание

## Какие узлы

1. **Границы:** HTTP, gRPC, queue consumer, cron, CLI.
2. **Бизнес-события:** заказ создан, оплата прошла, пользователь зарегистрирован.
3. **Решения:** auth ok/fail, validation reject, cache hit/miss, feature flag, fallback.
4. **Ошибки:** с типом, кодом, безопасным сообщением, stack (в error-tracker).
5. **Интеграции:** внешний API — request id партнёра, статус, latency.

## Алгоритм

```text
поток запроса
   │
   ├─ входы / выходы      → info
   ├─ бизнес-события      → info
   ├─ решения (auth…)     → info / warn
   ├─ интеграции          → info + latency
   └─ ошибки              → error (+ Sentry)
 убрать шум и PII
```

## Пример полей

```javascript
logger.info({
  requestId,
  userId,
  operation: 'checkout.pay',
  result: 'ok',
  paymentProvider: 'stripe',
  durationMs: 240,
}, 'payment completed');
```

## Анти-паттерны

- `logger.debug(req)` со всем телом и заголовками Authorization.
- Лог внутри `map` на 10k элементов без sample.
- Разные имена одной операции (`pay` / `payment` / `checkoutPay`) — ломает поиск.
