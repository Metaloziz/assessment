# 1. Тема

**Web-workers**

---

# 2. Главное в одну фразу

`Web Worker` запускает JavaScript в отдельном потоке браузера, чтобы тяжёлые вычисления не замораживали страницу, а результат возвращался через сообщения.

---

# 3. Суть

> `Web Worker` нужен в тот момент, когда одна вкладка должна и считать, и оставаться отзывчивой. Если тяжёлый цикл, парсинг большого файла, подготовка данных для графика или криптография идут прямо в `main thread`, браузер перестаёт нормально рисовать интерфейс, обрабатывать клики и крутить анимации.
>
> Воркер запускает отдельный JavaScript-контекст через `new Worker(...)`. У него нет доступа к DOM, `window` и элементам страницы, поэтому работа строится через обмен сообщениями: страница шлёт задачу через `postMessage`, воркер считает и отвечает назад через `onmessage`.
>
> На практике это удобно для CPU-задач, где важнее не “ускорить всё магически”, а убрать подвисание UI. Цена у такого подхода тоже есть: данные нужно сериализовать, код воркера живёт отдельно, а сам воркер надо корректно завершать через `terminate()` или `self.close()`.
>
> Не путайте `Web Worker` с `Service Worker`. `Web Worker` помогает считать в фоне для текущей страницы, а `Service Worker` работает вокруг сети, кэша и офлайн-режима.

---

# 4. Самое главное запомнить

- `Web Worker` полезен для тяжёлых CPU-задач: расчётов, парсинга, подготовки больших массивов данных.
- У воркера нет доступа к DOM, поэтому он не может напрямую менять JSX, `document` или состояние компонентов.
- Связь между страницей и воркером идёт через `postMessage` и `onmessage`; это разные контексты, а не “общая функция в фоне”.
- Большие `ArrayBuffer` можно передавать как `transferable`, чтобы не копировать память целиком.
- В React воркер обычно создают в `useEffect` и завершают в cleanup через `worker.terminate()`.
- `SharedWorker` может обслуживать несколько вкладок, но чаще в приложениях встречается обычный `Dedicated Worker`.
- `Service Worker` и `Web Worker` решают разные задачи: первый связан с сетью и кэшем, второй — с вычислениями.

| | Web Worker | Service Worker |
|---|---|---|
| Цель | Вычисления | Сеть / кэш / push |
| DOM | Нет | Нет |
| HTTPS | Не обязателен | Обязателен (кроме localhost) |

# 5. Описание

```text
UI / кнопка
   |
   | postMessage({ task })
   v
Web Worker
   |
   | считает без DOM
   v
postMessage({ result })
   |
   v
main thread обновляет интерфейс
```

## Что именно выигрываем

Главный смысл `Web Worker` не в том, что код “обязательно станет быстрее”, а в том, что страница не повиснет во время тяжёлой работы. Если вычисление идёт прямо в обработчике клика, браузер занят этим же потоком и откладывает перерисовку интерфейса. Поэтому кнопка может не отпускаться, индикатор зависает, а ввод ощущается “тупым”.

Когда расчёт уходит в воркер, `main thread` остаётся свободным для UI. Воркер не рисует страницу и не знает про компоненты, но он может спокойно считать, а потом вернуть готовый результат сообщением.

## Как устроен обмен

Обычно страница создаёт воркер так:

```ts
const worker = new Worker(new URL('./heavy.worker.ts', import.meta.url), {
  type: 'module',
})
```

После этого основной поток подписывается на `worker.onmessage`, а для запуска задачи вызывает `worker.postMessage(...)`. Внутри файла воркера код слушает `self.onmessage`, берёт входные данные, выполняет тяжёлую функцию и отправляет ответ через `self.postMessage(...)`.

```ts
worker.postMessage({ type: 'sumPrimes', limit: 1_200_000 })

worker.onmessage = (event) => {
  console.log(event.data.result)
}
```

Это не общий стек вызовов и не “асинхронная функция с доступом ко всему приложению”. Между страницей и воркером есть граница сериализации данных.

## Что можно и чего нельзя внутри воркера

Внутри `Web Worker` доступны многие обычные вещи JavaScript и часть Web API: таймеры, `fetch`, `URL`, typed arrays, `crypto`. Но прямого доступа к DOM нет: нельзя сделать `document.querySelector(...)`, нельзя повесить обработчик на кнопку и нельзя взять ref из React-компонента.

Именно поэтому хороший кандидат для воркера — код, который много считает и мало знает про интерфейс. Например, разбор CSV, фильтрация большого массива, генерация поискового индекса, подготовка точек для графика.

## Практические ловушки

- Передача больших объектов между потоками стоит времени: иногда узкое место переезжает из расчёта в сериализацию сообщений.
- Воркер живёт отдельно, поэтому нельзя “передать туда функцию с замыканием” или напрямую использовать store/React state.
- В проектах с Vite, webpack и другими сборщиками файл воркера обычно создают через `new URL(..., import.meta.url)`, чтобы бандлер правильно вынес его в отдельный asset.
- Если воркер больше не нужен, его надо завершать. Иначе можно оставить лишний фоновой поток жить дольше, чем нужно странице.
