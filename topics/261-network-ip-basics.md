# 1. Тема

**Базовое понимание IP**

---

# 2. Главное в одну фразу

IP задаёт логический адрес узла и доставку датаграмм: пакет идёт по `src`/`dst` и префиксу CIDR, а не по hostname и не по порту процесса.

---

# 3. Суть

> **IP** (Internet Protocol) — адресация узлов и доставка **датаграмм** между сетями. Адрес — число: IPv4 это 32 бита (`a.b.c.d`), IPv6 — 128 бит. Сам по себе адрес мало что решает: его читают вместе с **префиксом** (`10.0.2.15/24`). Префикс отделяет биты сети от битов хоста и отвечает на вопрос, лежит ли назначение в той же сети.
>
> Это проявляется, когда контейнер «не видит» БД в другой подсети, firewall режет по CIDR, а в логах один IP, хотя клиент клянётся, что ходит с другого. VPC, Docker-сети и ACL смотрят на адрес и маску, не на hostname и не на HTTP-путь.
>
> Хост кладёт в пакет `src` и `dst`. Если `dst` совпадает с локальным префиксом — доставка **on-link**. Иначе пакет уходит на **default gateway**, а роутеры выбирают next hop по **longest prefix match**. Частные диапазоны RFC1918 в публичный интернет сами не маршрутизируются: наружу их обычно выводит **NAT**, подменяя источник на публичный адрес.
>
> Ловушка: путать IP с именем (DNS — соседняя тема) и с портом процесса (транспорт). `10.x` в access-логе часто адрес после NAT или сосед по мосту, а не «IP ноутбука пользователя». `/16` и `/24` — разный размер сети, не две записи одного адреса.

---

# 4. Самое главное запомнить

- IPv4 — 32 бита (`203.0.113.10`); IPv6 — 128 бит (`2001:db8::1`); оба задают *узел*, не процесс.
- Адрес читают с префиксом: `10.0.2.15/24` значит сеть `10.0.2.0/24`, не «просто четыре октета».
- Совпадение префикса → on-link; иначе next hop / default gateway.
- Роутер выбирает маршрут по **longest prefix match**: `/24` бьёт `/16`, default `0.0.0.0/0` — запасной.
- RFC1918 (`10/8`, `172.16/12`, `192.168/16`) снаружи не маршрутизируются без NAT (или VPN/туннеля).
- NAT подменяет `src` (часто и порт); IP в логах бэка может быть адрес шлюза, не клиента.
- Loopback (`127.0.0.1/8`, `::1`) — только эта машина; link-local (`169.254/16`, `fe80::/10`) — сегмент без DHCP, не «интернет».

# 5. Описание

```text
пакет: src 10.0.2.15  →  dst ?
                 │
          совпал префикс
            /24 хоста?
           /          \
     да: on-link     нет: gateway
     (та же сеть)    (чужая сеть → NAT / роутер)
```

## Адрес и префикс (CIDR)

**CIDR** (Classless Inter-Domain Routing) — способ записать сеть: адрес + **длина префикса**. Число после `/` — сколько *старших* бит принадлежат сети, остальные — хосту. Так отказались от жёстких «классов» A/B/C (`/8`, `/16`, `/24` только): сеть может быть `/22`, `/27`, `/32`.

IPv4-адрес — 32 бита, четыре октета. `/24` значит: 24 бита сети, 8 бит хоста → 256 адресов. Два из них служебные: адрес самой сети и broadcast; хостам остаются `10.0.2.1` … `10.0.2.254`.

```text
10.0.2.15/24
│         └── 8 бит хоста
└── 24 бита сети  →  10.0.2.0

сеть:      10.0.2.0
broadcast: 10.0.2.255
хосты:     10.0.2.1 … 10.0.2.254
```

**Маска** — та же длина в виде четырёх октетов: `/24` = `255.255.255.0`, `/16` = `255.255.0.0`, `/32` = один конкретный хост. Проверка «в этой ли сети?» — не «похожи цифры», а битовое И: `(ip & mask) === (network & mask)`. Поэтому `10.0.2.40` в `10.0.2.0/24`, а `10.0.3.40` — уже другая сеть.

| Префикс | Маска | Сколько адресов | Типично |
| --- | --- | --- | --- |
| `/32` | `255.255.255.255` | 1 | один хост в ACL / маршруте |
| `/24` | `255.255.255.0` | 256 | LAN, Docker-мост |
| `/16` | `255.255.0.0` | 65 536 | крупная подсеть, VPC |
| `/0` | `0.0.0.0` | все | default route |

Чем **длиннее** префикс, тем уже сеть: `/24` точнее `/16`. Роутер при нескольких совпадениях берёт **longest prefix match**. `0.0.0.0/0` — «всё остальное», запасной выход в интернет.

Запись `10.0.2.15/24` на интерфейсе говорит: «мой адрес `10.0.2.15`, соседи — вся `10.0.2.0/24`». Пакет *внутрь* префикса идёт on-link; *наружу* — на gateway. Один интерфейс может нести несколько адресов (IPv4 + IPv6, VPN, alias). Маршрут выбирают **по `dst` пакета**, не по имени сервера.

## IPv4 и IPv6

| | IPv4 | IPv6 |
|---|---|---|
| Длина | 32 бита | 128 бит |
| Запись | `203.0.113.10` | `2001:db8::10` (сжатие нулей) |
| Частные / unique local | RFC1918 | `fc00::/7` (обычно `fd00::/8`) |
| Loopback | `127.0.0.1` | `::1` |

На практике часто **dual-stack**: один hostname резолвится и в A, и в AAAA. Клиент может пойти в IPv6, а ACL написан только под IPv4 — «сайт открывается не у всех».

IPv6 не использует broadcast; вместо него multicast. NAT для IPv6 не обязателен (адресов хватает), но unique local и firewall по-прежнему режут, кто с кем говорит.

## Специальные диапазоны

| Диапазон | Смысл |
| --- | --- |
| `127.0.0.0/8`, `::1` | loopback |
| `10/8`, `172.16/12`, `192.168/16` | частные (LAN, Docker, VPC) |
| `169.254.0.0/16`, `fe80::/10` | link-local |
| `224.0.0.0/4` | multicast IPv4 |
| публичный unicast | маршрутизируется в интернет (с оговорками ACL/NAT) |

Документация и стенды часто берут `192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24` (TEST-NET) — их не ждут как «живой» прод.

## NAT

**NAT** (Network Address Translation) подменяет адреса в заголовке IP (часто ещё и порт на транспорте), чтобы частная сеть могла выходить в интернет с одного публичного адреса. RFC1918 (`10/8`, `172.16/12`, `192.168/16`) в глобальную таблицу маршрутов не объявляют: пакет с `src 10.0.2.15` снаружи «неоткуда» и «некуда». Шлюз на границе переписывает адрес и ведёт **таблицу связок**.

Два направления:

| | Что меняют | Зачем |
| --- | --- | --- |
| **SNAT** (masquerade) | `src` частный → публичный IP шлюза (+ часто порт) | много хостов LAN выходят как один WAN-адрес |
| **DNAT** (проброс, port forward) | `dst` публичный:порт → внутренний хост:порт | пустить входящее на конкретный сервис внутри |

```text
исходящий (SNAT)
  10.0.2.15:52311  →  NAT  →  203.0.113.8:40012  →  api
                          таблица: 40012 ↔ 10.0.2.15:52311
  ответ api → 203.0.113.8:40012 → NAT смотрит таблицу → 10.0.2.15:52311

входящий без DNAT
  интернет → dst 10.0.2.15    нет маршрута / нет записи в таблице → drop
  интернет → dst 203.0.113.8:443  без проброса → drop
```

Ключ таблицы — обычно **публичный IP + порт** (и протокол TCP/UDP), не «просто IP». Поэтому два ноутбука за одним роутером не мешают друг другу: у каждого свой ephemeral-порт на WAN. **Masquerade** — SNAT, который подставляет текущий адрес исходящего интерфейса (удобно, если WAN-IP выдаёт DHCP).

Без записи в таблице (и без DNAT) входящий пакет на частный адрес **с интернета** не дойдёт: для публичной сети `10.0.2.15` не существует как маршрута. Отсюда «у меня открывается `localhost` / `10.x`, а у клиента — нет». Security group / firewall на облаке — отдельный фильтр; даже с DNAT порт могут закрыть политикой.

NAT не делает хост «анонимным» и не заменяет TLS: он только подменяет адреса. IP в access-логе бэка после SNAT — часто адрес шлюза (офисный NAT, CGNAT оператора), не ноутбук пользователя.

## Куда слать пакет

Упрощённое правило хоста:

1. `dst` в одном из локальных префиксов → on-link (дальше канал/ARP — соседняя тема уровней).
2. иначе → gateway, чей префикс **длиннее** всего подошёл (или default `0.0.0.0/0`).
3. на каждом хопе TTL / hop limit уменьшается; обрыв пути — ICMP, не HTTP-статус.

Имя хоста к этому шагу уже должно стать IP. Модель «какой уровень что делает» — темы TCP/IP; здесь важен **сам адрес**: префикс, частный/публичный, NAT.

## Ловушки

- Сравнивать адреса как строки (`10.0.2.5` «похоже» на `10.0.2.50`) вместо проверки префикса.
- Ждать, что частный IP из лога бэка — IP пользователя в интернете.
- Открыть порт в Docker на `127.0.0.1` и удивляться, что соседний контейнер не коннектится.
- Написать ACL только на IPv4 при dual-stack.
- Путать «нет маршрута» (IP) с «порт закрыт» (транспорт) и с `404` (HTTP).
