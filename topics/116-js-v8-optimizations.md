# 1. Тема

**Оптимизации в V8: скрытые классы · исправление типов аргументов · общие сущности в глобальной области видимости**

---

# 2. Главное в одну фразу

V8 ускоряет горячий код, когда объекты собраны в одну внутреннюю форму, аргументы функций приходят с предсказуемыми типами, а конструкторы и обработчики не пересоздаются на каждой итерации цикла.

---

# 3. Суть

> V8 не «магически ускоряет любой JavaScript». На горячем пути он запоминает, **как устроены объекты** (скрытые классы / shapes), **какие типы приходят в аргументы** на конкретном месте вызова, и **какие функции и конструкторы стабильны** во времени.
>
> **Скрытые классы** — внутренняя форма объекта: какие поля и в каком порядке появились. Если все экземпляры собираются одинаково, доступ к `obj.x` на одном call site проходит через **inline cache** быстрее (monomorphic). Разный порядок полей, `delete`, «то `y`, то `label`» — разные формы, кэш раздувается (polymorphic / megamorphic).
>
> **Исправление типов аргументов** — профиль вызовов: TurboFan строит узкий машинный код под наблюдаемые типы (`number + number`). Если после «числового» профиля прилетает строка или смешанный тип — **deopt**, откат к более общему пути. Семантика JS сохраняется, скорость — нет.
>
> **Общие сущности в глобальной / модульной области** — конструктор `Point`, функция `sumXY`, обработчик — объявлены **один раз** на уровне модуля, а не создаются заново внутри `for`. Иначе у движка каждый раз новая функция, профиль не копится, оптимизация не успевает «прилипнуть».
>
> Правило практики: сначала профиль (Performance, CPU profile), потом точечная правка hot path. Не переписывайте весь проект «под V8» заранее.

---

# 4. Самое главное запомнить

- Скрытый класс (shape) — внутренняя форма: поля и порядок их появления; одинаковая сборка → monomorphic IC.
- Inline cache на `obj.prop`: одна форма → быстро; зоопарк форм → polymorphic / megamorphic.
- Инициализируйте поля в конструкторе в **одном порядке**; избегайте `delete` и редких «случайных» ключей в hot path.
- На call site аргументы с **стабильными типами** помогают JIT; смена типа — типичный повод для deopt.
- Конструкторы и горячие функции — **на уровне модуля**, не `function make() { … }` внутри цикла на каждый проход.
- Пороги JIT и IC меняются между версиями V8 — выводы только из профиля, не из «мудрости интернета».

---

# 5. Описание

```text
горячий цикл
  → объекты одной shape?     → IC monomorphic
  → аргументы одного типа?   → TurboFan держит узкий код
  → функция/класс один?      → профиль копится
  → допущение сломано        → deopt / общий путь
```

## Скрытые классы

V8 не хранит «словарь свойств» на каждый доступ. Он запоминает **форму**: сначала появилось `x`, потом `y` — это одна shape. Другой объект с тем же порядком полей делит ту же форму.

```js
class Point {
  constructor(x, y) {
    this.x = x; // ← один порядок у всех экземпляров
    this.y = y;
  }
}

function lengthSquared(point) {
  return point.x * point.x + point.y * point.y;
}
```

```text
{ x, y } ──одна shape──► IC lengthSquared: monomorphic
{ x } потом y или label ──разные shapes──► polymorphic
```

Плохо для предсказуемости:

```js
const point = { x: 1 };
if (Math.random() > 0.5) point.y = 2;
else point.label = 'A'; // разные формы на одном call site
```

## Исправление типов аргументов

На месте вызова `add(a, b)` движок собирает **обратную связь по типам**. Длинная серия `add(1, 2)` даёт узкий профиль «число + число» — TurboFan может сгенерировать специализированный код.

```js
function add(a, b) {
  return a + b;
}

for (let i = 0; i < 10_000; i++) add(1, 2); // ← числовой профиль
add('1', '2'); // ← другой тип → deopt, общий путь
```

Смена типа **не ломает программу** — ломает только оптимизацию. В real code смешение часто приходит из JSON, необязательных полей или union без сужения на hot path.

## Общие сущности в глобальной / модульной области

**Глобальная / модульная область** здесь — не «всё в `window`», а **один раз объявленный** конструктор, фабрика или обработчик, который живёт столько же, сколько модуль, и не пересоздаётся в цикле.

Хорошо:

```js
// models/point.js — один раз на модуль
function Point(x, y) {
  this.x = x;
  this.y = y;
}

function sumXY(p) {
  return p.x + p.y;
}

export { Point, sumXY };
```

Плохо на hot path:

```js
let acc = 0;
for (let i = 0; i < n; i++) {
  function sumXY(p) {
    return p.x + p.y;
  } // ← новая функция каждую итерацию
  acc += sumXY({ x: i, y: i + 1 });
}
```

Один и тот же **исходный текст** `sumXY` внутри цикла каждый раз даёт **новую функцию** в рантайме — профиль и IC не «приклеиваются» к одному call site так же надёжно, как у объявления на уровне модуля.

## Практика

1. Пишите ясный код; не оптимизируйте «на глаз».
2. Найдите hot path в профиле.
3. Если узкое место — упростите shapes, типы аргументов и вынесите горячие функции из циклов.
4. Перепроверьте профилем после правки.
