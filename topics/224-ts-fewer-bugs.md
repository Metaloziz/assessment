# 1. Тема

**Как типизация приводит к уменьшению багов**

---

# 2. Главное в одну фразу

Статические типы ловят рассинхрон контрактов на этапе сборки — до того, как ошибка дойдёт до пользователя в рантайме.

---

# 3. Суть

> Типизация уменьшает класс багов, которые видны статически: передали не то поле, забыли обработать `null`, переименовали ключ в одном месте и не в другом. Checker сравнивает объявленные типы с фактическим использованием и останавливает сборку или подсветку в IDE.
>
> На практике это ускоряет безопасный рефакторинг: смена сигнатуры функции сразу подсвечивает все сломанные вызовы. Особенно полезно на стыках модулей — форма ответа API, props компонента, общая модель домена.
>
> Механизм простой: у значения есть тип; операция допустима, только если типы совместимы. Несовместимость — ошибка компиляции, а не «undefined is not a function» через неделю.
>
> Ловушка: типы не заменяют тесты и не ловят логические ошибки («скидка −10% вместо −10 пунктов»). `any`, лишние `as` и отключённый `strict` сужают пользу почти до нуля.

---

# 4. Самое главное запомнить

- Ошибки типов — на этапе check/build; многие «рантайм-сюрпризы» отсекаются раньше.
- Рефакторинг сигнатур и полей безопаснее: checker находит все места использования.
- `strictNullChecks` / `strict` ловят пропуски `null` и `undefined`.
- Типы не доказывают корректность бизнес-логики — нужны тесты и валидация входа.
- `any` и необоснованные assertion’ы отключают защиту точечно или массово.
- Внешние данные (JSON, query) типизируют после проверки, а не «вслепую» через `as`.

---

# 5. Описание

```text
правка кода
  → type checker
      ├─ ок  → дальше сборка / рантайм
      └─ ошибка типа → правка до merge / до клика в UI
```

## Какие баги отсекает типизация

| Класс проблемы | Пример без типов | Что делает TS |
|---|---|---|
| Неверный аргумент | `sum("1", 2)` → `"12"` | ошибка: нужен `number` |
| Нет поля | `user.nmae` → `undefined` | ошибка: нет свойства |
| `null` / `undefined` | вызов метода на пустом | при `strict` — явная проверка |
| Смена контракта | переименовали `id` → `userId` | все старые обращения красные |

Короткий контраст:

```ts
type User = { id: string; name: string };

function label(u: User) {
  return u.name.toUpperCase();
}

// label({ id: "1" }); // ошибка: нет name
// label(null);        // ошибка при strictNullChecks
```

Без типов оба вызова могли бы «молча» дойти до рантайма и упасть или дать странный UI.

## Рефакторинг и границы модулей

Когда форма `User` меняется, TS проходит по всем импортам и подсвечивает несовместимости. Это дешевле, чем ловить рассинхрон только e2e: ошибка локальна и с текстом «какое поле / какой тип ожидался».

На стыке с сетью типы описывают *ожидаемую* форму после парсинга. Сам HTTP не знает про `User` — сначала validate, потом узкий тип:

```ts
// плохо: доверяем сети
const user = (await res.json()) as User;

// лучше: проверить shape, затем работать с User
```

## Что типизация не закрывает

- Неверная формула, неверный порядок шагов, гонка в async.
- Ошибки конфигурации окружения и инфраструктуры.
- Баги в коде, намеренно выведенном из-под проверки (`any`, `@ts-ignore`).

Поэтому unit/integration-тесты и runtime-валидация остаются частью защиты; типы — ранний и дешёвый слой именно для формы данных и вызовов.
