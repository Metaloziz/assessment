# 1. Тема

**Fetch advanced. Есть ли разница с XMLHttpRequest**

---

# 2. Главное в одну фразу

`fetch` и `XMLHttpRequest` оба спрашивают сервер по HTTP, но по-разному сообщают вам: «ответ пришёл», «страницы нет» или «запрос оборвался».

---

# 3. Суть

> Представьте два пульта к одному телевизору. **`fetch`** и **`XMLHttpRequest`** (коротко XHR) — два таких пульта для запросов из JavaScript. Кнопка одна и та же: «спроси сервер». Меняется не сеть, а то, **как код узнаёт результат**.
>
> Зачем это знать. Если переписать старый XHR на `fetch` «один в один», легко пропустить ошибку. У `fetch` ответ «страницы нет» (код 404) часто **не** выглядит как исключение: промис уже «успешно» завершился, а внутри ответа написано, что всё плохо. Нужно самому глянуть `response.ok` или `status`.
>
> Как устроено. `fetch` отдаёт промис и объект ответа: сначала «письмо пришло», потом отдельно читают текст или JSON. XHR работает через события: «загрузка закончилась», «сеть упала», «отменили». Отменить запрос тоже можно у обоих, но кнопки разные: у `fetch` — `AbortController`, у XHR — метод `abort()`.
>
> Ловушка: думать, что «промис не упал» = «сервер всё отдал как надо». У `fetch` это часто не так. Новый код обычно пишут на `fetch`; XHR остаётся в старых проектах и там, где удобнее смотреть прогресс загрузки файла.

---

# 4. Самое главное запомнить

- Оба делают один и тот же тип работы: HTTP-запрос из браузера.
- Разница — в том, **как** вам отдают ответ и ошибку, а не в «другой сети».
- У XHR нет промисов «из коробки»: объект + события (`onload`), данные в полях `status` / `responseText`.
- У `fetch` сигнал «готово» — это resolve промиса и объект `Response`, не событие `load`.
- У `fetch` код 404/500 обычно **не** кидает исключение — смотрите `ok` или `status`.
- Тело ответа у `fetch` читают отдельно (`json()`, `text()`) и обычно один раз.
- Отмена: `AbortController` у `fetch`, `abort()` у XHR.
- Для нового кода берите `fetch`; XHR — легаси или удобный прогресс отправки файла.

# 5. Описание

```text
ваш код ──► fetch или XHR ──► браузер ──► сервер
                 │
                 ▼
        «как сообщили результат»
        fetch:  resolve промиса → объект Response
        XHR:    событие load на объекте → вызов onload
```

## Одна задача — два стиля

Серверу всё равно, чем вы пользуетесь. Он получает обычный HTTP-запрос. Разница на стороне JavaScript.

**`fetch`** удобен с `async`/`await`: написали «подожди ответ», потом разобрали JSON.

**XHR** старше: создаёте объект, вешаете обработчики, вызываете `send()`. Так писали до широкого распространения промисов.

В DevTools → **Network** оба запроса видны; в колонке **Type** часто будет `fetch` или `xhr`. До сервера уходит один и тот же HTTP — отличается только API в вашем коде.

## Как браузер сообщает: событие vs промис

Сеть в обоих случаях делает браузер: ваш код не «висит», пока идёт запрос. Меняется только сигнал «готово».

### XHR: объект и событие `load`

У XHR **нет промисов** в самом API. `new XMLHttpRequest()` возвращает обычный объект. Вы заранее вешаете на него функцию — «когда ответ будет, вызови вот это»:

```js
const xhr = new XMLHttpRequest();

xhr.onload = () => {
  // браузер сам вызовет это, когда ответ уже пришёл
  console.log(xhr.status, xhr.responseText);
};

xhr.open('GET', '/api/demo/echo');
xhr.send(); // ← только тут запрос реально уходит
```

По шагам:

1. Создали объект.
2. Записали в `onload` (при желании ещё `onerror` / `onabort`) обработчик — это подписка, а не «событие уже летит».
3. `open` + `send` — браузер идёт в сеть.
4. Когда ответ готов, браузер вызывает ваш `onload` и кладёт данные в поля **того же** объекта: `status`, `responseText` и т.д.

Событие не «отправляется в функцию посылкой». Объект получает событие `load`, и срабатывает обработчик, который вы повесили заранее.

### `fetch`: промис, не `onload`

С `fetch` браузер **не** шлёт вам событие `load` на объект запроса. Он «стучится» через **промис**:

```js
const promise = fetch('/api/demo/echo'); // сразу Promise, сеть уже идёт

const res = await promise; // ← промис resolve, когда ответ (заголовки) готов
const data = await res.json(); // ← ещё одно ожидание: дочитать тело
```

| | XHR | `fetch` |
| --- | --- | --- |
| Что создаёте | объект `XMLHttpRequest` | промис |
| Как подписаться | `xhr.onload = …` | `await` / `.then(…)` |
| Когда «готово» | браузер вызывает `onload` | браузер **resolve**’ит промис |
| Где лежат данные | поля `xhr.status`, `xhr.responseText` | объект `Response`: `res.status`, потом `res.json()` |

Одно и то же снизу (браузер + HTTP), разные способы сказать коду «можно продолжать».

Можно обернуть XHR в промис вручную — но сам API про события и колбэки, не про `Promise`.

## Главная ловушка `fetch`: «ответ есть» ≠ «всё хорошо»

Сервер может ответить: «такой страницы нет» (404) или «у меня ошибка» (500). Для `fetch` это часто **нормальный** конец промиса: письмо доставили. В письме просто плохие новости.

```js
const res = await fetch('/api/user/999');

// промис уже «ок», но страницы может не быть
if (!res.ok) {
  throw new Error(`Сервер ответил ${res.status}`);
}

const data = await res.json();
```

У XHR статус смотрят в обработчике `onload`: событие «загрузка закончилась» тоже приходит и при 404 — число статуса проверяете сами.

Настоящее исключение у `fetch` чаще бывает, когда **вообще не достучались**: нет сети, CORS запретил, запрос отменили.

## Отмена запроса

Иногда пользователь ушёл со страницы, и ответ уже не нужен.

- `fetch`: создаёте `AbortController`, передаёте `signal` в запрос, потом `abort()`.
- XHR: вызываете `xhr.abort()`.

Смысл один — «стоп», синтаксис разный.

## Когда ещё вспоминают XHR

Нужен простой прогресс «файл улетел на 30% / 70%» — у XHR это привычнее. В новом коде без такой полоски почти всегда хватает `fetch`.

## Короткая шпаргалка

| Вопрос | `fetch` | XHR |
| --- | --- | --- |
| Как ждут результат | промис | события |
| 404 / 500 | часто без исключения, смотрите `ok` | смотрите `status` в `onload` |
| Нет сети | обычно исключение | событие `error` |
| Отмена | `AbortController` | `abort()` |
