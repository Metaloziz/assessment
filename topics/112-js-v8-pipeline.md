# 1. Тема

**Процесс обработки кода в V8: AST, Предварительный и полный лексический анализ, Just-in-time, Компиляция, интерпретация, Деоптимизация скомпилированного кода**

---

# 2. Главное в одну фразу

V8 разбирает исходный текст до AST, быстро исполняет байткод интерпретатором и JIT-компилирует горячий код, а при ложных предположениях откатывает оптимизацию (deopt), не ломая семантику.

---

# 3. Суть

> Процесс обработки кода в V8 — это конвейер: исходный JavaScript превращают в токены и дерево синтаксиса (AST), затем в байткод, который сначала интерпретируют, а горячие участки при необходимости компилируют в машинный код.
>
> Так двигатель быстрее стартует и не тратит время на полную компиляцию всего файла. Оптимизация опирается на то, какие типы и формы объектов реально встретились в рантайме.
>
> Если предположение ломается — например, в «числовую» функцию пришла строка — оптимизированный код деоптимизируют и продолжают более общим путём. Это штатный механизм корректности, а не падение приложения.

---

# 4. Самое главное запомнить

- Лексический анализ режет текст на токены; парсер строит AST — структуру программы, не машинный код.
- Pre-parser (предварительный разбор) экономит работу на лениво исполняемых функциях; полный разбор делают, когда код реально нужен.
- Интерпретация байткода (Ignition) даёт быстрый старт; компиляция (TurboFan) ускоряет горячее.
- JIT = интерпретация + профилирование + компиляция «на лету», а не «сразу весь файл в машинный код».
- Компиляция опускает код «ниже» (байткод / машинный); транспиляция — исходник в другой исходник (TS → JS); интерполяция — подстановка значений в строку (`${…}`), не этап сборки.
- Деоптимизация откатывает спекулятивный код к безопасному пути; программа остаётся корректной.
- Пороги «N вызовов» и эвристики меняются — выводы проверяют профилем, а не угадывают.

---

# 5. Описание

```text
исходник
  → лексический анализ (токены)
  → парсер → AST
  → генерация байткода
  → Ignition (интерпретация) + сбор профиля
  → TurboFan (JIT-компиляция горячего)
  → при сломе допущений → deopt → снова общий / интерпретируемый путь
```

## Предварительный и полный лексический / синтаксический разбор

**Лексический анализ** (scanner / tokenizer) идёт по символам исходника и выдаёт токены: `function`, имя, `(`, `)`, `{` и т.д. Это ещё не «смысл программы», а поток лексем.

Исходник:

```js
const x = 1 + 2;
```

Примерный вид **токенов** (упрощённо; в движке у каждого токена ещё тип, значение и позиция в файле):

```text
Keyword(const)  Identifier(x)  Punctuator(=)
Literal(1)  Punctuator(+)  Literal(2)  Punctuator(;)
```

Или списком:

```text
[
  { type: "Keyword",    value: "const" },
  { type: "Identifier", value: "x" },
  { type: "Punctuator", value: "=" },
  { type: "Numeric",    value: "1" },
  { type: "Punctuator", value: "+" },
  { type: "Numeric",    value: "2" },
  { type: "Punctuator", value: ";" }
]
```

Пробелы и переносы обычно отбрасывают (или помечают отдельно) — парсеру важна последовательность лексем, а не «как красиво отформатирован файл».

**Парсер** по токенам строит **AST** (Abstract Syntax Tree) — дерево конструкций: объявления, выражения, блоки. AST описывает синтаксис; до машинных инструкций ещё далеко.

В V8 есть разделение труда:

- **Pre-parser (предварительный разбор)** — облегчённый проход: быстро проверяет синтаксис внутренних функций и собирает минимум метаданных, не строя полное «тяжёлое» представление сразу. Так ускоряют загрузку больших скриптов, где много функций ещё не вызывали.
- **Full parse (полный разбор)** — когда функцию реально собираются исполнять (или она нужна целиком), строят полноценное внутреннее представление и готовят байткод.

Практический смысл: «разобрали файл» ≠ «уже скомпилировали в машинный код». Много кода долго живёт как байткод или даже ждёт полного разбора до первого вызова.

## AST

AST — промежуточная структура «как устроен исходник». По нему удобно генерировать байткод, делать проверки и трансформации. AST не путают с байткодом и с машинным кодом: это разные уровни.

Исходник:

```js
const x = 1 + 2;
```

Упрощённое **дерево** (узлы — конструкции языка, листья — имена и литералы):

```text
VariableDeclaration (const)
└── VariableDeclarator
    ├── Identifier: x
    └── BinaryExpression (+)
        ├── Literal: 1
        └── Literal: 2
```

Тот же смысл в виде вложенной структуры (так AST часто показывают в JSON / AST Explorer):

```text
{
  type: "VariableDeclaration",
  kind: "const",
  declarations: [{
    type: "VariableDeclarator",
    id:   { type: "Identifier", name: "x" },
    init: {
      type: "BinaryExpression",
      operator: "+",
      left:  { type: "Literal", value: 1 },
      right: { type: "Literal", value: 2 }
    }
  }]
}
```

Важно: это **не** то, что выполнит процессор. Дальше по AST (или по внутреннему IR) V8 строит байткод; машинный код появится только если участок станет «горячим» и его возьмёт JIT.

Ещё один короткий пример — вызов:

```js
add(1, 2)
```

```text
CallExpression
├── Callee: Identifier "add"
└── Arguments
    ├── Literal: 1
    └── Literal: 2
```

## Компиляция, транспиляция и интерполяция

Три слова звучат похоже, но означают разное. Путать их с этапами V8 не стоит.

**Компиляция** — перевод программы в более низкоуровневое представление, которое ближе к исполнению: байткод, машинный код и т.п. В широком смысле «скомпилировать» = получить исполняемый артефакт, а не просто другой текст на том же уровне.

В V8 компиляция встречается на двух уровнях:

- исходник / AST → **байткод** (то, что потом крутит Ignition);
- горячий байткод → **машинный код** (TurboFan / JIT).

```text
JS → (внутри V8) байткод → (горячее) машинный код
```

**Транспиляция** (transpile = *trans*form + com*pile*) — перевод **исходника в другой исходник**, обычно того же «уровня абстракции»: TypeScript → JavaScript, современный JS → более старый JS (Babel), JSX → `React.createElement`. Результат по-прежнему читаемый (или почти) код для движка или следующего инструмента, а не машинные инструкции процессора.

```text
.ts / JSX / ES2024  →  обычный JS, который поймёт целевой runtime
```

Транспиляция происходит **до** V8 (бандлер, `tsc`, Babel). V8 получает уже JS и дальше сам парсит → байткод → при необходимости JIT. «Babel скомпилировал» в бытовой речи часто значит именно *transpile*, не TurboFan.

**Интерполяция** — не этап пайплайна и не сборка. Это **подстановка значений внутрь строки** (или шаблона) в рантайме:

```js
const name = 'Ann';
const msg = `Hello, ${name}!`; // интерполяция: в слот подставили значение name
```

В template literal `${…}` — выражение вычисляется и вставляется в строку. То же слово бывает у CSS/`styled-components` и у TypeScript template literal types, но смысл тот же: «вставить значение в шаблон», а не «перевести код в байткод».

Кратко:

| Термин | Что делает | Пример |
|--------|------------|--------|
| Компиляция | код → более низкий уровень | JS → байткод / машинный код в V8 |
| Транспиляция | исходник → исходник | TS / JSX → JS до браузера |
| Интерполяция | значение → внутрь строки/шаблона | `` `Hi, ${user}` `` |

## Интерпретация и компиляция в V8

**Интерпретация** в V8 — исполнение **байткода** интерпретатором **Ignition**: инструкция за инструкцией, без долгой подготовки машинного кода. Плюс — быстрый старт и проще собирать профиль (какие типы реально ходят).

**Компиляция** здесь — перевод горячей функции (или её части) оптимизирующим компилятором **TurboFan** в специализированный машинный код под наблюдаемый сценарий: типы аргументов, формы объектов, возможность inline.

Это не взаимоисключение: типичный путь — сначала интерпретация, потом выборочная компиляция.

## Just-in-time (JIT)

**JIT** — компиляция во время выполнения, а не заранее «весь бандл в .exe». В V8 цикл такой:

1. Быстро получить исполняемый байткод.
2. Пока код крутится, копить статистику.
3. Для горячих мест скомпилировать ускоренную версию.
4. Если допущения устарели — deopt и снова более общий путь (иногда с повторной оптимизацией позже).

JIT выгоднее там, где один и тот же путь выполняется много раз с похожими данными. На «по одному разу с разными типами» выигрыш меньше, а цена спекуляции выше.

## Деоптимизация скомпилированного кода

**Деоптимизация (deopt)** — отказ от текущего оптимизированного машинного кода, когда нарушено условие, на котором он строился: сменился тип, другая hidden class / форма объекта, редкая ветка и т.п.

```js
function add(a, b) {
  return a + b;
}

for (let i = 0; i < 10_000; i++) add(1, 2); // узкий числовой профиль
add('1', '2'); // другой тип — повод уйти с узкого оптимизированного пути
```

Deopt не означает «V8 сломался»: семантика JavaScript сохраняется, просто временно (или дольше) исполняется более общий вариант. В профилировщике иногда видно всплески deopt; чинят предсказуемостью горячего кода и измерением, а не ручным «запретом GC» или магическим числом итераций.

Нельзя опираться на конкретный порог «после N вызовов всегда TurboFan»: пороги и эвристики зависят от версии V8. Имеет смысл: стабильные типы и формы в горячих местах + проверка Performance / профилировщиком.
