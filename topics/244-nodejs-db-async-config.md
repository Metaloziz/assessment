# 1. Тема

**SQL и NoSQL, асинхронность, конфиги сред**

---

# 2. Главное в одну фразу

Сервер на Node не хранит все данные у себя в памяти — он читает их из базы по сети, не блокируя при этом остальные запросы, а адрес и пароль базы берёт из настроек среды, а не из исходного кода.

---

# 3. Суть

> Представьте интернет-магазин: список товаров, заказы и пользователи не лежат внутри одного файла `server.js`. Они живут в **базе данных** — отдельной программе, к которой сервер обращается по сети. **SQL-базы** (Postgres, MySQL) хранят данные в **таблицах** — как листы с колонками и строками, заранее согласованной схемой. **NoSQL** (MongoDB, Redis) часто ближе к JSON-документу или паре «ключ → значение» — форма гибче, но другие правила связей и проверок.
>
> Зачем разделять: когда много связанных сущностей (клиент → заказы → позиции) и нужны отчёты «собери всё вместе», удобнее SQL с таблицами и связями. Когда нужен быстрый кэш, гибкий документ профиля или счётчик — часто берут NoSQL или Redis. Плохой выбор — не «SQL устарел», а когда модель не подходит под задачу.
>
> Как это выглядит в Node: обработчик запроса не «замирает» на секунду, пока база думает. Он пишет `await pool.query(...)` или `await collection.findOne(...)` — **отдаёт управление**, сервер принимает другие запросы, а когда база ответила — продолжает. Подключение к базе настраивают через переменные окружения (`process.env.DATABASE_URL`): на ноутбуке одна база, на проде — другая, пароль не пишут в git.
>
> Ловушки для новичка: ждать базу **синхронно** — тогда один тяжёлый запрос тормозит весь сервер. И второе — захардкодить prod-пароль в коде или использовать один URL базы и для разработки, и для боевого окружения. Операции create/update/delete и кэш — в следующей теме; здесь — **где лежат данные**, **как ждать ответ** и **откуда брать настройки**.

---

# 4. Самое главное запомнить

- Данные приложения обычно **вне процесса Node** — в SQL или NoSQL, доступ по сети.
- SQL — таблицы и заранее известные колонки; NoSQL — чаще документ или ключ-значение, не «замена SQL навсегда».
- Три связи в SQL: **один к одному**, **один ко многим**, **многие ко многим** (последняя — через связующую таблицу).
- К базе ходят **асинхронно** через `await` и **пул** соединений — слот заняли, вернули, сервер не стоит.
- `DATABASE_URL`, пароли и ключи — из `process.env` / секретов платформы, не из репозитория; на dev и prod **разные значения**, `NODE_ENV` URL базы не подменяет.
- В запросах значения подставляют через плейсхолдеры (`$1`), а не склеивают строку из ввода пользователя.

# 5. Описание

```text
  запрос ──► обработчик ──await──► пул / клиент ──► SQL или NoSQL
                 │                        ▲
                 │                        │
                 └── читает настройки ◄───┘
                       process.env / .env
                       (dev ≠ prod)
```

## Зачем серверу база данных

Node-процесс может держать в памяти немного данных, но каталог на тысячи товаров, история заказов и пароли пользователей так не масштабируются. База данных — отдельный сервис: вы отправляете ей запрос («дай пользователя с id 5»), она отвечает строкой или документом.

В коде это выглядит как вызов драйвера (`pg`, `mysql2`, MongoDB client). Драйвер ходит по сети к Postgres или MongoDB — это **медленнее**, чем чтение из переменной, зато данные переживают перезапуск сервера и доступны нескольким инстансам приложения.

## SQL и NoSQL — две разные «формы полки»

| | SQL (Postgres, MySQL…) | NoSQL (частый случай) |
| --- | --- | --- |
| Как лежит | таблицы: колонки и строки | документ JSON, или `key → value` |
| Схема | колонки задают заранее | форма может меняться от записи к записи |
| Связи | таблицы связаны, запросы через `JOIN` | вложенный массив в документе или отдельная коллекция |
| Удобно когда | заказы, отчёты, строгие правила «нет клиента — нет заказа» | профиль с разными полями, кэш, счётчики |

**SQL** — как несколько связанных таблиц в Excel: у `users` колонки `id`, `email`; у `orders` — `id`, `user_id`, `total`. База знает типы и может запретить бессмысленные данные.

**NoSQL (документы)** — ближе к одному JSON-объекту на запись: `{ "_id": "...", "email": "...", "tags": ["vip"] }`. Удобно, когда структура «плывёт», но связи между сущностями чаще контролирует приложение, а не сама БД.

В Node оба варианта вызывают одинаково с точки зрения синтаксиса — через `async/await`:

```js
// SQL: таблица users, строка по id
const { rows } = await pool.query(
  'SELECT id, email FROM users WHERE id = $1', // ← $1 — место для значения, не склейка строк
  [userId],
);
```

```js
// документ MongoDB: один объект пользователя
const user = await db.collection('users').findOne({ _id: userId });
```

Один проект может использовать **и Postgres, и Redis**: Postgres — «источник правды» для заказов, Redis — быстрый кэш. Это не «или-или», а разные роли. Подробнее про кэш и CRUD — следующая тема.

## Типы связей в SQL

В SQL данные почти всегда разбиты на несколько таблиц. **Связь** отвечает на вопрос: «одной строке здесь сколько строк там соответствует?»

| Связь | Словами | Пример | Как хранят |
| --- | --- | --- | --- |
| **1:1** | один к одному | у человека один паспорт профиля | таблица `profiles`, у каждого `user_id` только один раз |
| **1:N** | один ко многим | у клиента много заказов | в `orders` колонка `customer_id` ссылается на клиента |
| **M:N** | многие ко многим | студент на многих курсах, на курсе много студентов | таблица `enrollments` с `student_id` и `course_id` |

```text
  1:1                    1:N                         M:N
  users ── profile       customers ──► orders        students ◄── enrollments ──► courses
```

**Внешний ключ** (`FOREIGN KEY`) — колонка в «дочерней» таблице, которая указывает на `id` в «родительской». База не даст сохранить заказ с `customer_id = 999`, если клиента 999 не существует. Для новичка это главное преимущество SQL: правила связей живут в самой базе.

Чаще всего в API встречается **один ко многим** — пользователь и его посты, категория и товары:

```sql
CREATE TABLE orders (
  id serial PRIMARY KEY,
  customer_id integer NOT NULL REFERENCES customers(id),
  total numeric NOT NULL
);

SELECT id, total FROM orders WHERE customer_id = 42;
```

**Один к одному** — когда тяжёлые или редкие поля выносят отдельно (био, настройки), но строго одна запись на пользователя. На `user_id` в `profiles` вешают `UNIQUE`.

**Многие ко многим** без третьей таблицы не описать: иначе пришлось бы копировать списки курсов в каждого студента и наоборот. Связующая таблица хранит только пары id.

В Node связанные данные читают запросом с `JOIN` или двумя шагами: сначала пользователь, потом `SELECT … WHERE user_id = $1`. ORM (Prisma, Drizzle) пишет SQL за вас, но мыслить всё равно удобно парами «один ко многим» / «многие ко многим».

В NoSQL ту же идею часто выражают **вложенным массивом** в документе или ссылками между коллекциями — без `JOIN` в SQL-смысле, зато проще менять форму записи.

## Асинхронность: не блокировать сервер

Node на одном потоке обслуживает много HTTP-запросов. Пока один обработчик **ждёт ответ базы** (сеть, диск на стороне Postgres), другие запросы должны иметь шанс выполниться.

Поэтому пишут `await`, а не «крутить цикл, пока не придёт ответ»:

```js
import pg from 'pg';

const pool = new pg.Pool({ connectionString: process.env.DATABASE_URL }); // ← пул соединений

export async function getUser(id) {
  const { rows } = await pool.query('SELECT * FROM users WHERE id = $1', [id]); // ← await: ждём БД, но не блокируем весь процесс
  return rows[0] ?? null;
}
```

**Пул** (`pg.Pool`) — несколько заранее открытых соединений к базе. Каждый запрос берёт свободное, делает работу, возвращает обратно. Без пула на каждый запрос открывали бы новое соединение — медленно и тяжело для базы.

Плохо для новичка: синхронные драйверы или долгий расчёт (хеш файла на 2 секунды) прямо в обработчике — пока он работает, очередь запросов стоит. Тяжёлую CPU-работу выносят в worker threads (отдельная тема); **ожидание базы** — это нормальный async I/O через `await`.

## Конфиги сред: dev и prod — разные настройки

Один и тот же код выкладывают на ноутбук, тестовый стенд и продакшен. База на ноутбуке — `localhost`, на проде — другой хост и другой пароль. Писать это в коде нельзя: секрет попадёт в git, а на prod случайно подключатся к dev-базе.

Настройки читают из **окружения** — переменных вроде `DATABASE_URL`, `PORT`, `NODE_ENV`:

```text
  локально (.env)     DATABASE_URL=postgres://localhost:5432/shop_dev
  на сервере          DATABASE_URL=postgres://***:***@db.prod/shop
```

```js
export const config = {
  port: Number(process.env.PORT ?? 3000),
  databaseUrl: process.env.DATABASE_URL, // ← адрес базы из среды
  nodeEnv: process.env.NODE_ENV ?? 'development',
};

if (!config.databaseUrl) {
  throw new Error('DATABASE_URL is required'); // ← лучше упасть при старте, чем молча ломаться
}
```

Локально часто кладут переменные в файл `.env` (пакет `dotenv` или встроенная загрузка в новых версиях Node). Файл `.env` с паролями **добавляют в `.gitignore`**. На проде те же имена переменных задают в панели хостинга или секрет-хранилище.

`NODE_ENV=production` говорит приложению «режим боя» (меньше логов, другие оптимизации), но **URL базы всё равно задают явно** — одной этой переменной мало.

## Граница с соседними темами

- **Рутинг и статика** — как сервер принимает HTTP; здесь — что происходит после того, как запрос попал в обработчик и нужны данные извне.
- **Кеширование. Подключение баз данных к серверу, CRUD** — следующая тема: как создавать, читать, обновлять и удалять записи и когда класть результат в кэш.
- **Worker threads** — для тяжёлых вычислений на CPU, не вместо async-обращений к базе.
