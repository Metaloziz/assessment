# 1. Тема

**Метрики серверной производительности**

---

# 2. Главное в одну фразу

Серверные метрики показывают, как backend обрабатывает нагрузку: время ответа, пропускную способность, ошибки и расход CPU/памяти — и отделяют медленный API от «тяжёлого» фронта.

---

# 3. Суть

> **Метрики серверной производительности** — измеримые сигналы о том, как API и инфраструктура отвечают на запросы: сколько миллисекунд уходит на обработку, сколько успешных запросов в секунду выдерживает сервис, какая доля ответов — ошибки, хватает ли CPU и памяти. Это не UX в браузере (LCP, INP) и не размер бандла — это слой backend и сети до клиента.
>
> Зачем смотреть: рост **latency** (особенно p95/p99) и **error rate** часто предшествует жалобам; высокий **TTFB** на фронте нередко означает медленный или перегруженный API, а не «тяжёлый React». Без серверных метрик оптимизируют не то.
>
> Как собирают: APM и экспортеры (Prometheus, Datadog) считают гистограммы latency, `rate()` по счётчикам 5xx, RPS по route; нагрузочные тесты (k6, Locust) дают прогноз до продакшена. Время ответа включает маршрутизацию, бизнес-логику и запросы к БД — не только «сеть до сервера».
>
> Ловушка: среднее latency скрывает хвост; один медленный эндпоинт или N+1 в SQL бьёт по p99. RPS растёт, пока CPU/память и пул БД не упрутся в потолок — throughput без ресурсов не бесконечен.

---

# 4. Самое главное запомнить

- **Latency** — время обработки запроса на сервере (логика + БД + очереди); смотрят **p50** (медиана), **p95** и **p99** (хвост), не только среднее.
- **Throughput (RPS)** — успешные запросы в секунду при заданной нагрузке.
- **Error rate** — доля 4xx/5xx; рост часто коррелирует с деградацией latency.
- **Resource usage** — CPU, memory, disk I/O, connections к БД — узкое место до «бесконечного» RPS.
- **Uptime / availability** — доля времени, когда сервис отвечает на проверки.
- Высокий **TTFB** в браузере часто указывает на backend, не на клиентские метрики.
- APM + метрики + нагрузочные тесты дополняют друг друга; один `console.time` в хендлере — не мониторинг.

# 5. Описание

```text
клиент ──HTTP──► API gateway / сервер
                      │
          ┌───────────┼───────────┐
          ▼           ▼           ▼
      handler      БД / cache    внешние API
          │           │           │
          └───────────┴───────────┘
                      │
              метрики: latency, RPS, 5xx, CPU/RAM
```

## Latency (время ответа)

Серверное время — от приёма запроса до отправки ответа. Включает парсинг тела, авторизацию, SQL, сериализацию JSON. Одного «среднего» числа мало: часть запросов может быть в разы медленнее остальных — смотрят **процентили** p50, p95, p99.

Контраст на стенде: handler без задержки (память) vs искусственная пауза в коде vs реальный `SELECT` в Postgres.

## p50, p95, p99 — процентили задержки

**Процентиль** — граница в отсортированном списке всех замеров latency за период. Не «среднее арифметическое», а «как быстро отвечаем у большинства и у самых медленных».

| Метрика | Смысл |
|--------|--------|
| **p50** | Половина запросов **быстрее** этого значения, половина — медленнее. Медиана, «типичный» ответ. |
| **p95** | 95% запросов быстрее, **5%** — медленнее. Часто алертят именно его: хвост уже заметен. |
| **p99** | 99% быстрее, **1%** — медленнее. Самые тяжёлые запросы: cold cache, N+1 в SQL, GC, очередь на сервере. |

**Зачем не среднее.** Допустим, 99 запросов по 50 ms и один — 5 000 ms. Среднее ≈ 100 ms — «вроде нормально». **p95** ≈ 50 ms, **p99** ≈ 5 000 ms — видно, что **1%** пользователей попадает в провал. Среднее маскирует такие хвосты; в SRE и APM поэтому смотрят p95/p99, а не только avg.

**p50 низкий, p99 высокий** — сервис в целом быстрый, но иногда кто-то упирается в баг, перегруз или медленный SQL. Это как раз то, что среднее часто прячет.

В Prometheus latency кладут в **гистограмму** (`Histogram` с buckets в секундах); Grafana или PromQL (`histogram_quantile(0.95, …)`) считают p95/p99 по route и status. В лабе p50/p95 считаются по client round-trip после пачки запросов — та же идея, другой срез (браузер + сеть + сервер).

## Throughput (RPS)

**Requests per second** — сколько запросов сервис стабильно обрабатывает при заданной concurrency. При росте нагрузки latency сначала ползёт вверх, потом растёт error rate (таймауты, 503).

## Error rate и доступность

Считают `rate(http_requests_total{status=~"5.."}[5m])` или аналог в APM. **Uptime** — доля успешных health-check'ов за период. Один всплеск 5xx на фоне низкой latency — баг в коде; 5xx + высокий latency — перегруз или БД.

## Ресурсы и связь с фронтом

CPU на 90%, исчерпанный пул Postgres, swap — типичные потолки до «масштабирования кодом». В **проде** CPU/RAM/disk смотрят через **node_exporter**, cAdvisor или дашборд облака (USE method), не через один HTTP-ответ.

В **Node** handler может отдать срез **своего процесса**: `process.memoryUsage()` (heap, rss) и дельту `process.cpuUsage()` до/после работы — полезно для утечек памяти и тяжёлых sync-участков. Это не «загрузка CPU всего сервера в %»; на стенде лёгкий vs тяжёлый handler показывает рост `cpuMs` и `heapDeltaMb` в JSON.

На клиенте **TTFB** (Time to First Byte) включает сеть + очередь на сервере + первый байт ответа — полезный мост к теме клиентских метрик.

## Что не путать

| Сигнал | Вопрос |
|--------|--------|
| Server latency | Как долго backend обрабатывал запрос? |
| TTFB (браузер) | Когда пришёл первый байт HTML/API? |
| LCP / INP | Как быстро пользователь видит и кликает UI? |
