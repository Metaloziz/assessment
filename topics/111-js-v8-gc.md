# 1. Тема

**Сборщик мусора V8**

---

# 2. Главное в одну фразу

V8 освобождает неиспользуемую память по достижимости объектов от корней, а не по счётчику «нужности».

---

# 3. Суть

> Сборщик мусора V8 освобождает объект, когда до него больше нельзя дойти от корней: стека, глобальных ссылок и активных контекстов. Он не знает бизнес-смысл данных и не удаляет объект только потому, что тот «уже не нужен».
>
> Это важно для долгоживущих приложений: безлимитный кэш, обработчик события или таймер могут удерживать большие данные и превращаться в утечку. Частые временные объекты также увеличивают нагрузку на память и паузы.
>
> V8 быстро собирает большинство объектов в молодом поколении, а пережившие несколько сборок переносит в старое, где работа дороже. Сначала движок помечает достижимые объекты, затем очищает память и при необходимости уплотняет её. Момент сборки не гарантирован, поэтому исправляют удерживаемые ссылки, а не пытаются вручную вызвать GC.

---

# 4. Самое главное запомнить

- Недостижимый объект может быть удалён, но момент сборки не определён.
- Minor GC обслуживает young generation; major GC маркирует и очищает старое поколение.
- Mark находит живые объекты, sweep освобождает мусор, compaction уменьшает фрагментацию.
- V8 выполняет часть работы инкрементально и конкурентно, но паузы возможны.
- Главные причины утечек — удерживаемые ссылки: безлимитные кэши, listeners, таймеры, замыкания.
- GC pressure — темп появления мусора; смотрят в Performance (паузы GC), Memory / `--trace-gc`, а чинят аллокации и ссылки.

---

# 5. Описание

```js
let session = { payload: new Array(1_000_000) };
session = null; // объект стал кандидатом на сборку
```

Сборщик запускается по давлению памяти и эвристикам, а не «каждые N секунд». Создание массы временных объектов повышает **GC pressure**; долгоживущий `Map` без лимита удерживает данные независимо от того, нужны ли они бизнес-логике.

**GC pressure** — нагрузка на сборщик из‑за того, *как быстро и сколько* мусора появляется. Это не «сколько байт в heap сейчас», а темп: много короткоживущих объектов → чаще minor GC; объекты, которые переживают young generation и копятся в old → тяжелее major GC и длиннее паузы. Осмысливать можно так: «мы создаём мусор быстрее, чем движок спокойно успевает его убирать» — UI подлагивает, FPS проседает, в Performance видны частые/длинные задачи Garbage Collection.

Как измерить или хотя бы увидеть:

- **Chrome DevTools → Performance**: запись сценария; в таймлайне ищут полосы/события GC, смотрят частоту и длительность пауз рядом с Main thread.
- **Memory**: heap snapshot до/после действия (рост удерживаемой памяти); Allocation instrumentation / sampling — какие аллокации сыплются во время лагов.
- **Performance monitor** (More tools): живой график JS heap — пила «вырос → GC сжал» при высоком pressure дёргается чаще.
- **Node.js**: флаги вроде `--trace-gc` / `--trace-gc-verbose` — в логе видно minor/major, сколько собрали и сколько заняло времени. Сравнивают до и после правки аллокаций.
- В коде браузера иногда смотрят `performance.memory` (не стандарт, не везде) — грубый ориентир по usedJSHeapSize, не замена трейсу GC.

Снижают pressure не «вызовом GC», а меньшим числом временных объектов в горячих путях (меньше лишних аллокаций в циклах/рендере) и отпусканием долгоживущих ссылок (кэши с TTL/LRU, снятие listeners).

```js
const cache = new Map();

function remember(key, value) {
  cache.set(key, value); // нужен TTL, LRU или явная очистка
}
```

**TTL** (Time To Live) — время жизни записи в кэше. Вместе с значением хранят срок годности (например, «живёт 5 минут»). При чтении или по таймеру просроченные ключи удаляют, и ссылки на данные отпускаются — иначе запись может висеть часами, хотя бизнес уже не использует её.

**LRU** (Least Recently Used) — политика вытеснения при лимите размера: когда кэш полон, удаляют запись, к которой дольше всего не обращались. Так в памяти остаются «горячие» данные, а забытые ключи не раздувают heap бесконечно. Часто комбинируют с TTL: и срок, и потолок по числу записей.

Без TTL/LRU (или явного `cache.clear` / `delete`) `Map` держит все значения достижимыми — для GC это не мусор, даже если пользователю они уже не нужны.

Для диагностики утечек в браузере сравнивают heap snapshots до и после сценария, ищут retaining paths. Оптимизацию начинают с измерения (Performance / Memory / `--trace-gc`), а не с ручного «вызова GC».
