# 1. Тема

**APO — избегание преждевременной оптимизации**

---

# 2. Главное в одну фразу

Сначала корректный и понятный код под реальные требования; ускорять **после** измерений — только тот участок, который профиль показывает как узкое место.

---

# 3. Суть

> **APO (Avoid Premature Optimization)** — сознательный отказ ускорять код «на глаз», пока нет доказательств, что именно этот участок съедает время или бюджет. Преждевременная оптимизация — это не «никогда не оптимизировать», а **не платить сложностью до того, как известен hotspot**.
>
> На практике порядок такой: сделать работающее решение с ясной структурой, зафиксировать SLA или симптом («страница > 3 с», «CPU 90%»), **профилировать** (DevTools Performance, flame graph, метрики бэкенда), найти 3–5% кода, где копится большая часть времени, и точечно улучшить только его.
>
> Угадывание hotspot'а почти всегда промахивается: оптимизируют сортировку на 200 строк, а 88% времени уходит в сеть; или вводят кэш там, где тормозит сериализация. Сложный «быстрый» код без профиля усложняет ревью, тесты и следующие фичи — выигрыш часто нулевой.
>
> Граница: когда SLA нарушен и профиль уже показал виновника — оптимизация **не** преждевременна. Когда требования ещё плавают — даже «умный» микро-патч может устареть до релиза. Цена APO — терпимая скорость на старте; цена нарушения APO — лишняя сложность и работа не там.

---

# 4. Самое главное запомнить

- **Профиль → hotspot → патч**, а не «я знаю, что тут медленно».
- Читаемость и корректность важнее микро-выигрыша без измерений.
- У Knuth: ~97% времени не в «мелких эффективностях»; критические 3% не стоит пропускать **после** измерения.
- Преждевременная оптимизация = сложность **до** доказательства пользы.
- Один профильный прогон дешевле недели «оптимизации» не того слоя.
- Оптимизация под нестабильные требования часто выбрасывается при следующем рефакторинге.

| | Преждевременно | Обоснованно |
|--|----------------|-------------|
| Когда | «Так быстрее наверняка» | SLA нарушен, профиль есть |
| Что меняют | Слой наугад | Hotspot из flame graph |
| Цена | Сложность, баги | Точечный дифф + регресс-тест |
| Проверка | Ощущения / бенч на синтетике | Prod-like нагрузка + метрики |

---

# 5. Описание

```text
требования + рабочий код
        ↓
   SLA / симптом?
   нет → не трогаем скорость
   да  → профиль (CPU / Network / Memory)
        ↓
   hotspot (узкий % кода / запросов)
        ↓
   точечный патч + замер «до/после»
        ↓
   остановиться, если SLA выполнен
```

## Откуда формулировка

В статье Donald Knuth *Structured Programming with go to Statements* (1974) есть знаменитая фраза: *premature optimization is the root of all evil*. Полный смысл шире: **большую часть времени** не стоит гоняться за микро-эффективностью, но **критический** участок после измерения ускорять нужно. В индустрии это сократили до **APO** — дисциплина «не оптимизировать рано».

## Что считается «преждевременным»

Типичные признаки:

1. **Нет симптома** — страница укладывается в бюджет, а разработчик переписывает цикл «на битовые операции».
2. **Нет профиля** — оптимизируют функцию, которую flame graph не показывает в top-N.
3. **Нестабильный контекст** — API и форматы данных ещё меняются каждую неделю.
4. **Синтетический бенч** — `for (i=0; i<1e7)` на пустом массиве вместо реального сценария пользователя.
5. **Оптимизация читаемости в минус** — inline-кэш, ручной unroll, «умный» пул объектов без доказанной нагрузки.

## Рабочий цикл

1. **Зафиксировать цель**: p95 ответа < 300 ms, LCP < 2.5 s, RPS на инстанс и т.д.
2. **Воспроизвести** на prod-like данных (не на трёх строках в dev).
3. **Профилировать**: Chrome Performance, React Profiler, `node --prof`, APM, `EXPLAIN` для SQL.
4. **Выбрать один hotspot** — часто сеть, N+1 запросы, лишние аллокации, синхронный JSON на большом payload.
5. **Минимальный патч** — кэш, batch, индекс, мемоизация **на горячем пути**, lazy load.
6. **Сравнить до/после** тем же сценарием; если SLA ок — **остановиться**.

## Пример: промах по слою

Список пользователей «тормозит». Без профиля кажется, что виноват `sort()`:

```javascript
// «Оптимизация» без профиля — сложнее, выигрыш ~0
function sortUsers(users) {
  return users.slice().sort((a, b) => {
    const ka = (a.name ?? '').toLowerCase();
    const kb = (b.name ?? '').toLowerCase();
    return ka < kb ? -1 : ka > kb ? 1 : 0;
  });
}

async function loadDashboard() {
  const res = await fetch('/api/users'); // ← 88% времени в Network
  const users = await res.json();
  return sortUsers(users); // ← оптимизировали здесь
}
```

После Performance tab видно: **Network → fetch**. Патч — кэш или pagination на API, а не микро-оптимизация сортировки 200 элементов.

## Когда оптимизация уместна сразу

Не путать APO с архитектурными решениями, которые **дешевле заложить заранее**, но не усложняют код:

- пагинация вместо «отдать 50 000 строк»;
- индекс в схеме БД под известный частый запрос;
- lazy import тяжёлой страницы по маршруту.

Это не «микро-оптимизация наугад», а контракт продукта. Если сомнение — сначала простой вариант + метрика; усложнять, когда профиль подтвердил.

## Связь с рефакторингом

Рефакторинг улучшает **структуру без смены поведения**; APO — про **не менять структуру ради скорости без данных**. Иногда после рефакторинга код уже достаточно быстр — отдельная «оптимизационная» ветка не нужна. Иногда профиль показывает, что после Extract Method hotspot остался — тогда патч локальный и понятный.

## Типичные ловушки

- **Cargo cult**: «в BigTech так делают» — без вашего профиля.
- **Преждевременный кэш**: инвалидация сложнее, чем экономия на miss-free read.
- **Оптимизация cold path**: код, который вызывается раз в час, раздувают «на будущее».
- **Забыть baseline**: нет цифры «до» — нельзя доказать, что патч помог.
