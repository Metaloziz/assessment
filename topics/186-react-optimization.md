# 1. Тема

**Способы оптимизации React-приложения:** лишние рендеры · `memo` / `useMemo` / `useCallback` · `lazy` + `Suspense` · стабильные `key` · Profiler

---

# 2. Главное в одну фразу

Сначала измеряют, где дорого (Profiler / Network), затем режут лишние рендеры (`memo`, стабильные props), откладывают код (`lazy`) и не ломают идентичность списков плохими `key`.

---

# 3. Суть

> Оптимизация React-приложения — это не «обернуть всё в `memo`», а убрать **лишнюю работу**: повторные `render` без смены данных, тяжёлые вычисления на каждый тик, загрузку кода, который сейчас не нужен, и пересоздание узлов списка из‑за нестабильных `key`.
>
> На практике сначала смотрят профиль: React DevTools **Profiler** показывает, какие компоненты перерисовались и сколько заняли; Network / analyzer — размер и момент загрузки чанков. Без цифр легко «оптимизировать» холодный путь и усложнить код впустую.
>
> Типичный набор рычагов: **`React.memo`** (и аккуратные `useMemo` / `useCallback`, чтобы props не менялись ссылкой зря) — пропуск `render` при равных props; **`React.lazy` + `Suspense`** — код маршрута/виджета подгружается по требованию; **стабильный `key`** у элементов списка — React переиспользует инстансы вместо remount. Рядом — узкий Context, виртуализация длинных списков, дебаунс ввода; это уже точечные ответы на конкретный профиль.
>
> Ловушка: мемоизация «на всякий случай» раздувает код и не лечит частые смены state у родителя. Плохой `key={index}` при сортировке/вставке даёт баги состояния (фокус, анимации), а не только «медленнее». Сначала узкое место, потом один рычаг под него.

---

# 4. Самое главное запомнить

- Сначала Profiler / Network — потом `memo` / `lazy` / виртуализация.
- `React.memo` пропускает `render`, если props поверхностно равны; новые объекты/функции на каждый рендер родителя сводят выгоду к нулю.
- `useMemo` / `useCallback` — стабилизировать **значения и колбэки**, которые уходят в мемоизированных детей, а не «кэшировать всё подряд».
- `React.lazy` + `Suspense` режут **начальный бандл**; fallback — пока грузится чанк.
- `key` идентифицирует элемент в списке: стабильный id → reuse; `index` при перестановках → remount и сюрпризы со state.
- «Больше `memo`» ≠ быстрее: лишние сравнения и сложность без выигрыша на горячем пути.

# 5. Описание

```text
измерить (Profiler / Network)
        │
        ├─ много лишних render ──► memo + стабильные props
        │                           (useMemo / useCallback точечно)
        ├─ большой initial JS ───► lazy + Suspense (чанки маршрутов)
        └─ длинный список / remount ─► key = id · virtualization
```

## Лишние рендеры и `memo`

Родитель вызвал `setState` → React по умолчанию снова вызывает `render` у детей. Если ребёнку не нужны новые данные, это пустая работа (плюс diff Virtual DOM).

```tsx
const Row = memo(function Row({ label }: { label: string }) {
  return <li>{label}</li>; // ← не вызовется, если label тот же
});
```

Сравнение по умолчанию — поверхностное (`Object.is` по каждому prop). Если родитель каждый раз передаёт `style={{ … }}` или `onClick={() => …}`, ссылка новая → `memo` бесполезен.

## `useMemo` и `useCallback`

- `useMemo(() => heavy(list), [list])` — не пересчитывать дорогой результат, пока `list` тот же.
- `useCallback(fn, deps)` — та же функция между рендерами, чтобы `memo`-ребёнок не считал prop «изменённым».

Их смысл чаще всего именно в **стабильности ссылок** для мемоизированных потомков или дорогих вычислений, а не в «ускорении любого выражения».

## `lazy` и code splitting

```tsx
const Settings = lazy(() => import('./SettingsPage')); // ← отдельный чанк

function App() {
  return (
    <Suspense fallback={<p>Загрузка…</p>}>
      <Settings />
    </Suspense>
  );
}
```

Маршрут или тяжёлый виджет не попадают в initial bundle, пока пользователь туда не зашёл. Смотреть Network: отдельный `.js` после навигации — признак, что split сработал.

## Стабильные `key` в списках

```tsx
// плохо при insert/sort: индекс «переезжает» на другой элемент
{items.map((item, i) => <Row key={i} item={item} />)}

// хорошо: key = стабильный id из данных
{items.map((item) => <Row key={item.id} item={item} />)}
```

React сопоставляет детей по `key`. Смена ключа = «это другой элемент» → unmount/mount, сброс локального state, лишняя работа. Для тысяч строк дополнительно смотрят виртуализацию (рисуют только видимое окно).

## Что ещё смотреть по профилю

| Симптом | Направление |
| --- | --- |
| Весь экран мигает от тика в шапке | Узкий state / Context; `memo` на тяжёлых ветках |
| Долгий FCP / большой main.js | `lazy`, analyzer, меньше тяжёлых deps в entry |
| Лаги скролла по 10k строк | Virtualization, не «ещё один `memo`» |
| Context обновляет полдерева | Разбить провайдеры или селекторы |

Смежные темы: Virtual DOM / reconciliation объясняют *почему* лишний render стоит денег; bundler-темы — *как* режется бандл на уровне сборки.
