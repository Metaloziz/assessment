# 1. Тема

**SOLID**

---

# 2. Главное в одну фразу

SOLID — пять простых правил, как разложить код по файлам, чтобы одно изменение правил обычно один кусок, а не половину проекта.

---

# 3. Суть

> SOLID — пять правил хорошей нарезки кода (Роберт Мартин). Буквы: Single Responsibility, Open-Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. Это не «обязательно классы» и не паттерны вроде Factory. Это ответы на вопрос: *куда* должна попасть правка, когда меняют налог, оплату или базу.
>
> Зачем: в реальном сервисе требования меняются часто. Если один `OrderService` и считает цену с НДС, и рисует PDF, смена налога трогает и цифры, и вёрстку счёта. SOLID помогает развести такие вещи: цена отдельно от PDF; новый Paypal — новый маленький кусок, а не правка старого `switch`; «квадрат» не ломает ожидания кода, который думал, что работает с прямоугольником; интерфейс не заставляет писать пустые методы; бизнес-код не знает про Postgres напрямую.
>
> Как проверять: представьте стрелку «вот что изменилось». SRP — стрелка попала в один файл. OCP — старый файл не трогали, добавили новый. LSP — подставили другой тип, а поведение для вызывающего кода осталось честным. ISP — в типе только методы, которые реально зовут. DIP — важный код зависит от простого договора (`Store`), а не от конкретной базы.
>
> Ловушка: не вешать все пять букв на каждый хелпер из двадцати строк. DIP — это не «обязательно контейнер DI». LSP ломается не из‑за имени Square, а когда вызывающий код получает сюрприз. Соседние темы (MVC, FP vs OOP) — про другое; SOLID — про швы между модулями.

---

# 4. Самое главное запомнить

- SRP: в одном файле — одна *причина* менять. Не путать с «один метод».
- OCP: новое поведение лучше добавить новым куском; если каждый Paypal правит старый `switch` — правило сломано.
- LSP: можно подставить другой тип туда, где ждут общий договор, и вызывающий код не должен удивляться.
- ISP: не заставляйте код реализовывать методы, которые он никогда не вызывает.
- DIP: важный код смотрит на договор (`Store`), а не на `PostgresStore`.
- DIP ≠ «нужен DI-контейнер»: достаточно передать зависимость аргументом.
- Не дробить всё подряд: швы нужны там, где требования реально расходятся.

# 5. Описание

```text
изменение ──►  S  один файл — один повод    цена отдельно от PDF
               O  добавить кусок, не правку  Paypal рядом, checkout цел
               L  подмена без сюрпризов      area(), не Square как Rect
               I  только нужные методы       run, без пустых persist
               D  договор, не база           Report → Store ← Postgres
```

Общий тест для всех пяти: «куда попадёт правка?»

## SRP — одна причина менять

Файл (или модуль) лучше менять по **одной** причине. Сменили формулу НДС — не должны править макет счёта. «Делает одно» ≠ «один метод»: посчитать цену — одна ответственность, даже если внутри три функции.

```ts
// плохо: два повода в одном объекте
export function createOrderService() {
  return {
    quote(items: { price: number }[]) { /* НДС */ },
    invoicePdf(id: string, total: number) { /* макет */ },
  };
}
```

Лучше: `quoteWithVat` в одном файле, `invoicePdf` — в другом. Налог правит только цену.

## OCP — открыт для нового, закрыт для правок

Идея Бертрана Мейера: новое поведение добавляют **новым** куском, а не правкой уже работающего кода. Типичная ошибка — большой `switch (channel)` внутри `checkout`: каждый новый Paypal снова открывает старый файл.

```ts
type PayMethod = { pay: (amount: number) => Promise<void> };

export function checkout(method: PayMethod, amount: number) {
  return method.pay(amount); // ← Checkout не знает Paypal
}
```

Новый канал = новый объект с `pay`. Старый `checkout` не трогают. Рядом лежит паттерн Strategy: OCP говорит *зачем* нужен слот, Strategy — *как* его сделать.

## LSP — подмена без сюрпризов

Барбара Лисков: если код ждёт тип `A`, можно подставить `B`, и всё должно работать честно — без скрытых ловушек. Классический провал: квадрат выдают за прямоугольник. Код делает `setWidth(5)` и `setHeight(4)`, ждёт площадь 20, а у «квадрата» стороны связаны — получается 16.

Честный договор — общий `area()`, без обещания «ширина и высота независимы»:

```ts
type Shape = { area: () => number };

export const rectangle = (w: number, h: number): Shape => ({
  area: () => w * h,
});
export const square = (side: number): Shape => ({
  area: () => side * side,
});
```

Имя Square само по себе ничего не чинит. Чинит договор, который вызывающий код реально использует.

## ISP — только методы, которые нужны

Толстый `Worker { run, persist, notify }` заставляет простую ping-задачу писать пустые `persist` и `notify`. Лучше узкий договор: `Runnable { run }` — только то, что вызывают.

Пустой метод «чтобы TypeScript не ругался» — сигнал: интерфейс слишком жирный для этого клиента.

## DIP — зависеть от договора, не от детали

Важный код (отчёт, заказ) не должен сам импортировать Postgres или `fs`. Оба конца смотрят на простой договор:

```text
ReportService ──► Store ◄── PostgresStore
                     ▲
                     └── MemoryStore
```

Как именно **передают** `Store` (аргумент, фабрика, контейнер) — тема Dependency Injection. DIP здесь про другое: *направление* — бизнес-код не знает Postgres.

Ловушка: «абстракция», которая один в один копирует Postgres (`query(sql: string)`), почти не помогает. Договор лучше писать словами бизнеса (`loadUsers()`), а не словами драйвера.

## Что не путать

| Путают | На деле |
| --- | --- |
| SRP = «один метод» | одна *причина* менять файл |
| OCP = «никаких `if`» | не править уже закрытый модуль; ветка в новом куске — норма |
| LSP = обязательно `extends` | честная подмена по договору |
| ISP = «много мелких файлов» | резать интерфейс по тому, *кто* его вызывает |
| DIP = DI-контейнер | смотреть на договор; `inject()` не обязателен |
