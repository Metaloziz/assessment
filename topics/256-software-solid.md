# 1. Тема

**SOLID, Cohesion и Coupling**

---

# 2. Главное в одну фразу

SOLID помогает нарезать код так, чтобы вещи одного повода жили вместе, а правка в одном модуле не тащила половину проекта.

---

# 3. Суть

> Связность и зацепление — два вопроса про нарезку. **Связность** (`cohesion`): лежат ли в одном файле вещи одного повода? Высокая — формула НДС и округление денег рядом. **Зацепление** (`coupling`): сколько чужих внутренностей нужно знать, чтобы поменять этот кусок? Слабое — заказ зовёт `store.load()`, а не SQL Postgres. **SOLID** — пять правил Роберта Мартина, как к этому прийти: *куда* попадёт правка, когда меняют налог, оплату или базу.
>
> Зачем: в сервисе требования ездят часто. Если один `OrderService` считает цену, рисует PDF и сам пишет в Postgres, смена налога трогает вёрстку счёта, а смена базы — весь заказ. Высокая связность держит правку в одном месте; слабое зацепление не тащит соседей.
>
> SRP и ISP поднимают связность: один повод менять файл, в типе только методы, которые реально зовут. OCP и DIP слабее делают зацепление: новый Paypal — новый кусок, не правка `switch`; бизнес смотрит на договор `Store`, не на Postgres. LSP следит, чтобы подмена типа не дала сюрприз — иначе вы зацеплены за скрытое поведение.
>
> Ловушка: не вешать все пять букв на хелпер из двадцати строк. Связность — не «один метод». Зацепление — не «ноль импортов»: модули должны разговаривать, но через узкий договор. DIP — не «обязательно контейнер DI». Соседние темы (MVC, FP vs OOP) — про другое.

---

# 4. Самое главное запомнить

- Связность: в одном файле — вещи одного повода; «свалка» хелперов — низкая связность.
- Зацепление: чем больше чужих внутренностей знает модуль (SQL, поля PdfKit), тем больнее соседям при правке.
- SRP и ISP поднимают связность: один повод менять файл; в типе только то, что зовут.
- OCP и DIP слабее делают зацепление: новый Paypal рядом; бизнес смотрит на `Store`, не на Postgres.
- LSP: подставили другой тип — вызывающий код не должен удивляться.
- DIP ≠ «нужен DI-контейнер»: достаточно передать зависимость аргументом.
- Не дробить всё подряд: швы нужны там, где требования реально расходятся.

# 5. Описание

```text
изменение (НДС / Paypal / база)
        │
        ├─ что лежит в одном файле?     связность (cohesion)
        │    вместе про одно дело  →  правка в одном месте
        │
        └─ кто знает чьи внутренности?  зацепление (coupling)
             узкий вызов, не SQL соседа  →  соседей не тащим

SOLID — короткие правила, как к этому прийти:
S / I   выше связность      один повод; только нужные методы
O / D   слабее зацепление   новый кусок; договор, не база
L       честный договор     подмена без сюрприза
```

Сначала два вопроса «что вместе / кто от кого зависит». Буквы SOLID — практичные ответы, не отдельная религия.

## Связность — что лежит в одном файле

Связность (`cohesion`) — насколько куски **внутри** модуля про одно дело. Высокая: в `pricePolicy.ts` живут ставка, сумма и округление — их меняют, когда меняют деньги. Низкая: в `orderStuff.ts` рядом НДС, PDF, письмо «заказ уехал» и ночная чистка cron. Смена налога открывает файл, где лежит почта.

Это не «один метод на файл». Посчитать цену — одно дело, даже если внутри три функции. Учебники перечисляют виды связности; на практике хватает вопроса: *по одному ли поводу правят этот файл?*

```ts
// низкая связность: четыре разных повода в одном файле
export function quoteWithVat(items: { price: number }[]) { /* НДС */ }
export function invoicePdf(id: string, total: number) { /* макет */ }
export function sendShippedMail(to: string) { /* письмо */ }
export function nightlyCleanup() { /* cron */ }
```

Лучше: цена — в одном файле, макет счёта — в другом. Налог правит только цену.

## Зацепление — сколько соседей нужно знать

Зацепление (`coupling`) — насколько модуль зависит от **других**. Слабое: заказ зовёт `store.loadOrder(id)` и не знает, SQL это или память. Жёсткое: тот же заказ сам пишет `select … from orders` и ставит `doc.x = 40` у PdfKit. Сменили драйвер базы — правите заказ. Сменили рендерер — снова заказ.

Импорты сами по себе не зло. Зло — знать чужие внутренности (поля, SQL, порядок файлов). Модули должны разговаривать, но через узкий договор.

```text
жёстко:  Заказ ──SQL──► Postgres
                ──x,y──► PdfKit

слабо:   Заказ ──load()──► Store ──► Postgres
              ──render()──► счёт
```

## SRP — одна причина менять

Файл лучше менять по **одной** причине. Сменили формулу НДС — не должны править макет счёта. SRP — самый прямой путь к высокой связности: «делает одно» ≠ «один метод».

```ts
// плохо: два повода в одном объекте
export function createOrderService() {
  return {
    quote(items: { price: number }[]) { /* НДС */ },
    invoicePdf(id: string, total: number) { /* макет */ },
  };
}
```

Лучше: `quoteWithVat` в одном файле, `invoicePdf` — в другом. Налог правит только цену.

## OCP — открыт для нового, закрыт для правок

Идея Бертрана Мейера: новое поведение добавляют **новым** куском, а не правкой уже работающего кода. Типичная ошибка — большой `switch (channel)` внутри `checkout`: каждый новый Paypal снова открывает старый файл и сильнее цепляет его за каналы.

```ts
type PayMethod = { pay: (amount: number) => Promise<void> };

export function checkout(method: PayMethod, amount: number) {
  return method.pay(amount); // ← Checkout не знает Paypal
}
```

Новый канал = новый объект с `pay`. Старый `checkout` не трогают. Рядом лежит паттерн Strategy: OCP говорит *зачем* нужен слот, Strategy — *как* его сделать.

## LSP — подмена без сюрпризов

Барбара Лисков: если код ждёт тип `A`, можно подставить `B`, и всё должно работать честно — без скрытых ловушек. Классический провал: квадрат выдают за прямоугольник. Код делает `setWidth(5)` и `setHeight(4)`, ждёт площадь 20, а у «квадрата» стороны связаны — получается 16.

Честный договор — общий `area()`, без обещания «ширина и высота независимы»:

```ts
type Shape = { area: () => number };

export const rectangle = (w: number, h: number): Shape => ({
  area: () => w * h,
});
export const square = (side: number): Shape => ({
  area: () => side * side,
});
```

Имя Square само по себе ничего не чинит. Чинит договор, который вызывающий код реально использует. Иначе вы зацеплены за сюрприз подтипа.

## ISP — только методы, которые нужны

Толстый `Worker { run, persist, notify }` заставляет простую ping-задачу писать пустые `persist` и `notify`. Лучше узкий договор: `Runnable { run }` — только то, что вызывают. Интерфейс тогда связный: методы про одно дело клиента, а не «всё, что когда-нибудь понадобится».

Пустой метод «чтобы TypeScript не ругался» — сигнал: интерфейс слишком жирный для этого клиента.

## DIP — зависеть от договора, не от детали

Важный код (отчёт, заказ) не должен сам импортировать Postgres или `fs`. Оба конца смотрят на простой договор — так слабеет зацепление:

```text
ReportService ──► Store ◄── PostgresStore
                     ▲
                     └── MemoryStore
```

Как именно **передают** `Store` (аргумент, фабрика, контейнер) — тема Dependency Injection. DIP здесь про другое: *направление* — бизнес-код не знает Postgres.

Ловушка: «абстракция», которая один в один копирует Postgres (`query(sql: string)`), почти не помогает. Договор лучше писать словами бизнеса (`loadUsers()`), а не словами драйвера.

## Что не путать

| Путают | На деле |
| --- | --- |
| связность = «один метод» | вещи одного повода в одном файле |
| зацепление = «ноль импортов» | не знать чужие внутренности; узкий вызов — норма |
| OCP = «никаких `if`» | не править уже закрытый модуль; ветка в новом куске — норма |
| DIP = DI-контейнер | смотреть на договор; `inject()` не обязателен |
