# 1. Тема
**Назначение unit-тестов**
---
# 2. Главное в одну фразу
Unit-тесты быстро проверяют небольшой модуль в контролируемой изоляции, фиксируя его контракт и защищая код от регрессий.
---
# 3. Ответ для собеседования
> «Unit-тест проверяет маленькую единицу поведения — функцию, класс, reducer или компонентную логику — изолированно от реальной сети, БД и файловой системы. Его назначение: подтвердить контракт входов и выходов, рано поймать регрессию, упростить рефакторинг и документировать ожидаемое поведение. Внешние зависимости подменяю двойниками, поэтому тесты должны быть быстрыми, независимыми и детерминированными. Unit-тесты — фундамент пирамиды, но не заменяют integration и e2e.»
---
# 4. Самое главное запомнить
- Одна единица поведения в изоляции.
- Быстрый feedback и дешёвая локализация бага.
- Моки — для внешних зависимостей, не для всего кода.
- Тестируем наблюдаемое поведение, а не private-детали.
- TDD использует unit-тест как первый шаг цикла Red–Green–Refactor.
---
# 5. Описание
```javascript
test('применяет скидку 10%', () => {
  expect(calcDiscount(1000, 10)).toBe(900);
});
```

| Тип | Проверяет | Скорость | Пример |
|---|---|---|---|
| Unit | Модуль в изоляции | Высокая | расчёт скидки |
| Integration | Связку модулей | Средняя | service + repository |
| E2E | Пользовательский поток | Низкая | вход и покупка |

Пирамида тестов обычно выглядит так: много unit, меньше integration и немного критичных e2e. Unit-тест не обязан мокировать соседний чистый модуль; изоляция нужна прежде всего от I/O и нестабильности.

### Хорошие практики
- именовать тест как сценарий и ожидаемый результат;
- готовить независимые данные в каждом тесте;
- проверять позитивный, граничный и ошибочный путь;
- избегать реального времени, случайности и сети;
- держать тест простым: один понятный повод для падения.

TDD — не отдельный тип тестирования: это способ разработки, в котором тест сначала описывает требуемое поведение, затем направляет минимальную реализацию и страхует рефакторинг.
