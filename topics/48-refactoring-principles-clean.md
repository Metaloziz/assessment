# 1. Тема

**Основные принципы рефакторинга: код должен становиться чище, при этом не должна создаваться новая функциональность**

---

# 2. Главное в одну фразу

Рефакторинг улучшает структуру и читаемость кода **без** добавления новой функциональности и **без** изменения внешнего поведения.

---

# 3. Ответ для собеседования

> «**Рефакторинг** — осознанное изменение внутренней структуры кода при сохранении наблюдаемого поведения. Цель: код становится чище, проще и дешевле в поддержке, но пользователь и API снаружи ведут себя так же.
>
> Ключевой принцип: **не смешивать** рефакторинг с фичами. Сначала (или отдельно) чистим структуру под зелёными тестами, потом уже добавляем новое поведение — иначе сложно понять, баг от рефакторинга или от новой логики.
>
> Опора: тесты / ручная проверка контракта, маленькие шаги, частые коммиты. Классика — приёмы Fowler: Rename, Extract Method/Function, Inline, Move, Introduce Parameter Object и т.д.»

---

# 4. Самое главное запомнить

- Рефакторинг ≠ новая фича и ≠ «переписать с нуля».
- Поведение снаружи не меняется; меняется устройство внутри.
- Код должен становиться **чище** (читаемость, связность, дублирование, имена).
- Делать **маленькими шагами** под страховкой тестов.
- Не рефакторить «заодно» с багфиксом/фичей в одном непрозрачном диффе.

| | Рефакторинг | Новая функциональность |
|--|-------------|------------------------|
| Поведение | То же | Меняется / расширяется |
| Цель | Чище, проще поддержка | Новая ценность для пользователя |
| Риск | Регрессия структуры | Новые сценарии и краевые случаи |
| Дифф | Идеально отдельный PR/коммит | Отдельный от чистки |

---

# 5. Описание

Определение в духе Martin Fowler: *изменение внутренней структуры ПО, которое не меняет его наблюдаемое поведение и делает код проще для понимания и дешевле для изменения*.

### Почему «без новой функциональности»

Если в одном изменении и чистка, и фича:

1. ревьюер не отделяет «это просто переименование» от «здесь новая ветка логики»;
2. упавший тест не говорит, что сломалось — структура или требование;
3. откат становится дорогим: нельзя безопасно вернуть только половину.

Практическое правило: **один тип намерения на коммит/PR** — либо refactor, либо feature/fix.

### Что значит «код становится чище»

Обычно улучшают:

- **имена** — отражают намерение;
- **дублирование** — DRY там, где одинаковое поведение, не «похожий код»;
- **размер функций/компонентов** — одна ответственность;
- **связность модулей** — сильная cohesion, слабая coupling;
- **уровни абстракции** — не смешивать детали I/O с бизнес-правилами в одной простыне;
- **мёртвый код и ложную сложность** — убрать то, что мешает читать.

«Чище» измеряется не вкусом ради вкуса, а тем, насколько быстрее следующий разработчик поймёт и безопасно изменит код.

### Безопасный цикл

1. Убедиться, что есть покрытие критичного поведения (или зафиксировать ручной чеклист).
2. Сделать маленький шаг рефакторинга.
3. Прогнать тесты / проверить сценарий.
4. Закоммитить.
5. Повторить.

Крупный «большой взрыв» без шагов — это уже rewrite, а не рефакторинг.

### Типичные приёмы (ориентиры)

```javascript
// До: длинная функция смешивает разбор и побочный эффект
function submit(form) {
  const email = String(form.email || '').trim().toLowerCase()
  if (!email.includes('@')) throw new Error('invalid')
  api.send(email)
}

// После рефакторинга: поведение то же, структура яснее
function normalizeEmail(value) {
  return String(value || '').trim().toLowerCase()
}

function assertValidEmail(email) {
  if (!email.includes('@')) throw new Error('invalid')
}

function submit(form) {
  const email = normalizeEmail(form.email)
  assertValidEmail(email)
  api.send(email)
}
```

Здесь не появилось нового продукта — только яснее границы ответственности.

### Чего рефакторинг не делает

- не добавляет экраны, флаги, эндпоинты «заодно»;
- не «улучшает» продукт без явного запроса (новая валидация UX — это уже поведение);
- не оправдывает отсутствие тестов: без страховки чистка превращается в лотерею.

Если нужно и почистить, и добавить фичу — сначала (или в отдельном PR) рефакторинг до удобной точки расширения, затем отдельным коммитом — поведение.
