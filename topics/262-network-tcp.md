# 1. Тема

**Базовое понимание TCP**

---

# 2. Главное в одну фразу

TCP поднимает соединение между сокетами `IP:порт` и доставляет байты надёжно и по порядку — это поток, на котором живут HTTP, TLS и БД, а не сам прикладной протокол.

---

# 3. Суть

> **TCP** (Transmission Control Protocol) — транспорт с **соединением**: два сокета (`IP` + порт) сначала договариваются о сессии, затем видят **поток байт**, а не «сообщения HTTP». Канал полный дуплекс: писать и читать можно одновременно. IP шлёт датаграммы как получится; TCP нумерует байты, подтверждает, повторяет потери и восстанавливает порядок.

> На этом стоят `fetch`, `http`/`net` в Node, SSH, Postgres, Redis: пока нет **ESTABLISHED**, прикладных байт нет. «Сайт не открылся» почти всегда раскладывается на DNS, TCP, TLS и уже HTTP — TCP отвечает только за трубу до порта.

> Рукопожатие (**three-way handshake**). Клиент шлёт **Synchronize** (`SYN`) со своим ISN. Сервер отвечает сегментом с двумя флагами: **Synchronize + Acknowledgment** (`SYN-ACK`) — свой ISN и подтверждение чужого `SYN`. Клиент закрывает тройку **Acknowledgment** (`ACK`). Дальше сегменты с `seq`/`ack`. Получатель двигает окно приёма (**rwnd**, flow control); отправитель ещё ограничивает себя **cwnd** (congestion). Потеря — повтор по RTO или dup ACK, не логика HTTP. Штатное закрытие — **Finish** (`FIN`) с обеих сторон (часто **TIME_WAIT**); обрыв — **Reset** (`RST`).

> Ловушка: путать TCP с HTTP и с UDP. HTTP — смысл метода и статуса *внутри* потока; UDP — датаграммы без сессии и гарантий протокола. `ECONNREFUSED` — хост ответил **RST** (на порту никто не слушал); `ETIMEDOUT` — ответа нет (фильтр, путь). Модель TCP/IP целиком — соседние темы группы.

---

# 4. Самое главное запомнить

- Сокет = `IP` хоста + **порт** процесса; TCP даёт поток байт, не кадры HTTP.
- Handshake: **Synchronize** (`SYN`) → **Synchronize + Acknowledgment** (`SYN-ACK`) → **Acknowledgment** (`ACK`), затем `ESTABLISHED`.
- Надёжность: `seq`/`ack`, повтор потери, порядок; flow control — `rwnd`, congestion — `cwnd`.
- **Finish** (`FIN`) — штатное закрытие (часто `TIME_WAIT`); **Reset** (`RST`) — обрыв; в Node `ECONNREFUSED` типично от Reset.
- `ETIMEDOUT` ≠ `ECONNREFUSED`: таймаут — тишина, refused — явный отказ порта.
- HTTP/TLS/SSH/БД сидят *на* TCP; UDP — другой транспорт, не «сломанный TCP».
- HTTP/2 мультиплексирует потоки, но всё ещё одно TCP-соединение: потеря сегмента тормозит все streams.

# 5. Описание

```text
Клиент :ephemeral                          Сервер :443
   CLOSED                                     LISTEN
      │  ── Synchronize (SYN) seq=ISNc ─────────────────►  │
      │  ◄─ Synchronize+Acknowledgment (SYN-ACK) ────────  │
      │  ── Acknowledgment (ACK) ack=ISNs+1 ────────────►  │
   ESTABLISHED                              ESTABLISHED
      │  ── DATA seq …  /  ◄─ Acknowledgment (ACK) ─────   │
      │  ── Finish (FIN)  /  Reset (RST) при обрыве ───►   │
```

## Сокет и поток байт

TCP не знает JSON и не знает «запрос». Он везёт октеты. Границы сообщений прикладного протокола (длина в заголовке HTTP, `\n` в Redis) — задача уровня выше.

В коде это `net.Socket`: `write` / `'data'` / `'end'`. Порт в `listen(443)` выбирает процесс; клиентский порт обычно ephemeral (ОС выдаёт свободный).

```text
203.0.113.10:443  ←  сервер слушает
192.0.2.4:53122   ←  этот клиент (эфемерный порт)
```

Один хост держит много TCP-сессий: ключ — четвёрка src IP/port + dst IP/port.

## Рукопожатие и имена флагов

Флаги в заголовке TCP — биты. Имена, которые пишут в дампах, — сокращения:

| Сокращение | Полное имя | Что делает |
|------------|------------|------------|
| `SYN` | **Synchronize** | «Синхронизируй номера»: открыть соединение и объявить свой **ISN** |
| `ACK` | **Acknowledgment** | «Подтверждаю»: принял байты / чужой `SYN` до этого номера (`ack`) |
| `SYN-ACK` | **Synchronize + Acknowledgment** | не отдельный протокол, а **два флага в одном сегменте**: сервер и открывается, и подтверждает клиентский `SYN` |
| `FIN` | **Finish** | «больше данных не будет» (half-close возможен) |
| `RST` | **Reset** | сессии нет или её надо оборвать |
| `PSH` | **Push** | отдать данные приложению, не копить в буфере |

Тройка handshake — три сегмента, не три разных протокола:

```text
1. Клиент → сервер   Synchronize              SYN=1 ACK=0
2. Сервер → клиент   Synchronize+Acknowledgment  SYN=1 ACK=1
3. Клиент → сервер   Acknowledgment           SYN=0 ACK=1
```

После третьего сегмента обе стороны в `ESTABLISHED`. **ISN** (initial sequence number) — стартовый `seq`, не обязан быть нулём. Сам `SYN` занимает один номер последовательности; первый байт данных клиента идёт с `seq = ISN+1`.

Пока handshake не завершён, `socket.write` в Node ещё не уходит в ESTABLISHED-поток — сокет в очереди; ошибка коннекта придёт в `'error'`, не как HTTP-статус.

## Надёжность: повтор и окна

Потерянный сегмент **повторяют**. Два пути: истёк **RTO** (retransmission timeout) или пришли дубликаты **Acknowledgment** (fast retransmit). Приложение видит тот же поток — дыр в `read` нет, только задержка.

Два разных «окна», их путают:

| Окно | Кто задаёт | Смысл |
|------|------------|--------|
| `rwnd` (receive window) | получатель | сколько ещё влезет в буфер (**flow control**) |
| `cwnd` (congestion window) | отправитель по сигналам сети | сколько можно в полёт, чтобы не забить путь |

В полёте оказывается `min(rwnd, cwnd)`. Медленный клиент с маленьким `rwnd` и забитый линк с падающим `cwnd` — разные диагнозы: один смотрит на получателя, другой на сеть.

## Закрытие и Reset

Штатно каждая сторона шлёт **Finish** (`FIN`) и ждёт **Acknowledgment**. Сторона, которая закрыла первой, часто сидит в **TIME_WAIT**: держит четвёрку, чтобы запоздавший сегмент не сел на новый сокет с теми же портами.

**Reset** (`RST`) — не «вежливый конец»: порт закрыт, сегмент к мёртвой сессии, `socket.destroy()`. Практические сигналы в Node:

| Ошибка | Что произошло на TCP |
|--------|----------------------|
| `ECONNREFUSED` | до хоста дошли, на порту нет LISTEN → **Reset** (`RST`) |
| `ETIMEDOUT` / hung SYN | Synchronize ушёл, ответа нет (drop, фильтр, нет маршрута) |
| `EPIPE` / `ECONNRESET` | писали в уже закрытую/сброшенную сессию |

Таймаут коннекта — не `404` и не CORS.

## Чем TCP не является

- **Не HTTP.** Метод и статус живут в байтах потока; TCP не читает `GET`.
- **Не UDP.** У UDP нет handshake, seq/ack и повтора в протоколе.
- **Не IP.** IP выбирает хост и путь пакета; порт и надёжность — транспорт.
- **Не TLS.** TLS (и HTTPS) садятся *после* TCP (или рядом в QUIC/UDP — вне темы).

HTTP/2 на одном TCP: мультиплекс streams не отменяет head-of-line **на TCP**: потеря сегмента останавливает все потоки этого соединения. HTTP/3/QUIC уходят на UDP как раз из‑за этого — соседняя история, не эта тема.

## Ловушки

- Ждать от TCP «сообщений» и границ JSON без прикладного фрейминга.
- Лечить `ECONNREFUSED` как «сеть легла»: часто просто не тот порт / сервер не слушает.
- Считать `TIME_WAIT` утечкой сокетов: это штат протокола после активного close.
- Путать flow control (`rwnd`) с congestion (`cwnd`) и крутить `TCP_NODELAY`, «чтобы быстрее», без понимания Nagle.
