# 1. Тема

**Признаки грязного кода**

---

# 2. Главное в одну фразу

Грязный код — это фрагменты, где **понять намерение и безопасно изменить поведение дорого**: шумные комментарии, длинные списки аргументов, смешанные обязанности и сильное зацепление между модулями.

---

# 3. Суть

> «Грязный код» — не эстетика и не «не мой стиль». Это **сигналы трения**: следующий разработчик долго читает, боится тронуть строку, правка в одном месте ломает другое. Признаки не приговор — они показывают, **куда смотреть** перед рефакторингом.
>
> **Комментарии.** Избыточные повторяют очевидное из кода (`i++ // увеличить i`). Неинформативные не объясняют *зачем* (`// fix`, `// TODO`). Полезный комментарий — про намерение, контракт или неочевидное ограничение, которое код не может сказать сам.
>
> **Много аргументов.** Функция с пятью–семью однотипными параметрами легко перепутать порядок, сложно расширять. Объект параметров или маленький тип с именованными полями сохраняет поведение, но снимает «позиционную лотерею».
>
> **Связность и зацепление.** В одном модуле смешаны расчёт, печать, SMS и ночная уборка — низкая связность внутри файла. Модуль, который знает SQL соседа и поля чужого принтера, — высокое зацепление. Чистый вариант: одно дело на файл и узкие вызовы через интерфейс.
>
> Ловушка: лечить симптомы косметикой (переименовать переменную, но оставить бог-функцию) или считать «грязным» любой старый код. Сначала **узнаёте запах**, потом маленький рефакторинг под тестами — Extract Method, Introduce Parameter Object, Split Module.

---

# 4. Самое главное запомнить

- Грязный код = **дорого читать и менять**, а не «некрасиво отформатировано».
- Избыточный комментарий дублирует код; неинформативный не помогает понять *зачем*.
- Много positional-аргументов — риск перепутать порядок; объект параметров — тот же контракт, яснее вызов.
- Смешанные обязанности в одном файле и прямой доступ к чужим деталям — признаки слабой структуры.
- Запах → маленький приём рефакторинга, не «переписать всё».
- Старый, но покрытый тестами модуль может быть терпимым; свежий без тестов — всё равно рискованный.

| Запах | Что беспокоит | Направление чистки |
| --- | --- | --- |
| Шумные комментарии | Код и комментарий говорят одно | Удалить дубль; имя переменной / функции |
| Пустые комментарии | Не ясно *зачем* ветка | Имя + тест; комментарий только про бизнес-правило |
| 5+ аргументов | Порядок, расширение | Parameter object, defaults |
| Свалка в файле | Любая правка трогает всё | Extract Module / Method по одному поводу |
| Знает чужие детали | Ломается при смене соседа | Интерфейс, dependency injection |

---

# 5. Описание

```text
фрагмент кода
  → читаемость: имена, размер, дубли
  → комментарии: дубль кода? объясняют зачем?
  → сигнатуры: сколько аргументов, порядок
  → границы модулей: одно дело? знает ли соседа изнутри?
  → запах → маленький рефакторинг (не фича в том же PR)
```

## Комментарии: шум и пустота

**Избыточные** — когда комментарий повторяет то, что уже видно:

```javascript
total += price // прибавляем цену
if (!email.includes('@')) return false // проверяем email
```

Код уже говорит «прибавляем» и «проверяем». Лучше сильное имя или Extract Method.

**Неинформативные** — когда без комментария непонятно, но с ним тоже:

```javascript
// fix
discount = 0.15

// TODO
if (user.role === 3) allow()
```

«fix» и «TODO» не объясняют бизнес-правило. Либо имя `applyLoyaltyDiscount`, либо комментарий *почему* 15 % для `role === 3`, либо константа `Role.Manager`.

Полезный комментарий — про то, чего **нет в коде**: юридический лимит, костыль под баг API, инвариант домена.

## Много аргументов

```javascript
// Грязно: легко перепутать city и zip
createUser('Ann', 'ann@x.com', true, false, 'RU', 'Moscow', '101000', '+7…')

// Чище: те же данные, вызов читается
createUser({
  name: 'Ann',
  email: 'ann@x.com',
  address: { country: 'RU', city: 'Moscow', zip: '101000' },
  notify: { email: true, sms: false },
})
```

Порог не магический: как только при добавлении поля приходится помнить позицию или передавать `undefined` «заглушки» — пора Parameter Object.

## Связность и зацепление

**Низкая связность внутри файла** — функции про разное живут рядом: посчитать сумму, напечатать чек, отправить SMS, закрыть смену. Любая задача «про деньги» задевает и печать.

**Высокое зацепление** — модуль лезет в SQL, поля принтера, env соседа. Смена склада или принтера ломает кассу.

Чистый контраст: файл про цену; касса вызывает `loadCart()` и `printTotal()`, не зная SQL.

## Как использовать на практике

1. При ревью или перед задачей — **назвать запах** (не «плохой код», а «7 аргументов + комментарии-fix»).
2. Выбрать **один** приём Fowler под запах.
3. Прогнать тесты / ручной сценарий — поведение снаружи то же.
4. Не смешивать с новой фичей в одном диффе.

В лабе три пары «грязный vs чистый»: комментарии, аргументы, связность — смотрите файлы на вкладке «Код».
