# 1. Тема

**TypeScript, область применения**

---

# 2. Главное в одну фразу

TypeScript добавляет к JavaScript статическую проверку типов на этапе сборки и стирает типы в обычный JS для браузера и Node.

---

# 3. Суть

> TypeScript (TS) — язык поверх JavaScript: вы пишете типы у переменных, функций и модулей, а компилятор `tsc` (или сборщик со встроенным checker’ом) проверяет их до запуска. На выходе — обычный JavaScript без типов: рантайм их не видит.
>
> Типы нужны там, где контракты между частями кода часто ломаются при правках: UI и API, библиотека и потребители, общая модель данных в команде. Файлы `.d.ts` описывают типы для уже существующего JS или для пакетов без исходников TS.
>
> Типичный путь: `.ts` / `.tsx` → проверка типов → transpile (или emit от `tsc`) → тот же JS, что и без TS. IDE подсвечивает ошибки раньше, чем тест или клик в UI.
>
> Ловушка: думать, что «раз прошло `tsc`, в рантайме всё безопасно». Типы стираются; внешние данные (JSON, query, DOM) всё равно проверяют явно. `any` и неверные assertion’ы отключают защиту без падения сборки.

---

# 4. Самое главное запомнить

- TS = JS + статическая проверка; исполняется уже JS после transpile.
- Типы живут на этапе разработки и сборки, в рантайме их нет.
- `tsc` проверяет типы и может эмитить JS; Vite/webpack/esbuild часто проверяют отдельно или через плагин.
- Области: приложения, библиотеки, `.d.ts` для чужого или legacy JS.
- `.tsx` — TypeScript + JSX (React и похожие).
- Успешная сборка не заменяет валидацию внешних данных и тесты.

---

# 5. Описание

```text
исходник .ts / .tsx
  → type checker (ошибки типов)
  → transpile / emit
  → JavaScript (.js)
  → браузер / Node (типов уже нет)
```

## Зачем TypeScript в проекте

Без типов контракт функции — только договорённость в голове или в комментарии. С типами несовпадение аргумента, поля объекта или возвращаемого значения видно в IDE и на CI, пока код ещё не уехал в прод.

Типичные места применения:

| Контекст | Что даёт TS |
|---|---|
| Приложение (SPA, SSR) | Контракты props, store, API-клиент |
| Библиотека | Публичный API + `.d.ts` для потребителей |
| Миграция с JS | Постепенные `.ts` рядом с `.js`, `allowJs` |
| Чужой / legacy код | Только декларации `.d.ts`, без переписывания |

## Что происходит при сборке

Компилятор или checker строит модель типов модуля, сверяет вызовы и присваивания, затем (если emit включён) выкидывает аннотации и выдаёт JS. Сборщики вроде Vite часто транспилируют через esbuild/swc, а полную проверку типов оставляют отдельному `tsc --noEmit` в CI — быстрее feedback loop, та же семантика «типы не в бандле».

Короткий фрагмент до и после:

```ts
function greet(name: string): string {
  return `Hi, ${name}`;
}
```

После emit типы исчезают:

```js
function greet(name) {
  return `Hi, ${name}`;
}
```

## `.d.ts` и область «только типы»

Файл декларации описывает форму модуля без реализации: глобальные типы, ambient modules, типы npm-пакета. Потребитель видит автодополнение и проверку; в рантайме подключается уже JS-реализация пакета.

```ts
// greeter.d.ts
export function greet(name: string): string;
```

## Границы ответственности

TS не проверяет сеть, файлы и пользовательский ввод «сам по себе». После `JSON.parse` тип по умолчанию слишком широкий — нужна схема (zod и др.) или ручная проверка. Assertion `as User` говорит checker’у «поверь», но не меняет значение в памяти.
