# 1. Тема

**Особенности работы с браузерными событиями**

---

# 2. Главное в одну фразу

Браузерные события работают не как "вызов функции по клику", а как очередь сигналов с фазами распространения, настройками слушателя и ограничениями со стороны самого браузера.

---

# 3. Суть

> Браузерное событие - это сигнал от страницы: пользователь кликнул, начал ввод, прокрутил экран, фокус перешёл в поле, документ закончил строить DOM. На первый взгляд всё просто: повесили `addEventListener` и ждём. Но у событий есть свои правила, и именно из-за них код иногда ведёт себя "странно".
>
> Важно, что событие живёт внутри модели браузера, а не только внутри вашего компонента. Оно проходит фазы захвата, цели и всплытия, может иметь действие по умолчанию, может быть отменяемым или нет, а слушатель может сработать один раз, в фазе capture или как `passive`. Поэтому обработчик влияет не только на свой элемент, но и на поведение страницы вокруг него.
>
> На практике разработчик чаще всего упирается не в сам `click`, а в детали: почему `preventDefault()` не сработал на `scroll`, почему `focus` не всплыл, почему один и тот же `input` приходит десятки раз, почему удалённый слушатель продолжает жить. Эти особенности важны для форм, drag-and-drop, горячих клавиш, делегирования и отладки сложного UI.
>
> Полезная привычка - смотреть на событие как на контракт браузера: какой у него тип, всплывает ли оно, можно ли отменить стандартное действие, в какой момент оно приходит и кто реально является `target`. Тогда поведение интерфейса перестаёт быть магией.

---

# 4. Самое главное запомнить

- Не все события всплывают: например, `focus` и `blur` ведут себя иначе, чем `click`.
- `preventDefault()` работает только у отменяемых событий и не должен использоваться в `passive`-слушателе.
- `event.target` показывает исходный узел, а `event.currentTarget` - узел текущего обработчика.
- Один и тот же жест пользователя может породить цепочку событий: `pointerdown` -> `mousedown` -> `focus` -> `click`.
- Для `removeEventListener` важны та же функция и совместимые параметры подписки.
- Частые события вроде `scroll`, `mousemove`, `input` требуют аккуратности по производительности.

# 5. Описание

```text
Жест пользователя / изменение страницы
                |
                v
      браузер создаёт Event
                |
                v
  capture -> target -> bubble
                |
                +--> default action? (переход по ссылке, submit, scroll)
                |
                +--> listener options: capture / once / passive / signal
```

## Что у события есть кроме типа

У события есть не только `type`, но и поведение. Одни события всплывают, другие нет. Одни можно отменить через `preventDefault()`, другие уже считаются информационными и отмене не подлежат. Если эти свойства не учитывать, делегирование или перехват действий начинает ломаться в неожиданных местах.

Например, `click` обычно всплывает и хорошо подходит для одного обработчика на контейнере. А `focus` не всплывает, поэтому для делегирования чаще используют `focusin`, либо подписываются на фазу захвата.

## Почему важны опции слушателя

У `addEventListener` есть третий аргумент с настройками:

```js
const controller = new AbortController();

window.addEventListener('scroll', onScroll, {
  passive: true,
  signal: controller.signal,
});

button.addEventListener('click', handleClick, {
  once: true,
});
```

`passive: true` говорит браузеру, что обработчик не будет тормозить стандартную прокрутку вызовом `preventDefault()`. `once: true` снимает слушатель после первого вызова. `signal` удобен, когда нужно убрать сразу пачку подписок без ручного `removeEventListener`.

## Где обычно появляются ошибки

Частая ловушка - считать, что любое событие одинаково удобно для делегирования. Например, при работе с клавиатурой и фокусом важно помнить про `keydown`, `keyup`, `focusin`, `focusout`, а не только про `click`.

Ещё одна ловушка - не учитывать частоту события. `mousemove` или `scroll` могут приходить много раз за секунду, поэтому в таких обработчиках лучше избегать тяжёлых вычислений, лишних `setState` и синхронных layout-операций.

## Мини-пример с проверкой отмены

```js
link.addEventListener('click', (event) => {
  if (event.cancelable) {
    event.preventDefault();
  }

  console.log({
    type: event.type,
    target: event.target,
    currentTarget: event.currentTarget,
    cancelable: event.cancelable,
    defaultPrevented: event.defaultPrevented,
  });
});
```

Такой шаблон полезен в отладке: он сразу показывает, можно ли вообще отменять действие браузера и кто на самом деле получил событие.
