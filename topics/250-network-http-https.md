# 1. Тема

**Протоколы HTTP, HTTP/2, HTTPS**

---

# 2. Главное в одну фразу

HTTP задаёт формат запроса и ответа (метод, путь, заголовки, статус, тело); HTTP/2 ускоряет доставку тем же смыслом через бинарные фреймы и мультиплекс; HTTPS — это HTTP поверх TLS с шифрованием и проверкой сервера.

---

# 3. Суть

> **HTTP** — протокол прикладного уровня «клиент спрашивает — сервер отвечает». Запрос несёт метод (`GET`, `POST`, …), URL/путь, заголовки и опционально тело; ответ — статус (`200`, `404`, …), заголовки и тело. Семантика методов и кодов одна и та же в браузере, `fetch`, мобильном клиенте и на бэкенде.
>
> Без общего формата фронт и API не договорятся: куда слать JSON, как отличить «не найдено» от «ошибка сервера», какие заголовки кеша и авторизации уходят с запросом. **HTTP/2** не меняет этот смысл — меняет *транспорт*: вместо текстовых сообщений по очереди на соединении идут бинарные фреймы и несколько потоков сразу. **HTTPS** добавляет TLS: трафик шифруется, клиент проверяет сертификат сервера; в браузере «замочек» и cookie с флагом `Secure` опираются именно на это.
>
> Как это стыкуется на практике. Клиент открывает TCP (и при HTTPS — TLS), по ALPN часто договаривается о `h2` или `http/1.1`, затем шлёт HTTP-сообщения. Заголовки вроде `Content-Type`, `Authorization`, `Cache-Control` несут метаданные; тело — полезную нагрузку. Сервер отвечает классом статуса: `2xx` успех, `3xx` перенаправление, `4xx` ошибка клиента, `5xx` ошибка сервера.
>
> Ловушка: путать «сайт открылся по HTTPS» с «API безопасен» — TLS закрывает канал, но не заменяет auth, валидацию и правильные статусы. И наоборот: понимать REST-ресурсы полезно, но это уже модель API поверх HTTP, а не сам протокол. HTTP/2 не отменяет необходимость осмысленных методов и заголовков — он только убирает часть сетевых узких мест HTTP/1.1.

---

# 4. Самое главное запомнить

- Сообщение HTTP = стартовая строка + заголовки + опциональное тело.
- Метод говорит *намерение* (`GET` читать, `POST` создавать/действовать); статус — *итог*.
- Классы статусов: `2xx` / `3xx` / `4xx` / `5xx` — читать по сотням, не заучивать все коды.
- HTTP/1.1: текстовый протокол; на одном соединении легко упереться в head-of-line (ответы ждут друг друга).
- HTTP/2: бинарные фреймы, мультиплекс потоков, сжатие заголовков (HPACK); семантика методов/статусов та же.
- HTTPS = HTTP + TLS: шифрование + подлинность сервера (сертификат); без TLS заголовки и тела видны в сети.

| Слой | Что даёт |
|------|----------|
| HTTP | Смысл: метод, путь, заголовки, статус, тело |
| HTTP/2 | Эффективная доставка того же смысла по одному соединению |
| HTTPS | Защита канала (TLS), не замена прикладной безопасности |

# 5. Описание

```text
Клиент                         Сеть / TLS                    Сервер
  │  ── TCP (+ TLS, если HTTPS) ──────────────────────────►  │
  │  ── HTTP request ─────────────────────────────────────►  │
  │     метод + путь + заголовки [+ тело]                    │
  │  ◄─ HTTP response ─────────────────────────────────────  │
  │     статус + заголовки [+ тело]                          │
```

При HTTPS между «TCP» и «HTTP request» появляется рукопожатие TLS; поверх уже защищённого канала идут те же HTTP-сообщения (часто уже как HTTP/2).

## HTTP: запрос и ответ

Типичный запрос (упрощённо, как в HTTP/1.1):

```http
GET /api/users/42 HTTP/1.1
Host: api.example.com
Accept: application/json
Authorization: Bearer …
```

Ответ:

```http
HTTP/1.1 200 OK
Content-Type: application/json
Cache-Control: private, max-age=60

{"id":42,"name":"Ada"}
```

- **Стартовая строка запроса:** метод + путь (+ версия в HTTP/1.x).
- **Заголовки:** метаданные (`Host`, `Content-Type`, `Authorization`, `Cookie`, кеш…).
- **Тело:** есть у `POST`/`PUT`/`PATCH` и у многих ответов; у `GET` обычно нет.

В DevTools → Network видно метод, статус, timing, request/response headers — это основной способ «пощупать» протокол в браузере.

## Методы и статусы (без ухода в REST)

Метод — глагол намерения. Частые:

| Метод | Типичный смысл |
|-------|----------------|
| `GET` | Прочитать ресурс / данные |
| `POST` | Создать или выполнить действие |
| `PUT` / `PATCH` | Заменить / частично обновить |
| `DELETE` | Удалить |
| `OPTIONS` | Узнать допустимые методы / CORS preflight |

Статус читают **классом**:

- `2xx` — успех (`200` OK, `201` Created, `204` No Content).
- `3xx` — нужен другой URL (`301`/`302`, `304` Not Modified).
- `4xx` — проблема на стороне клиента (`400`, `401`, `403`, `404`).
- `5xx` — сервер не смог (`500`, `502`, `503`).

Клиентский код должен ветвиться по статусу: `404` — «нет ресурса», не то же самое, что сеть упала или CORS заблокировал ответ до JS.

## HTTP/1.1 и узкое место

В HTTP/1.1 сообщение — текст. Браузер открывает несколько TCP-соединений к одному хосту, но на каждом ответы по сути выстраиваются в очередь: долгий ответ блокирует следующие на том же соединении (**head-of-line blocking** на уровне HTTP). Отсюда исторические обходы: спрайты, домены-шарды, склейка файлов.

```text
HTTP/1.1 (одно соединение):
  req A ──►  …ждём ответ A…  ──► req B ──► …
             ▲ HOL: B не уходит, пока A не завершён
```

## HTTP/2: тот же HTTP, другой провод

HTTP/2 сохраняет методы, статусы и заголовки как понятия, но кодирует обмен **бинарными фреймами**. На одном TCP-соединении параллельно живут **потоки (streams)** — мультиплекс: маленькие ответы не ждут огромный файл на соседнем потоке.

```text
HTTP/2 (одно соединение, несколько streams):
  stream 1: ████░░░░  (HTML)
  stream 3: ███░░░░░  (CSS)     ← кадры перемешаны на проводе
  stream 5: ██░░░░░░  (API JSON)
```

Дополнительно: сжатие заголовков (**HPACK**), сервер может **push** (на практике в вебе почти не используют / отключают). Переход на h2 не отменяет необходимость правильных `Cache-Control` и разумной нарезки ресурсов — он убирает часть транспортных костылей HTTP/1.1.

В Network иногда видно `Protocol: h2` / `http/1.1` — это результат переговоров (часто через **ALPN** внутри TLS).

## HTTPS = HTTP поверх TLS

```text
[ HTTP messages ]
[ TLS record / handshake / сертификат ]
[ TCP ]
[ IP ]
```

**TLS** даёт:

1. **Шифрование** — сниффер в кафе не читает тело и заголовки как открытый текст.
2. **Подлинность сервера** — цепочка сертификатов до доверенного CA (или своего корпоративного корня).
3. **Целостность** — подмена байтов по пути детектируется.

HTTP без TLS на публичной сети — логины, токены и cookie уходят открытым текстом. Флаг cookie `Secure` как раз требует HTTPS. Локальная разработка часто идёт по `http://localhost` — исключение браузеров для удобства, не модель продакшена.

HTTPS **не** заменяет: проверку прав на API, защиту от XSS/CSRF, валидацию входа. Это слой канала, не прикладная политика.

## Связь с соседними темами

- Path и **query** — части URL внутри HTTP-запроса (отдельная тема про query).
- **REST** — соглашение, *как* раскладывать ресурсы и методы поверх HTTP.
- **WebSocket / SSE / long-poll** — другие модели доставки поверх или рядом с HTTP.
- Ниже по стеку — TCP/IP; HTTP/2 всё ещё сидит на TCP (QUIC/HTTP/3 — следующий шаг, вне этой темы).
