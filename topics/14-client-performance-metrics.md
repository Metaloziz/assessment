# 1. Тема

**Метрики клиентской производительности**

---

# 2. Главное в одну фразу

Core Web Vitals измеряют, как пользователь видит страницу: когда появляется главное (LCP), как быстро откликается ввод (INP) и не прыгает ли вёрстка (CLS); лабораторный прогон не заменяет полевые данные.

---

# 3. Суть

> Клиентские метрики описывают не «насколько быстрый сервер», а что происходит в браузере: когда человек увидел главный контент, успел ли интерфейс ответить на клик и не уехала ли кнопка под пальцем. Ядро — **Core Web Vitals**: `LCP` (Largest Contentful Paint), `INP` (Interaction to Next Paint) и `CLS` (Cumulative Layout Shift).
>
> Их смотрят, потому что ощущение «сайт тормозит» плохо ловится одним `TTFB` или размером бандла. Поздний `LCP` часто значит, что hero-ресурс пришёл поздно; плохой `INP` — long tasks на main thread; `CLS` — картинки и баннеры без зарезервированного места. Пороги «хорошо» у Google: `LCP` ≤ 2.5 с, `INP` ≤ 200 мс, `CLS` ≤ 0.1 — ориентир по 75-му процентилю, не магия.
>
> Считают через Performance API и библиотеку `web-vitals`: браузер отмечает моменты отрисовки и ввода. **Lab** — один прогон в Lighthouse или DevTools на вашем железе и сети. **Field** — выборка реальных сессий (RUM, Chrome UX Report) с устройствами и сетями, которые вы не контролируете.
>
> Ловушка: зелёный Lighthouse на ноутбуке не гарантирует поле. `FID` снят с Core Web Vitals — смотрят `INP`. Оптимизируют причину метрики (LCP-элемент, long task, сдвиг), а не «накрутку» score.

---

# 4. Самое главное запомнить

- Core Web Vitals = `LCP` (главный контент) + `INP` (отзывчивость) + `CLS` (стабильность layout).
- Порог «хорошо»: `LCP` ≤ 2.5 с, `INP` ≤ 200 мс, `CLS` ≤ 0.1; в field смотрят 75-й процентиль, не среднее.
- Lab (Lighthouse / DevTools) — синтетика на одном устройстве; Field (RUM / CrUX) — реальные сессии.
- `FID` устарел: в CWV его заменил `INP` (почти все взаимодействия, не только первый клик).
- Рядом, но не CWV: `FCP` (первая отрисовка), `TTFB` (первый байт HTML), TBT / long tasks (занятость main thread).
- Чинят причину: приоритет LCP-ресурса, меньше JS на критическом пути, размеры медиа и слоты под баннеры.

---

# 5. Описание

```text
навигация
  → TTFB   первый байт HTML
  → FCP    первая отрисовка
  → LCP    самый крупный видимый элемент     ← CWV
  → ввод (клик / тап / клавиша) → INP        ← CWV
  → сдвиги layout за жизнь страницы → CLS    ← CWV

источники данных
  Lab   = Lighthouse / DevTools   (один контролируемый прогон)
  Field = RUM / CrUX              (выборки реальных сессий)
```

## Core Web Vitals

Это три метрики, которые Google считает ключевыми для UX загрузки, отзывчивости и визуальной стабильности. Они не покрывают всё (память, FPS игры, размер бандла), но дают общий язык: «страница стала видимой, отвечает на ввод, не прыгает».

Пороги одинаковы в lab и в field; отличается **откуда** берётся число. В Search Console и CrUX смотрят **75-й процентиль** полевых сессий: если у четверти пользователей `LCP` хуже 2.5 с, страница не в «хорошо», даже если у вас локально 1.2 с.

## LCP — когда видно главное

`LCP` — момент, когда отрисован **самый крупный** элемент в viewport: обычно `<img>`, poster видео, фоновая картинка через CSS или крупный текстовый блок. Это не «вся страница готова» и не первая палочка `FCP`: мелкий логотип может нарисоваться рано, а hero-баннер — через несколько секунд.

Типичные причины плохого `LCP`:

- картинка-герой без приоритета (`fetchpriority="high"` / `preload`), ленивая загрузка LCP-элемента;
- блокирующий CSS/JS до отрисовки;
- медленный `TTFB` — HTML пришёл поздно, считать LCP ещё не из чего.

```js
import { onLCP } from 'web-vitals';

onLCP((metric) => {
  console.log(metric.value, metric.entries); // ← элемент-кандидат в entries
});
```

## INP — отзывчивость на ввод

`INP` измеряет задержку от клика, тапа или нажатия клавиши до **следующей отрисовки**. В выборку попадают почти все взаимодействия за визит; в отчёт идёт высокое значение (не среднее «по всем кликам»).

`FID` (First Input Delay) смотрел только **первую** паузу до начала обработки события и больше не входит в Core Web Vitals. Страница может быстро ответить на первый клик и потом «зависнуть» на тяжёлом хендлере — `INP` это поймает, `FID` нет.

Плохой `INP` почти всегда = long task на main thread: тяжёлый обработчик, большой JSON.parse, лишний layout в событии. Чинят разделением работы (`scheduler.yield`, `requestIdleCallback`, web worker), а не «ещё одним `useMemo` вокруг всего дерева».

## CLS — страница не должна прыгать

`CLS` суммирует **неожиданные** сдвиги layout: элемент, который уже был на экране, внезапно уехал. Вклад сдвига = доля затронутой площади × дистанция перемещения. Сдвиг в ответ на клик (открыли аккордеон) в окне ~500 мс обычно не считается неожиданным.

Классика: `<img>` без `width`/`height`, веб-шрифт, из-за которого текст перестраивается, рекламный слот нулевой высоты, в который потом вставляется баннер. Лечится резервом места, а не «запретом анимаций».

```html
<img src="hero.webp" width="1200" height="630" alt="" />
<!-- ← место в потоке известно до загрузки файла -->
```

## Lab и Field

| | Lab | Field |
|---|---|---|
| Откуда | Lighthouse, DevTools Performance, локальный прогон | RUM (`web-vitals` → свой бэк), CrUX |
| Условия | Одно устройство, сеть, кэш, которые вы задали | Реальные телефоны, 3G/Wi‑Fi, холодный/тёплый кэш |
| Зачем | Воспроизвести и отладить причину | Понять, что видят пользователи |

Lab удобен, потому что прогон повторяемый: выключили JS на критическом пути — `LCP` в отчёте изменился. Field нужен, потому что 90-й процентиль на слабом Android может не иметь ничего общего с вашим MacBook. PSI (PageSpeed Insights) показывает **оба** среза: лабораторный аудит и поле CrUX, если URL достаточно посещаемый.

```js
import { onINP, onCLS } from 'web-vitals';

function sendToRum(metric) {
  navigator.sendBeacon('/rum', JSON.stringify(metric));
}

onINP(sendToRum);
onCLS(sendToRum);
```

## Рядом с CWV

Эти метрики помогают **найти причину**, но сами по себе не Core Web Vitals:

- **`FCP`** — первая отрисовка чего-либо. Ранний FCP и поздний LCP = «показали оболочку, главное ещё едет».
- **`TTFB`** — время до первого байта HTML. Высокий TTFB часто серверный (тема про серверные метрики), не «тяжёлый React».
- **TBT / long tasks** — насколько main thread занят в lab-прогоне. Связаны с `INP`, но это синтетика, не полевой INP.

Размер бандла, CDN и lazy-loading влияют на эти числа, но это уже рычаги соседних тем, не сами метрики.
