# 1. Тема

**Подходы к определению легаси кода**

---

# 2. Главное в одну фразу

«Легаси» — не синоним «старому коду»: это код, с которым **дорого и рискованно менять поведение**; команда выбирает рабочее определение (тесты, стек, трение изменений), а не ярлык по календарю.

---

# 3. Суть

> Универсального определения легаси нет — важно **договориться в команде**, по каким признакам планируют работу: где нужны тесты, где strangler, где адаптер, а что можно не трогать.
>
> Классика Michael Feathers: **легаси = код без тестов**, через который вы боитесь провести изменение. Возраст и «не мы писали» сами по себе не решают — молодой модуль без покрытия тоже легаси в этом смысле.
>
> Другие линзы: **устаревший стек** (EOL runtime, неподдерживаемые зависимости), **трение изменений** (долгий lead time, tribal knowledge, нет владельца), **бизнес-контекст** (критичен для выручки, но дорог в эволюции). Один и тот же файл может быть «нормальным» по одной шкале и легаси по другой.
>
> Ловушка: называть легаси всё подряд или, наоборот, откладывать работу, потому что «код же работает». Критерии нужны, чтобы приоритизировать **страховку** (тесты, обёртки) и **постепенную замену**, а не для моральной оценки авторов.

---

# 4. Самое главное запомнить

- Feathers: легаси ≈ **нет тестов** + страх менять поведение, а не «написано в 2010».
- Возраст и «чужой код» — слабые критерии сами по себе; смотрят вместе с риском и стоимостью изменения.
- Устаревший стек — отдельная ось: EOL, CVE без патчей, несовместимость с текущим toolchain.
- Один модуль может быть «свежим» по дате и «легаси» по отсутствию тестов — и наоборот.
- Договорённость команды: **явные пороги** (покрытие, deps, lead time) лучше споров «это же legacy».
- План действий зависит от линзы: тесты и seam’ы, strangler, adapter, freeze — не один рецепт «переписать».

| Линза | Вопрос | Типичный сигнал «легаси» |
| --- | --- | --- |
| Feathers | Можно ли безопасно изменить? | Нет тестов / нет seam’ов, каждый diff — лотерея |
| Стек | Жив ли контракт с платформой? | EOL Node, jQuery 1.x, deps без security-fix |
| Трение | Сколько стоит доставить изменение? | Недели на мелкий фикс, один «хранитель» знаний |
| Бизнес | Что теряем, если сломаем? | Критичный revenue-path при высокой сложности |

---

# 5. Описание

```text
модуль в репозитории
  → выбранная линза (тесты / стек / трение / бизнес)
  → признаки по этой шкале
  → вердикт для планирования (страховка · strangler · adapter · freeze)
  → не путать с «моральной оценкой» кода
```

## Определение Feathers (тесты и страх изменений)

В *Working Effectively with Legacy Code* легаси — код **без автоматических тестов**, который сложно менять без регрессий. Старый, но покрытый модуль в этой модели **не** легаси: у вас есть обратная связь при рефакторинге.

Практический след:

- сначала **characterization tests** или тонкий интеграционный контур вокруг seam’а;
- затем рефакторинг под зелёными тестами (см. темы про принципы рефакторинга в группе);
- «переписать с нуля» без страховки — другой риск, не замена определения.

Молодой сервис без единого теста на критичный путь — легаси по Feathers, даже если написан вчера.

## Возраст и «не мы писали»

«Старому коду» часто не доверяют эмоционально, но **возраст не доказывает** плохое качество. Полезный вопрос не «когда закоммитили», а «сколько стоит понять и изменить сейчас».

«Не мы писали» — про **ownership и bus factor**: если ушли авторы и нет документации/тестов, трение растёт. Это пересекается с линзой трения, а не заменяет определение Feathers.

## Устаревший стек и зависимости

Отдельная линза — **технический долг платформы**:

- runtime/framework без security-патчей;
- библиотеки, которые нельзя обновить без ломающего рефакторинга;
- toolchain (сборка, CI) не поддерживает текущие стандарты.

Здесь легаси ближе к **риску эксплуатации**, чем к читаемости. Модуль может быть понятным, но всё равно требовать миграции, потому что jQuery-плагин или AngularJS 1.x больше не вписываются в целевой стек.

## Трение изменений и comprehension debt

Признаки:

- мелкий баг → недели согласований и «раскопок»;
- правки только через одного человека;
- побочные эффекты в неожиданных местах (глобалы, implicit I/O).

Это близко к «грязному коду», но фокус на **стоимости изменения**, а не на стиле. Читаемый, но не покрытый тестами модуль всё ещё легаси по Feathers; нечитаемый, но с тестами — больно поддерживать, но менять можно предсказуемее.

## Бизнес-контекст

Продуктовый взгляд: модуль **критичен для выручки** и одновременно **дорог в эволюции**. Тогда решение — не «переписать всё», а:

- изолировать seam (adapter, anti-corruption layer);
- strangler — новый путь рядом со старым;
- freeze — явно не трогать, кроме P0, пока не построен обход.

«Работает в проде» не отменяет легаси-статус, если следующая фича блокируется страхом и сроками.

## Как договориться в команде

Минимальный рабочий набор:

1. **Зафиксировать линзу** для приоритизации (часто Feathers + стек для security).
2. **Пороги** — например: «критичный путь без тестов = backlog страховки», «deps с CVE > 7 = миграция в квартал».
3. **Не смешивать** вердикт с action: «легаси» ≠ «удалить завтра»; это триггер для плана.

Пример фрагмента критериев (не стандарт, а шаблон):

```markdown
## Легаси по Feathers
- нет автотестов на модуль И он в top-20 по частоте изменений
→ сначала characterization test на seam

## Легаси по стеку
- зависимость без патча > 90 дней И используется в prod
→ adapter или замена в roadmap
```

## Сопоставление двух модулей

| Признак | `billing/legacyProcessor.js` | `checkout/CheckoutForm.tsx` |
| --- | --- | --- |
| Год появления | 2014 | 2023 |
| Стек | jQuery 1.x | React 18 |
| Тесты | нет | ~82% на критичный путь |
| Lead time мелкого фикса | недели | дни |
| Feathers | легаси | нет (есть страховка) |
| Стек | легаси (EOL-слой) | актуальный |
| Трение | высокое | низкое |

Один репозиторий — разные вердикты по разным линзам; спор «легаси или нет» обычно значит «мы говорим о разных шкалах».
