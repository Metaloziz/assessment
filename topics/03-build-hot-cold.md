# 1. Тема

**Механизмы ускорения горячей/холодной сборки проекта**

---

# 2. Главное в одну фразу

Пока вы правите код, нужна быстрая «горячая» пересборка только изменённого; перед выкладкой на прод — полная «холодная» сборка, которую ускоряют кэшем и быстрыми инструментами.

---

# 3. Суть

> Когда вы запускаете `npm run dev`, проект **собирается** — исходники превращаются в то, что понимает браузер. Вы сохраняете файл и ждёте, что изменение быстро появится на экране. Это **горячая сборка** (hot): важна скорость после каждого save.
>
> Когда вы делаете `npm run build` или pipeline на CI собирает релиз — это **холодная сборка** (cold): пересобирается всё приложение «с нуля», часто без dev-сервера. Здесь важны итоговый размер, и то, чтобы повторная сборка не занимала столько же, сколько самая первая.
>
> Рычаги разные. В dev помогают **HMR** (Hot Module Replacement — подмена только изменившегося модуля без полной перезагрузки страницы) и пересборка не всего проекта, а только связанных файлов. В prod и на CI помогают **кэш на диске** (webpack запоминает уже посчитанное), быстрые компиляторы вроде **esbuild** и **SWC**, а в больших монорепо — инструменты вроде Turborepo, которые не пересобирают то, что не менялось.
>
> Ловушка для новичка: включить «всё для скорости» сразу везде. Тяжёлое сжатие кода в dev только тормозит правки; без кэша каждая полная сборка на CI снова «как в первый раз». Сначала поймите, что вы ускоряете — dev после save или prod на сервере.

---

# 4. Самое главное запомнить

- **Горячая** — пока разрабатываете: сохранили файл → быстро увидели результат.
- **Холодная** — полная сборка для prod или CI: дольше, но нужна перед выкладкой.
- **HMR** обновляет кусок страницы без полной перезагрузки; state формы может сохраниться.
- Повторный `build` быстрее первого, если включён **кэш webpack** на диске.
- **Vite** в dev часто стартует быстро: отдаёт файлы по запросу, а не собирает всё заранее.
- Не сравнивайте инструменты «в целом» — смотрите отдельно на dev и на prod.

---

# 5. Описание

```text
ГОРЯЧАЯ (dev)                         ХОЛОДНАЯ (prod / CI)
сохранили файл                         npm run build
    ↓                                      ↓
пересобрали только связанные файлы     есть кэш на диске?
    ↓                                   ↙              ↘
HMR — патч в браузер               нет → полная работа   да → быстрее
```

## Горячая сборка — когда вы в dev

Представьте, что вы правите одну кнопку на странице. Не нужно каждый раз заново «варить» весь сайт — достаточно обновить то, что зависит от этой кнопки.

**HMR** — dev-сервер шлёт в браузер только изменившийся модуль. Страница не перезагружается целиком, поэтому введённый в форму текст может остаться на месте. Если HMR не сработал, браузер делает обычную перезагрузку — тогда state сбросится.

**Webpack** в dev следит за файлами (`watch`) и может игнорировать `node_modules`, чтобы не тратить время на чужие пакеты. **Lazy compilation** — идея «не собирать страницу, пока вы на неё не зашли».

**Vite** устроен иначе: в dev он не склеивает всё приложение в один большой файл заранее, а отдаёт модули браузеру по запросу. Тяжёлые библиотеки (React и т.п.) один раз подготавливает через esbuild.

```text
изменили Button.tsx
  → пересобрали Button и то, что от него зависит
  → браузер получил обновление (HMR)
```

## Холодная сборка — prod и CI

Перед выкладкой нужен финальный набор файлов в папке `dist/`: сжатый, без лишнего dev-кода. Это всегда **полная** работа — её и называют холодной.

Первый такой прогон самый долгий. Второй и следующие могут быть короче, если бандлер **сохранил промежуточный результат на диск**. В Webpack 5 для этого есть `cache: { type: 'filesystem' }`.

Чтобы ускорить саму обработку кода, вместо медленной цепочки инструментов часто ставят **esbuild** или **SWC** — они быстрее переводят TypeScript/JSX в обычный JavaScript. На CI ещё кешируют `node_modules` и папку с кэшем сборки, чтобы не качать и не пересчитывать одно и то же каждый раз.

| Инструмент | Зачем новичку знать |
|------------|---------------------|
| Vite | Быстрый старт в dev |
| Webpack + cache на диске | Повторный `build` не «с нуля» |
| esbuild / SWC | Быстрая обработка кода |
| Turborepo / Nx | В монорепо не пересобирают лишние пакеты |

## Как понять, что реально тормозит

Не включайте настройки «наугад». Засеките три вещи:

1. **Cold start** — сколько ждёте первый `build` или `dev` с пустым кэшем.
2. **Hot update** — сколько от save до изменения на экране.
3. **Повторный build на CI** — быстрее ли второй прогон, когда кэш уже есть.

Если медленно только после save — крутите dev (HMR, Vite, lazy). Если медленно на CI — кэш, быстрый transpile, affected builds.
