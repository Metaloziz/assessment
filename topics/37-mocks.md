# 1. Тема
**Моки**
---
# 2. Главное в одну фразу
Мок заменяет зависимость в тесте и позволяет контролируемо проверить, как тестируемый код с ней взаимодействует.
---
# 3. Ответ для собеседования
> «Моки нужны, чтобы unit-тест не зависел от сети, БД, файловой системы или стороннего сервиса. Я подменяю зависимость и проверяю наблюдаемое взаимодействие: была ли она вызвана, сколько раз и с какими аргументами. Не мокирую всё подряд: чрезмерные моки привязывают тест к реализации и могут дать зелёный тест при неработающей интеграции.»
---
# 4. Самое главное запомнить
- Mock: проверяем взаимодействие.
- Stub: возвращает заранее заданные данные.
- Spy: наблюдает за вызовами существующей функции.
- `toHaveBeenCalledWith` проверяет контракт вызова.
---
# 5. Описание
| Двойник | Главный вопрос | Пример |
|---|---|---|
| Mock | «Вызвали ли зависимость правильно?» | `logger.info` получил событие |
| Stub | «Какие данные вернёт зависимость?» | репозиторий вернул пользователя |
| Spy | «Как вызвали реальную функцию?» | `jest.spyOn(console, 'warn')` |

```javascript
test('запрашивает пользователя по правильному пути', async () => {
  // Arrange
  const api = { get: jest.fn().mockResolvedValue({ data: { id: 42 } }) };
  const service = new UserService(api);

  // Act
  const user = await service.getUser(42);

  // Assert
  expect(user).toEqual({ id: 42 });
  expect(api.get).toHaveBeenCalledWith('/users/42');
  expect(api.get).toHaveBeenCalledTimes(1);
});
```

`mockResolvedValue` удобен для успешного async-ответа, `mockRejectedValue` — для ветки ошибки. После теста сбрасывайте общее состояние: `jest.clearAllMocks()` или настройка `clearMocks: true`.

Проверяйте взаимодействие, когда оно является частью контракта: отправка письма, запись события аудита, вызов платёжного шлюза. Для чистой функции лучше проверить результат, а не внутренние вызовы.
