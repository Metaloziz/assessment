# 1. Тема

**Компоненты: Props, State, однонаправленный поток данных**

---

# 2. Главное в одну фразу

Props — входные данные сверху, state — локальная память компонента; UI обновляется, когда меняются они, а данные текут вниз по дереву, а события — вверх через колбэки.

---

# 3. Суть

> В React у компонента два главных источника данных для отрисовки. **`props`** — то, что передали *снаружи* (родитель): текст, флаги, колбэки, дети. Считаются неизменяемыми с точки зрения получателя: дочерний компонент их не «правит», а использует. **`state`** — данные, которыми компонент *владеет сам* (через `useState` / `useReducer` или `this.state` в классе): счётчик, открыта ли модалка, черновик поля.
>
> Зачем разделять: props делают компонент настраиваемым и переиспользуемым, state — интерактивным. Если всё тащить только в props, родитель раздувается; если всё держать в локальном state далеко внизу, соседям нечем поделиться. Практическое правило: state живёт в ближайшем общем предке тех, кому он нужен (**lifting state up**).
>
> Поток **однонаправленный**: данные вниз (`props`), намерения изменить данные — вверх (`onChange`, `onSubmit`). Родитель обновляет state → дети получают новые props → дерево перерисовывается согласованно. Нет двусторонней «магии» вроде `ng-model` между произвольными узлами.
>
> Ловушка: мутировать props или state напрямую (`props.x = …`, `state.items.push`) — React не увидит смену ссылки/снимка как надо. State обновляют через setter/`setState` новым значением (или функцией от предыдущего). Props «изменить снизу» нельзя — только попросить родителя через колбэк.

---

# 4. Самое главное запомнить

- `props` — вход с родителя, только для чтения внутри ребёнка.
- `state` — локальные данные владельца; смена → повторный render.
- Данные вниз, события вверх (колбэки в props).
- Общий state поднимают к ближайшему общему родителю.
- Не мутировать: новый объект/массив или функциональный `setState`.
- `key` у списка влияет на тождество state между рендерами, не путать с props `id`.

# 5. Описание

```text
        Parent (state: query)
           │  props: value, onChange
           ▼
        SearchInput
           │  пользователь печатает
           ▼
        onChange(newValue) → setQuery → новый render Parent → новые props
```

## Props

```jsx
function UserCard({ name, role }) {
  return (
    <article>
      <h2>{name}</h2>
      <p>{role}</p>
    </article>
  );
}

<UserCard name="Ира" role="редактор" />
```

Любое выражение в `{}` — JavaScript. Дети (`children`) тоже props. Менять `name` внутри `UserCard` нельзя — только родитель передаст другое значение.

## State

```jsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);
  return (
    <button type="button" onClick={() => setCount((c) => c + 1)}>
      {count}
    </button>
  );
}
```

`useState` возвращает текущее значение и функцию обновления. После `setCount` React планирует новый render этого компонента (и потомков, если их props/context зависят от изменения).

## Controlled input — связка props + state

```jsx
function Search({ query, onQueryChange }) {
  return (
    <input
      value={query}
      onChange={(e) => onQueryChange(e.target.value)}
    />
  );
}
```

Значение поля живёт в родителе; инпут только отображает и сообщает о вводе. Так один `query` могут читать и список результатов, и URL, и кнопка «Очистить».

## Props vs state

| | Props | State |
| --- | --- | --- |
| Кто задаёт | родитель (или обёртка) | сам компонент |
| Можно ли писать внутри | нет | только через setter |
| Типичный пример | `title`, `onSave` | `isOpen`, черновик формы |
| Переиспользование | настройка снаружи | поведение «внутри» |

## Однонаправленный поток

1. Пользователь кликает / печатает.
2. Обработчик вызывает `setState` или колбэк родителя.
3. Владелец state обновляет данные.
4. React пересчитывает дерево с новыми props/state.
5. DOM приводится к новому описанию.

Двусторонняя связь между дальними узлами без общего предка или внешнего store ломает предсказуемость: непонятно, кто источник истины.

## Частые ошибки

- Копировать props в state «на всякий случай» и забыть синхронизировать при смене props.
- Использовать state там, где достаточно вычислить значение из props при render.
- Обновлять state исходя из старого значения так: `setCount(count + 1)` в цикле событий — лучше `setCount((c) => c + 1)`.
