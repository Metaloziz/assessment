# Как писать темы assessment

Проектный скилл (`skills/` в корне репо, не в `.cursor`). Полные правила — [`TOPIC_FORMAT.md`](../../TOPIC_FORMAT.md).

Связанный скилл лаб: [`write-assessment-labs`](../write-assessment-labs/SKILL.md).

## Источники истины (читать перед работой)

1. [`TOPIC_FORMAT.md`](../../TOPIC_FORMAT.md) — структура, «Суть», Описание, ссылки, стык с лабой.
2. [`LAB_FORMAT.md`](../../LAB_FORMAT.md) + [`write-assessment-labs`](../write-assessment-labs/SKILL.md) — если нужна лаба.
3. Метаданные: [`app/src/content/groups.ts`](../../app/src/content/groups.ts) — группа, уровень, `sortInGroup`.

### Тема всегда связана с группой

Тема **всегда** относится к своей группе (`groupId` в `TOPIC_META`): охват «Сути», Описания и лабы — внутри предметной области группы, не соседней.

Перед написанием / рерайтом:

1. Открыть `TOPIC_GROUPS` — title группы (`ts` → «TS», `react` → «React», …).
2. Посмотреть соседние темы той же `groupId` в `TOPIC_META` — что уже покрыто, где границы.
3. Держать контент в рамках группы; не уводить в другую группу (например, тема в `ts` — про TypeScript, не про React-хуки как центр; тема в `network` — про сеть, не про общий JS-синтаксис).

Если заголовок/запрос явно не стыкуется с группой — **остановись** и уточни у пользователя группу или формулировку, не пиши «как получится».

Правило Cursor `.cursor/rules/topic-format.mdc` только отсылает сюда и к `TOPIC_FORMAT.md` — **не дублируй** длинные правила в новых местах.

## Когда что делать

| Запрос | Действия |
|--------|----------|
| Новая тема / группа | `topics/NNN-….md` + запись в `TOPIC_META` / при необходимости группа в `TOPIC_GROUPS` |
| Только теория | junior → **без** лабы, пока явно не попросили |
| middle / senior | теория **+ лаба** по скиллу лаб; проводка `hasLab` в `parseTopicMd.ts` и `TopicPage.tsx` |
| Правка одной темы | тяни качество к эталонам; **не** массовый рерайт всех файлов |
| Старый «Ответ для собеседования» | заменить на `# 3. Суть`; убрать подразделы «ответ на собесе» |

Имена файлов: `NNN-slug.md`, номер = префикс id (как `140-project-prod-dev-plugins`). Уровень **только** в `groups.ts`, не в заголовке markdown.

## Структура `topics/*.md` (обязательна)

Заголовки секций буквальные — парсер режет по `# 1.` … `# 6.`:

```markdown
# 1. Тема
**Заголовок**

# 2. Главное в одну фразу
Одна плотная фраза.

# 3. Суть
> абзац
>
> абзац
>
> …

# 4. Самое главное запомнить
- буллеты или короткая таблица

# 5. Описание
## Подразделы, схемы, примеры кода

# 6. Ссылки
- [название](url)
```

Язык: **русский**. Тон: учёба и практика в коде — **не** найм / собеседования.

Текст темы — **для человека, который учится**, не для RFC и не для шпаргалки акронимами. Подробности — § «Человекочитаемый текст» ниже и в `TOPIC_FORMAT.md`.

Теория объясняет; лаба на экране показывает **одну** схему. Кластер паттернов — переключателем, не полотном. Не копировать всё «Описание» в стенд.

### Запрещённая лексика

Не писать: собеседование, интервью, interview, кандидат, оффер, «часто спрашивают», «как отвечать», «шпаргалка к интервью» и т.п. (полный список — в `TOPIC_FORMAT.md`).

## Оформление разделов

- **1 «Тема»:** заголовок **использовать как есть** — ровно тот, что в списке тем / Notion / задании пользователя. **Нельзя** дополнять охватом (`· Stage 3 · …`), уточнениями, списком подтем. Охват — в §2–§5 и в лабе, не в `# 1`. Пример: для темы про TS-декораторы заголовок — `**Декораторы**`, не `**Декораторы · Stage 3 · factories**`.
- **2:** одна **человеческая** фраза (механизм + зачем), не список терминов через запятую.
- **3 «Суть»:** один `>`; 2–4 абзаца **что → зачем → как → ловушка**; ~80–160 слов (широкая — до ~200–220); не буллеты, не копия §2; **сначала своими словами**, термин — в той же фразе.
- **4:** 4–7 проверяемых утверждений **простым языком**, не слоганы и не телеграф `A ≠ B ≠ C`.
- **5:** если есть поток — ASCII-схема (` ```text `) **сразу**; затем `##` с **абзацами**, не каталог API. Рендерер не рисует mermaid. Термины в `` `code` `` после расшифровки. Код короткий.
- **6:** 3–6 первоисточников (spec / MDN / официальные доки).

Чеклист «Сути»:

- [ ] что / зачем / как на месте
- [ ] читается вслух ~за минуту **без спотыкания о необъяснённый жаргон**
- [ ] нет лексики собеседований и «я бы…»
- [ ] `# 3. Суть` именно так
- [ ] детали вынесены в Описание, если раздулось

## Человекочитаемый текст (обязательно)

Читатель — человек, который **учит механизм**, не справочник. Senior/middle **не** значит «больше акронимов». Глубина — в точности и ловушках, не в плотности RFC.

**Как писать**

1. Сначала житейская фраза («телефонная книга», «пока нет адреса — соединяться некуда»), потом имя из спеки в `` `code` ``.
2. Один главный образ на тему. Не три метафоры подряд.
3. «Описание» — связные абзацы вокруг схемы: зачем, что происходит, что ломается. Таблица — 2–4 контраста, не замена текста.
4. Заголовок вроде «Базовое понимание …» / просьба «общее понимание» / «простыми словами» — **большая картина** (что встречает разработчик), не каталог внутренних ролей, типов записей, кодов ошибок.
5. Соседние темы не тащить внутрь «на всякий случай»: хватит одной отсылки («подробности адреса — тема IP»).

**Плохо** (телеграф / справочник):

> Stub спрашивает рекурсор; при cache miss цепочка root → TLD → authoritative. NXDOMAIN ≠ SERVFAIL ≠ `ETIMEDOUT`.

**Хорошо** (тот же DNS, общее понимание):

> Вы пишете `api.example.com`, компьютеру нужен IP. DNS отвечает «у этого имени такой адрес». Пока адреса нет, сайт не откроется — это не то же самое, что «сервер лежит».

Полные правила и ещё примеры — [`TOPIC_FORMAT.md`](../../TOPIC_FORMAT.md) § «Человекочитаемый текст».

## Лаба (middle / senior)

Читай [`write-assessment-labs`](../write-assessment-labs/SKILL.md) и [`LAB_FORMAT.md`](../../LAB_FORMAT.md). Не копируй каркас сюда.

Якоря: одна схема на экране; ghost-выбор + **Запустить**; метафора схемы под механизм (не копировать CORS-поток); 2–3 кейса на видимый паттерн; лог — квитанция. Проводка: `hasLab` + `TopicPage`.

## Workflow новой темы

```
1. Уточнить группу, уровень, заголовок, id (NNN-slug)
2. Сверить охват с группой: title в TOPIC_GROUPS + соседние темы той же groupId
3. Прочитать TOPIC_FORMAT.md (+ эталон Сути при широкой теме)
4. Добавить TOPIC_META в groups.ts (sortInGroup)
5. Написать topics/NNN-….md **человекочитаемо** (схема + абзацы, не каталог) — только в рамках группы
6. Если middle/senior → лаба по скиллу лаб + parseTopicMd hasLab + TopicPage import
7. Чеклист темы в TOPIC_FORMAT.md + «тема связана с группой» + «текст читается вслух без жаргонного телеграфа»
```

## Чего не делать

- Не копировать весь `TOPIC_FORMAT.md` в ответы пользователю — делай тему по правилам.
- Не дополнять / расширять заголовок в `# 1. Тема` — только исходное имя.
- Не писать тему вне предметной области её `groupId` и не игнорировать соседние темы группы.
- Не массово переписывать старые темы без запроса.
- Не ставить лабу junior «на всякий случай».
- Не оставлять в UI агентские инструкции про формат.
- Не писать mermaid в темах — рендерер его не рисует.
- Не делать «Описание» каталогом API без схемы и «зачем».
- Не писать тему как RFC / глоссарий: без абзацев «своими словами», с необъяснённым stub/NXDOMAIN/RR «с порога».
- Не подменять связный текст телеграфом `A → B → C` и таблицей из 8 типов.
- Не считать уровень senior поводом уплотнять жаргон: «базовое / общее понимание» — картина для человека.
